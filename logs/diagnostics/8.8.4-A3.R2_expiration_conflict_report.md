## Executive Summary

The RTB signal expiration mechanism has a **fundamental design flaw** in its unique index strategy. When `expireSignal()` attempts to UPDATE a signal's status from 'queued' to 'expired', it conflicts with existing expired records for the same (mode, symbol, strategy) combination.

**Root Cause:** The unique index includes `status` as part of the composite key, allowing multiple records per (mode, symbol, strategy) as long as they have different statuses. However, when updating a 'queued' record to 'expired', it creates a duplicate key violation if an 'expired' record already exists.

## 8. Root Cause Summary

### The Problem
1. The unique index `rtb_signals_symbol_strategy_idx` includes `status` in its composite key
2. This allows multiple records per (mode, symbol, strategy) with different statuses
3. Old 'expired' records are NOT cleaned up before new signals are queued
4. When a new 'queued' signal is later expired, it conflicts with the old 'expired' record

### The Sequence
```
T1: Signal A created → (paper, ETHUSD1, mean_reversion, queued)
T2: Signal A expired → (paper, ETHUSD1, mean_reversion, expired)  
T3: Signal B created → (paper, ETHUSD1, mean_reversion, queued) [OK - different status]
T4: Signal B expired → ERROR! (paper, ETHUSD1, mean_reversion, expired) already exists
```

---

## 9. Recommended Fix Options (Read-Only - No Changes Made)

### Option A: Clean Old Expired Records First
Before expiring a signal, delete any existing expired records for the same (mode, symbol, strategy).

### Option B: Modify expireSignal() to Use UPSERT Logic
Instead of UPDATE, use INSERT ON CONFLICT to replace the old expired record.

### Option C: Change Unique Index
Remove `status` from the unique index, allowing only one signal per (mode, symbol, strategy) at any time. This would require additional logic to handle status transitions.

### Option D: Soft Delete with Tombstone
Instead of keeping expired records, hard-delete them or move to a history table.
