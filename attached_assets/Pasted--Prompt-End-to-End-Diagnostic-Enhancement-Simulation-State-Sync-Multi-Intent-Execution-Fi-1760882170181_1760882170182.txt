Part A — Simulation State: Diagnose & Repair
A1. Source of Truth & Idempotency

Ensure a single authoritative source of simulation state (paper_sim_sessions or system_state service).

Implement idempotent handlers:

startPaperSim({userId, mode:'paper', runForMs?, startingBalance?})

stopPaperSim({userId, mode:'paper'})

getPaperSimStatus({userId, mode:'paper'}) → {isRunning, startedAt?, endsAt?, sessionId?}

Starting when already active returns current session; stopping when already stopped returns {isRunning:false}.

A2. State Reconciliation Contract

All components (Walter, APIs, UI) must call getPaperSimStatus after every start/stop.

Start sequence: validate → approvals (if needed) → startPaperSim → getPaperSimStatus → reply.

Stop sequence: stopPaperSim → getPaperSimStatus → reply.

A3. Consistent Surfacing (API/UI/Broker)

/api/state/summary, dashboard toggle, and Walter’s “status chip” must all read from the same state source.

Emit and persist cluster_bus_event(topic='simulation_state_changed') on every start/stop.

Create walter_execution_log entries (action_type:'start_sim'|'stop_sim', sessionId, etc.).

Add a missing simulation_sessions record when needed (start_time, mode, portfolio_balance, status:'running').

Include sessionInfo in Walter’s chat JSON output.

A4. Acceptance Tests

1️⃣ Start twice → only one active session.
2️⃣ Dashboard + /api/state/summary show RUNNING after start, STOPPED after stop.
3️⃣ Walter’s chat reply mirrors true state (no contradictions).
4️⃣ Logs and events exist for start and stop.

Part B — Multi-Intent & Multi-Step Execution
B1. Intent Extraction & Batching

Extend nlai-interpreter.ts to detect and queue multiple intents (guardrails, screeners, goals, strategies, simulation, reporting, etc.) from a single message.

Preserve parameters and execution order.

Chunk oversized messages but never drop sections.

B2. Brokered Sequential Execution

In nlai-execution-broker.ts:

Sequentially execute each intent with policy checks, execution, logging, and cluster events.

Continue on non-critical failures; record all results.

Link child logs to a parent_command_id.

B3. Unified Response Aggregator

Replace JSON fallbacks with a human-readable summary:

Overall Summary of the session.

Per-Intent Results showing old→new values, strategies used, status of sim, approvals, errors (if any).

Use compact tables or short code blocks for data; never dump raw JSON.

B4. Token & Length Safety

Add message chunking and re-ordering logic to avoid context loss for long inputs.

B5. Approvals Integration

Auto-approve low-risk paper-mode actions within guardrails.

Create pending approvals for higher-risk or live actions and return a summary listing which steps executed and which are awaiting approval.

B6. Acceptance Tests

Send the entire “Purpose Alignment & Performance Run” message → detect and execute all intents in order.

Output one well-formatted response with no raw JSON.

Verify each intent’s result and logs in walter_execution_log.

Confirm simulation state accurate throughout (RUNNING then STOPPED).
