Directive 8.8.4-A3.R1 – Verification & Hardening of Pair-Key SQE Integration

Classification: Verification & Stability Directive
Parent Phase: 8.8.4 – Ready-to-Buy (RTB) Completion
Issued: 2025-12-17
Objective:
Verify, harden, and finalize the 8.8.4-A3 implementation for pair-level validation and SQE re-qualification to guarantee long-term stability, correctness, and alignment with architectural standards.

1. Verification Objectives

Replit must verify and provide evidence (code excerpts or logs) that the following five areas are correctly implemented and functioning:

Area	Verification Target	Expected Evidence
1. Pair-Key Normalization	Pair keys must be normalized as uppercase ${BASE}/${QUOTE} prior to storage or comparison to prevent case mismatches (e.g., btc/usd ≠ BTC/USD).	Code snippet showing: const pairKey = \${signal.base.toUpperCase()}/${signal.quote.toUpperCase()}``
2. Active Trade Verification Source	hasActivePair() must check the active trades table (e.g., open_trades or paper_sim_open_positions), not cached RTB data.	Code snippet of query used within hasActivePair()
3. Engine-Aware Refresh Control	The 30-second refresh cycle (refreshAndRank()) must only run when the trading engine is active for that mode.	Code check: if (!engine.isActive(mode)) return;
4. CWQI Decay Configurability	The CWQI decay coefficient (λ = 0.03/min) must be configurable (via system_settings, env, or constant).	Config file or code snippet showing CWQI_DECAY_RATE defined
5. RTB Promotion Synchronization	When a pair is promoted to an active trade, it must be removed from RTB before the trade record is created to prevent double-activation.	Log or code snippet from promotion flow showing removal before trade insert
