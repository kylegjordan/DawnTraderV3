📘 Phase 8.8.3-I — Ready-To-Buy (RTB) Lifecycle Fixes

Directive to Replit

🎯 Phase Goal

Ensure the Ready-To-Buy (RTB) Signals Pool behaves exactly as designed in the DawnTrader future-state architecture:

RTB MUST ALWAYS reflect the most recent, valid strategy signals generated from:

Active Filtered Pool → Strategy Evaluation → RTB Candidate Queue

And the RTB pool must stay:

fresh

deduped

auto-expiring

aligned with active trades

correctly WebSocket-updating

This phase ensures pipeline integrity before we proceed to 8.8.3-J Metrics and 8.8.3-K Trade History.

📍 CONTEXT (Full System Summary)

To avoid ambiguity, here is the intended lifecycle exactly as ChatGPT and the future-state blueprint specify.

1. Strategy signals generate ~every FX5 cycle

FX5 runs every 30 seconds

Strategy Engine evaluates all Active Filtered Pool symbols

This produces zero or more signals

RTB should reflect exactly the most recent signals, not a historical accumulation

2. RTB pool should store only FRESH signals

1 signal = 1 pair + 1 strategy + 1 timestamp
TTL should match exactly one FX5 cycle (≈ 30 seconds)

3. RTB must NOT contain:

expired signals

duplicates

signals for symbols with an active trade already open

symbols already in RTB

stale signals from prior simulations

signals whose FX5 eligibility has expired

4. RTB Auto-Refresh

UI auto-refresh is 30 seconds, but the backend pipeline should correctly manage:

signal expiration

signal deduping

removal of signals once they are processed or become invalid

5. Once a trade executes for a signal →

it MUST be removed immediately from RTB

it MUST NOT re-enter RTB until cooldown finishes

backend must enforce this with storage checks

This has been implemented in parts but not holistically validated after the watchlist removal + Active Filter Pool integration.

Task 2 — Fix RTB Expiration (TTL)

Ensure signals expire after EXACTLY one FX5 cycle.

Requirements:

Each signal must store createdAt timestamp

TTL = 30 seconds (or FX5_SCAN_INTERVAL from config)

Any signal older than TTL is removed automatically

Implementation:

Add cleanup method to RTB service

Run at each FX5 cycle OR at each enqueue

Also run when getReadyToBuy() is called

Task 3 — Prevent Any RTB Entry for Symbols Already Being Traded

Current state:

This logic exists in some code paths

But must be audited post-watchlist removal and Active Pool migration

Requirements:

Before inserting a signal into RTB:

Check if symbol exists in storage.getActiveTrades()

If active trade exists → reject signal

Add detailed logging tag prefix:
[8.8.3-I][RTB_REJECT_ACTIVE]

Task 4 — RTB Deduping (Exact Behavior)

If a symbol already exists in RTB, then:

It must NOT be added again

BUT its timestamp should refresh if a new signal arrives
(fresh signal replaces stale one)

Required behavior:

either REPLACE existing signal

or UPDATE timestamp + strategy info

Rejecting duplicates entirely is wrong — newer signals should override older ones.

Task 5 — Remove All Stale Data Between Simulations

Problem:

Replit logs show RTB sometimes persists across simulations

Old signals appear after simulation restart

This is unacceptable

Fix:

When paper sim resets → RTB storage must fully clear

Add logs:
[8.8.3-I][RTB_RESET]

Task 6 — Fix RTB → Active Trades Transition

When a trade is opened (BUY):

Remove matching signal from RTB immediately

Also:
