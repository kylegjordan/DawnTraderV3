Objective: Enable live, regime-aware scanning ratio adjustment between Ideal and Rotational pools by introducing explicit pool tracking in telemetry.

🧠 1. Revision Summary (Why This Change Matters)

Gemini correctly identified that the telemetry_history table did not include a pool column.
Without this, we can’t distinguish whether a trade originated from the Ideal or Rotational pool, which is central to the new Adaptive Ratio Manager.

The revision adds this missing field and ensures it’s recorded for every strategy performance entry.

Task 2 (Updated Telemetry Repository Queries)

File: /server/services/telemetry-repository.ts

Revised to use the new column safely.

export async function getPerformanceByPool(poolType: "ideal" | "rotational", regime: string) {
  const result = await db
    .select({
      winRate: sql`AVG(win_rate)`,
      avgEdge: sql`AVG(expected_edge)`,
    })
    .from(telemetry_history)
    .where(
      and(
        telemetry_history.pool.eq(poolType),
        telemetry_history.regime.eq(regime),
        telemetry_history.mode.eq("live")
      )
    );

  return result[0];
}


✅ No query failures.
✅ Now aligned with schema v1.5.5.
✅ All ratios are computed on pool-segmented data.

🧩 3. Telemetry Recording Flow

Before (11.1A):

Trade → TelemetryAggregator → recordStrategyPerformance()
  |→ telemetry_history (regime, symbol, win_rate, mode, ...)


Now (11.2 R1):

Trade → TelemetryAggregator → recordStrategyPerformance(pool)
  |→ telemetry_history (regime, pool, symbol, win_rate, mode, ...)


This ensures that for every trade and signal, we retain a traceable “pool of origin.”
