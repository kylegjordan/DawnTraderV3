Directive: I7-COMPACT-MAP – Fix Compact vs Canonical Symbol Mapping for WebSocket & REST
Context (Please Read First)
We’ve confirmed all of the following:


The only exchange DawnTrader currently trades on is Kraken.


FX5 emits symbols that ultimately arrive in DawnTrader as “compact” symbols (no slash, sometimes with Z-prefixed fiat codes, e.g.:


RUJIUSD, RUJIEUR


ZUSDZJPY


MORPHOUSD


APTEUR


GOMININGEUR




The paper positions stored in paper_sim_open_positions also use these compact symbols.


The KrakenAssetPairsService (server/markets/kraken-asset-pairs-service.ts) and mapping logic already:


Fetch all Kraken AssetPairs (≈1,349 pairs).


Build a canonical view (base/quote, wsname, altname, etc).


Are correctly initialized (I7-MAP-AUTO-FIX is working).




WebSocket adapter is now starting at server boot and can receive ticks when correctly subscribed.


Current problem: The mapping layer does not reliably interpret these compact symbols, so WebSocket subscriptions and REST mapping fall back to kraken_rest for most symbols.


Key constraints / decisions:


✅ Do NOT change the database schema.


✅ Do NOT change the signal/strategy/orchestrator pipeline to stop compacting names.


✅ All fixes should be contained in:


kraken-asset-pairs-service.ts


kraken-symbol-resolver.ts


The price / subscription call sites (PaperExecutionEngine / LivePricingAdapter / WS adapter), without altering signal generation.




Goal:
Make the mapping layer treat compact symbols as first-class citizens, so that both WebSocket and REST mapping work correctly for any FX5-emitted symbol, without touching DB schema or strategy engine behavior.

High-Level Design
Current Flow (Simplified)


FX5 → DawnTrader receives symbol as compact (e.g. MORPHOUSD).


Strategy engine / SignalOrchestrator creates signals using compact symbols.


PaperExecutionEngine opens positions with symbol stored as compact (e.g. MORPHOUSD).


Pricing / exits / WS subscribe call mapping functions like toKrakenWS(symbol) or toKrakenRest(symbol) with that compact symbol.


Mapping layer is primarily keyed by canonical format (MORPHO/USD), not compact.


Result: many symbols fall back to REST, and WebSocket coverage is partial.


Target Flow


FX5 + strategy pipeline still produce compact symbols (no change).


When pricing or subscribing:


Engine passes compact symbol (e.g. MORPHOUSD).


Mapping layer:


Recognizes it as compact.


Resolves to canonical MORPHO/USD.


From canonical, resolves both:


Kraken WebSocket wsname (e.g. MORPHO/USD)


Kraken REST pair (e.g. MORPHOUSD or same wsname if appropriate).








WebSocket and REST calls always go through the mapping layer, which supports:


canonical → exchange pairs


compact → canonical → pairs




No DB schema changes required. No changes to strategy engine / orchestrator behavior.

Inside the KrakenAssetPairsService class, where you store pair metadata (e.g. maps keyed by canonical symbol, wsname, altname), add:
// New: map from compact symbol (e.g. 'MORPHOUSD') → pair info
private compactSymbolMap: Map<string, KrakenPairInfo> = new Map();

Where KrakenPairInfo is whatever struct you currently use internally (base, quote, wsname, restName / altname, tier, status, etc.).
1.2 Populate compactSymbolMap during refresh()
In refresh() where you iterate through Kraken’s AssetPairs results and build the internal map(s):


After you determine the canonical internal symbol and base/quote (e.g. "MORPHO/USD", base=MORPHO, quote=USD):

IMPORTANT: Use Kraken internal base/quote codes, not wsname base/quote. This ensures:


ZUSD + ZJPY → ZUSDZJPY


RUJI + USD → RUJIUSD


etc.




If you already produce a compact somewhere else, unify and reuse that logic rather than duplicating.


1.3 Add a resolver for compact symbols
Add a new public method:
public resolveByCompactSymbol(compact: string): KrakenPairInfo | null {
  if (!compact) return null;
  const key = compact.trim().toUpperCase();

  const hit = this.compactSymbolMap.get(key);
  if (hit) return hit;

  // Optional: lenient fallbacks if needed
  // e.g. if key contains '/', try removing it and look again.
  // For now keep it simple.
  return null;
}

1.4 Update resolveAny to consult compact map
You already have a method like resolveAny(symbol: string) that tries canonical + wsname + altname.
Update it roughly as:
public resolveAny(symbol: string): KrakenPairInfo | null {
  if (!symbol) return null;
  const trimmed = symbol.trim();
  const upper = trimmed.toUpperCase();

  // 1) If it looks canonical (has '/'), use existing canonical resolution
  if (upper.includes('/')) {
    const byCanonical = this.resolveByInternalSymbol(upper);
    if (byCanonical) return byCanonical;
  }

  // 2) Try compact map (no slash)
  const byCompact = this.resolveByCompactSymbol(upper);
  if (byCompact) return byCompact;

  // 3) Existing fallback logic (wsname, altname, tier-based, etc.)
  // ...
}

This ensures both forms are fully supported.

2) Update Kraken Symbol Resolver to Use the Compact-Aware Service
File: server/markets/kraken-symbol-resolver.ts

2.1 Normalize and route through resolveAny
Update toKrakenWS to use resolveAny:
export function toKrakenWS(normalSymbol: string): string | null {
  if (!normalSymbol) return null;
  const s = normalSymbol.trim().toUpperCase();

  // 1) Static map (Tier 0) – if you still maintain KRAKEN_SYMBOL_MAP
  const staticHit = KRAKEN_SYMBOL_MAP[s];
  if (staticHit?.wsName) {
    return staticHit.wsName;
  }

  // 2) Auto-map service (Tier 1/2)
  if (!krakenAssetPairsService.isReady()) {
    return null;
  }

  const info = krakenAssetPairsService.resolveAny(s);
  if (!info) return null;

  // Use whatever field you treat as WebSocket pair (e.g. wsname)
  return info.wsname ?? info.restPair ?? null;
}

2.2 Same for toKrakenRest
export function toKrakenRest(normalSymbol: string): string | null {
  if (!normalSymbol) return null;
  const s = normalSymbol.trim().toUpperCase();

  const staticHit = KRAKEN_SYMBOL_MAP[s];
  if (staticHit?.restName) {
    return staticHit.restName;
  }

  if (!krakenAssetPairsService.isReady()) {
    return null;
  }

  const info = krakenAssetPairsService.resolveAny(s);
  if (!info) return null;

  // Use the field you use for REST API (altname or pair name)
  return info.restName ?? info.wsname ?? null;
}

2.3 Make isMappable truly cover compact symbols
export function isMappable(symbol: string): boolean {
  if (!symbol) return false;
  const s = symbol.trim().toUpperCase();

  // Static Tier 0
  if (KRAKEN_SYMBOL_MAP[s]) return true;

  if (!krakenAssetPairsService.isReady()) return false;

  // Any form (canonical or compact) is fine
  return !!krakenAssetPairsService.resolveAny(s);
}

listUnmappableSymbols and getSymbolMappingDetails should rely on isMappable / resolveAny so they correctly treat compact names as mappable if they correspond to a real Kraken pair.
