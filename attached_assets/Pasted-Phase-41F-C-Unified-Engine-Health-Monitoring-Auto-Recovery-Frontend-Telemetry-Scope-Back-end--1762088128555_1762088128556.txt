Phase 41F-C — Unified Engine Health Monitoring, Auto-Recovery & Frontend Telemetry

Scope: Back-end health monitor + non-blocking broadcasts + automatic recovery hooks + a new System Monitoring tab (“Engine Telemetry”) + full validation (paper & live).
Do not reactivate Walter unless a step explicitly says to toggle a feature flag for a short validation and then turn it back off.

Context (why we’re doing this)

We’ve just completed production-grade queuing (41F-A/B): start/stop are serialized, deduplicated, and non-blocking with clean telemetry. The next reliability gap is observability: we need first-class visibility into queue health, trading engine loops, data feeds, cache, and DB—plus automatic recovery when something stalls (e.g., WS 403, long-running job, stuck busy flag). This phase adds a single source of truth for system health, continuous heartbeat, defensive self-healing, and a UI panel to make issues obvious within seconds.

Guardrails

Walter stays disabled. If you must touch Walter, wrap with WALTER_COMPAT_MODE=false and document any temporary enable/disable in logs.

Non-blocking everything: Health checks and broadcasts must never block HTTP routes or queue jobs.

No schema breaks: New tables/columns must be additive and backward-compatible.

Storage/Publishing

In-memory ring buffer (last 250 heartbeats) for quick UI charts.

Do not write to DB on each beat; emit via:

HTTP: GET /api/health/engine (returns latest + last N = 120s)

WS topic: health_engine broadcasting the latest snapshot

Add log markers: [41F-C][HEARTBEAT], [41F-C][CHECK].

2) Auto-Recovery Hooks

Inside HealthMonitor (or a sibling recovery.ts):

Rules (config in config/health.json):

Stuck queue job: executing age > queue.maxExecMs (default 3,000 ms) → log [41F-C][RECOVERY][QUEUE], soft reset job, notify listeners with failure, continue queue.

Engine idle / dead tick: last orchestrator tick > engine.maxTickGapMs (default 60,000 ms) while isRunning=true → emit [41F-C][RECOVERY][ENGINE] and call non-blocking engine.recover() (restart loop, not the process).

WS blocked: websocketStatus=blocked and last market update age > market.fallbackMaxAgeMs (default 20,000 ms) → force REST refresh & backoff jitter.

Busy flag drift: paper/live state mismatch (manager stopped but busy true) → clear flag safely and report.

All recovery actions must be fire-and-forget, never block API handlers.

3) Non-blocking Broadcast Separation

Ensure all contextBridge.broadcast* calls are queued to microtasks (e.g., setImmediate / queueMicrotask) and never awaited in HTTP paths.

Add markers [41F-C][BROADCAST] {event, latencyMs}.

4) Metrics APIs

GET /api/health/engine → latest beat + ring buffer (JSON)

GET /api/health/summary → reduced payload for widgets (overallOk, per-section ok, last latencies)

WS topic health_engine pushes the latest beat every 5s (or on state change)

5) Feature Flags

ENGINE_HEALTH_MONITOR_ENABLED=true

ENGINE_AUTO_RECOVERY_ENABLED=true

BROADCAST_NONBLOCKING_ENFORCED=true

All flags read from server config; default enabled.
