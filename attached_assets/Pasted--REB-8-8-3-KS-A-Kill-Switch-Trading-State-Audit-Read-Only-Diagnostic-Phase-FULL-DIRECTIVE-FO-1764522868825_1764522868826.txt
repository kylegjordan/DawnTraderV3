⭐ REB 8.8.3-KS-A — Kill Switch & Trading State Audit (Read-Only Diagnostic Phase)

FULL DIRECTIVE FOR REPLIT

🧠 Context

We are currently stabilizing Phase 8.8 (Real-Time Pipeline) and must verify the correctness of the trading state → engine state → passive learning relationships, as well as the daily-loss kill switch behavior.

DawnTrader’s architecture defines:

✔ isEngineActive[mode]

The single authoritative source of whether a mode (paper, live) is running in:

Active trading, or

Passive learning (when isEngineActive === false).

✔ Passive learning

Is not a mode.
It is always derived as:

passiveLearning = !isEngineActive

✔ Daily Loss Kill Switch

There is only one kill switch, and it is triggered only when realized 24-hour loss ≥ daily loss % threshold.

When triggered:

isEngineActive[mode] must flip from ACTIVE → STOPPED

The system remains in passive learning

No separate “kill switch state machine” should exist

✔ LATTI

May adjust guardrail/filter numeric values (if set to LATTI-controlled),
but LATTI must not:

Stop trading

Trip any kill switch

Set isEngineActive

Set any “tradingSuspended” or “killSwitchTripped” fields

✔ Manual Trading Toggle (header)

This is the normal user-controlled start/stop mechanism, and should:

Set isEngineActive[mode] ← True/False

Not trip kill switch states

🎯 Objective of this Audit

Produce a precise, forensic map of:

How trading active/stopped is currently implemented,

How kill switch states are implemented,

Whether any secondary/legacy kill-switch logic exists,

Where LATTI or Coherency rules may be improperly interacting,

What flags or states currently determine whether DawnTrader is ACTIVE or PASSIVE,

Every code path that can stop the engine.

No modifications will be made in this phase.

Output will be a human-readable report + JSON state map.
