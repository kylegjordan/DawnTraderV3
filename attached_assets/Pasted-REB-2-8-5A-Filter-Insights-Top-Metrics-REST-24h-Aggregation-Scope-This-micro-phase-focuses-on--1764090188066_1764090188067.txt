2. Next Scan Countdown – Correct Behaviour
2.1 Backend: true “time until next scan”
/api/paper-sim/diagnostics/scan-latest must continue to compute nextScanInMs on the server like this (or equivalent):
const lastScanTime = new Date(scanState.cycleEndTimestamp).getTime();   // ms
const scanInterval = scanState.cycleFrequencyMs; // normally 30000
const nextScanTime = lastScanTime + scanInterval;
const now = Date.now();
const nextScanInMs = Math.max(0, nextScanTime - now);



When the engine is ACTIVE, this should return something between 0 and scanInterval.


When the engine is STOPPED, return 0 for nextScanInMs.


2.2 Front-end: live countdown using REST only
In filter-insights.tsx:


Keep a currentTime state updated via setInterval every 1s.


Track the time of the last successful REST fetch for scan-latest:
const [restFetchTime, setRestFetchTime] = useState<number>(Date.now());

const { data: scanLatestData } = useQuery(/* ... */, {
  // existing options
  onSuccess: () => setRestFetchTime(Date.now()),
});



Compute the countdown purely from REST:
const serverNextScanMs = scanLatestData?.data?.nextScanInMs ?? 0;
const elapsedSinceFetch = currentTime - restFetchTime;
const remainingMs = Math.max(0, serverNextScanMs - elapsedSinceFetch);
const nextScanSeconds = Math.floor(remainingMs / 1000);



Display nextScanSeconds as the “Next Scan In” value.


Important implementation notes:


Do not involve any WebSocket payload here.


Do not reset restFetchTime when nextScanInMs is already 0; otherwise the timer can “stick” at 0. Only update restFetchTime in the onSuccess handler of the query.


The behaviour we want (and that Kyle is already seeing partially) is:


Count down 30→0.


When a new scan completes, REST returns a fresh nextScanInMs from ~30000, and the next countdown begins.


If REST polling frequency is 5s, the countdown will “jump” in 5s chunks but should never oscillate or stick at >0.





3. Cycles per Hour – Real Calculation, No Hard-Coding
Right now, cyclesPerHour is effectively a hard-coded 120.0. That’s not acceptable – it should reflect actual FX5 performance.
3.1 Backend calculation (recommended)
Implement cyclesPerHour on the server side (in the service that feeds scan-latest) roughly as:
// Per mode, keep a rolling array of recent cycle completion timestamps (in ms)
interface ScanHistory {
  timestamps: number[];
}

const scanHistoryByMode = new Map<string, ScanHistory>();

export function recordScanCompletion(mode: 'paper' | 'live', completedAt: number) {
  const history = scanHistoryByMode.get(mode) ?? { timestamps: [] };
  history.timestamps.push(completedAt);

  // Keep only the last 60 minutes
  const oneHourAgo = completedAt - 60 * 60 * 1000;
  history.timestamps = history.timestamps.filter(ts => ts >= oneHourAgo);

  scanHistoryByMode.set(mode, history);
}

export function getCyclesPerHour(mode: 'paper' | 'live'): number {
  const history = scanHistoryByMode.get(mode);
  if (!history || history.timestamps.length === 0) return 0;
  return history.timestamps.length; // “cycles in last hour” ≈ “cycles per hour”
}



Call recordScanCompletion(mode, Date.now()) once per FX5 scan when it finishes.


In your scan-latest handler, set:
const cyclesPerHour = getCyclesPerHour(mode);



Return this in the scan-latest payload as data.cyclesPerHour.


3.2 Front-end display


Use only the cyclesPerHour value from the scan-latest response.


No WebSocket, no client-side math.


Format e.g. cyclesPerHour.toFixed(1) and style in blue as you’re already doing.


When the engine is STOPPED, recordScanCompletion should still be called if FX5 keeps scanning in passive mode – but the 24h aggregation will later be gated to ACTIVE. For the top card specifically, it’s acceptable for cyclesPerHour to gradually drop or reflect the current scan health.

4. 24h Filter Activity – REST-Only Aggregation (No Legacy Aggregator)
4.1 Remove usage of the legacy scan24hAggregator
For this micro-phase:


Do not use server/services/scan-24h-aggregator.ts or any scan24hAggregator.* calls for the 24h metrics.


If the file still exists, it must not be imported or referenced by the code paths serving /api/paper-sim/diagnostics/scan-24h.


All 24h metrics should instead be computed by a lightweight FX5-specific 24h window implemented alongside the FX5 scanner / diagnostics.
4.2 Implement a simple FX5 24h window
Create a small module (conceptually similar to the previous market-scanner 24h window) that:
interface Scan24hEntry {
  cycleId: string;
  completedAt: number;       // ms timestamp
  evaluatedCount: number;
  eligibleCount: number;
  evaluatedSymbols: string[]; // or Set<string> if you prefer
  survivedSymbols: string[];
}

type Mode = 'paper' | 'live';

const windowByMode = new Map<Mode, Scan24hEntry[]>();

Recording logic:


Add a function like:
function recordScanFor24h(mode: Mode, entry: Scan24hEntry, isEngineActive: boolean) {
  if (!isEngineActive) {
    // 24h metrics must only track ACTIVE trading cycles
    return;
  }

  const now = entry.completedAt;
  const window = windowByMode.get(mode) ?? [];
  window.push(entry);

  const cutoff = now - 24 * 60 * 60 * 1000;
  const trimmed = window.filter(e => e.completedAt >= cutoff);

  windowByMode.set(mode, trimmed);
}



Call this from wherever you already know all of these values – e.g. the same place that updates Stage-3 state and emits the scan-latest data:
recordScanFor24h(mode, {
  cycleId,
  completedAt: Date.now(),
  evaluatedCount,
  eligibleCount,
  evaluatedSymbols, // deduped list of symbols touched in this cycle
  survivedSymbols,  // deduped survivors
}, isEngineActive /* from engine state for this mode */);



Only record when the trading engine is ACTIVE for that mode (paper in your test).


In passive learning / STOPPED state, FX5 may still scan, but do not track those scans in this 24h window.




Aggregation logic for /scan-24h:
In the handler for GET /api/paper-sim/diagnostics/scan-24h?mode=paper, compute:
function get24hSummary(mode: Mode): Scan24hResponse {
  const window = windowByMode.get(mode) ?? [];
  if (window.length === 0) {
    return {
      mode,
      totalCycles: 0,
      totalEvaluated: 0,
      totalSurvived: 0,
      uniqueEvaluated: 0,
      uniqueSurvived: 0,
      windowStart: null, // or ISO of now-24h; UI doesn’t rely heavily on this
      windowEnd: new Date().toISOString(),
    };
  }

  const totalCycles = window.length;
  const totalEvaluated = window.reduce((sum, e) => sum + e.evaluatedCount, 0);
  const totalSurvived = window.reduce((sum, e) => sum + e.eligibleCount, 0);

  const evaluatedSet = new Set<string>();
  const survivedSet = new Set<string>();
  for (const e of window) {
    e.evaluatedSymbols.forEach(s => evaluatedSet.add(s));
    e.survivedSymbols.forEach(s => survivedSet.add(s));
  }

  const uniqueEvaluated = evaluatedSet.size;
  const uniqueSurvived = survivedSet.size;

  const windowStart = new Date(window[0].completedAt).toISOString();
  const windowEnd = new Date(window[window.length - 1].completedAt).toISOString();

  return {
    mode,
    totalCycles,
    totalEvaluated,
    totalSurvived,
    uniqueEvaluated,
    uniqueSurvived,
    windowStart,
    windowEnd,
  };
}

The route should simply:
apiRouter.get('/paper-sim/diagnostics/scan-24h', (req, res) => {
  const mode = (req.query.mode as Mode) ?? 'paper';
  const summary = get24hSummary(mode);
  res.json({ ok: true, data: summary });
});

Key constraints:


This window is fed directly by FX5 and gated by engine ACTIVE state.


It does not depend on any legacy aggregator module.


It ignores passive learning scans, which matches the truth screenshots and your expectations.
