Instructions for Replit: Resilience & Safeguard Improvements
🎯 Objective

Harden the execution bot with resilience and recovery safeguards. These changes do not alter strategy logic or guardrails but improve real-world reliability under exchange and network conditions.

Phase 1: Bracket Order Rollback

Goal: If an order leg (entry, stop, or target) fails, the system must auto-cancel the others to prevent dangling orders.

Instructions:

Add orchestration so when placing bracket orders, all 3 must confirm success before considered “active.”

If any leg fails, rollback (cancel remaining legs, log error).

Add detailed logs for rollback events (✅ for success, ❌ for rollback).

Testing:

Simulate failure by mocking Kraken API returning error on stop order placement.

Verify: other orders are auto-cancelled, trade is marked invalid, log shows rollback.

Phase 2: Partial Fill Recovery

Goal: If only part of an entry order fills, system should manage remaining position correctly.

Instructions:

Detect partial fills (compare requested vs filled qty).

If below threshold (e.g. 90%), either:

Cancel leftover and manage filled portion with scaled stops/targets, or

Place catch-up order (configurable).

Record decision in audit trail.

Testing:

Simulate partial fill with mock API response (50% filled).

Verify: stops/targets match filled quantity, leftover handled per config.

Phase 3: Exchange Constraint Enforcement

Goal: Enforce tick size & minimum notional before sending orders.

Instructions:

Add validation layer before order submission.

Round prices/quantities to Kraken’s tick size.

Block orders that fall below min notional, with clear error message.

Testing:

Try to place order at $0.00001 with $0.10 notional.

Expect: ❌ Rejected with “Notional below Kraken min” message.

Try odd decimal precision → expect auto-rounded.

Phase 4: Rate Limit Handling

Goal: Prevent ban from hitting Kraken API too fast.

Instructions:

Add rate limiter in KrakenService.

Queue requests if needed.

Use exponential backoff when 429 (too many requests) received.

Testing:

Simulate burst of 50 API calls in 1 second.

Verify: requests are throttled, no hard Kraken rejections.

Log should show backoff retries when 429 occurs.

Phase 5: Retry Logic for Network/API Errors

Goal: Automatically retry transient errors.

Instructions:

Wrap Kraken API calls in retry mechanism.

Retry on network errors (timeouts, 5xx errors).

Max 3 retries with exponential backoff.

On permanent failure, log & mark trade as aborted.

Testing:

Simulate timeout on first call → system retries.

Verify: trade proceeds after retry success.

Simulate 3 consecutive failures → ❌ abort + log.

Phase 6: Advanced Safeguards (from EXECUTION_BOT_REVIEW.md)

Goal: Implement resilience features #6–10.

Instructions:

Add circuit breaker: stop trading for 60s if 5 consecutive API failures.

Add order validation echo: confirm order details after Kraken ack.

Add failover logging: duplicate logs to file + DB for audit safety.

Add sequential confirmation: wait for each step to confirm before proceeding to next.

Add safety net close: if any position is orphaned, auto-close it at market.

Testing:

Simulate 5 API failures in a row → expect circuit breaker activated.

Corrupt one order confirmation → expect rejection.

Kill DB temporarily → logs should still write to file.

Orphan test: close stop order manually via API, system should detect & close position.
