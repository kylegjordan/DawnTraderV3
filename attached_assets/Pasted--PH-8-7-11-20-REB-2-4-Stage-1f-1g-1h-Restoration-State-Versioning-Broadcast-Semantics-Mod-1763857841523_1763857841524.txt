4. Behavioral Truth You’re Restoring

Summarizing Stage-1f / 1g / 1h from the truth docs:

4.1 Stage-1f – State Versioning

Each scan cycle produced a monotonic stateVersion (or equivalent scanCycleId).

This version:

Was attached to the entire scan snapshot, not individual fragments.

Allowed consumers (UI) to know: “these metrics, breakdowns, pool stats all belong to the same cycle.”

Was the basis for ensuring no mixed-cycle payloads.

Key properties:

Version increments once per completed scan (per mode).

No version bump until the whole scan is ready.

Version is per mode (paper vs live), not global.

4.2 Stage-1g – Acknowledged Delivery / De-mixed Payloads

Broadcast logic never emitted partial, mixed, or stale states.

The system:

Waited until all required components for that cycle were available (FX5 metrics, breakdown, Active Pool summary, etc.).

Emitted a single, unified payload per cycle with a consistent version.

Ensured the UI never saw “half updated” or “previous metrics + new breakdown.”

The UI implicitly “acknowledged” this by always using the latest version from the WebSocket payload.

No complex NACK protocol is needed here; the key is atomic broadcast with a single version.

4.3 Stage-1h – Blocking Broadcast / Atomic Snapshot

Emission was blocking / atomic per cycle:

For a given mode (paper/live), the system did not emit the next cycle’s payload until the current cycle’s snapshot was complete.

This ensured:

No overlapping or interleaved payloads.

No “UI thrash” where multiple overlapping updates raced in.

Clean, predictable UI state.

Logging included markers like:

[STAGE1][DEBUG] Emitting unified scan snapshot (paper, version=123)

[STAGE1][DEBUG] Skipping emit - snapshot incomplete

You are restoring this model, NOT inventing a new one.

5. Implementation Plan
STEP 1 – Identify/Refactor the “Snapshot Builder”

Locate the module/function that currently:

Collects FX5 scan results.

Reads 24h metrics / scan counts.

Reads Active Pool stats.

Assembles the payload used for filter insights / WebSocket.

If this logic is scattered:

Introduce a single, small “snapshot builder” function (e.g. buildScanSnapshot(mode)), but keep it in an existing, appropriate file (no new top-level service).

This function should:

Take mode (paper/live).

Gather all required pieces from existing services.

Return a single typed object (e.g. ScanSnapshot) that includes stateVersion.

Do NOT add new business logic beyond:

Version handling.

Atomic assembly.

STEP 2 – Restore State Versioning (Stage-1f)

Implement a per-mode version tracker:

For example: in a scanner/broadcast context module:

type Mode = 'paper' | 'live';

const scanStateVersion: Record<Mode, number> = {
  paper: 0,
  live: 0,
};


Or reuse an existing structure if the truth docs show a specific pattern.

Rules:

Increment version only when:

A full snapshot has been successfully built for that mode.

Attach the version to the snapshot:

interface ScanSnapshot {
  mode: Mode;
  stateVersion: number;
  // existing fields: metrics, breakdown, pool stats, etc.
}


Do not persist this version in the DB unless the truth docs explicitly show that.
If unclear, keep it in-memory only, scoped to the process.

STEP 3 – Restore Atomic Broadcast (Stage-1g/1h)

Identify the code that emits WebSocket updates for the scan:

Likely something like broadcastScanUpdate(...), wsHub.emit('scan_tick', ...), etc.

Change that emitter so it only ever emits full ScanSnapshot objects with a version:

No more incremental or partial payloads for that channel.

If you currently send smaller fragments, keep that code unchanged for other channels.
For the main scan insights channel, you must send the unified snapshot.

Implement minimal gating logic:

If any required component for a snapshot is missing or errors:

Do not emit.

Log a debug line like:

[STAGE1H][DEBUG] Skipping emit for paper - snapshot incomplete (missing breakdown)


On success:

[STAGE1H][DEBUG] Emitting unified scan snapshot (mode=paper, stateVersion=NNN)


Ensure that, for a single mode, only one snapshot per 30s cycle is emitted (unless an explicit retrigger is part of the truth docs).

STEP 4 – Integration with FX5 and Active Pool (No Behavior Changes)

FX5 behavior is already restored – do NOT alter its filtering logic or batch logic.

Active Pool behavior is already restored – do NOT alter TTL, dedupe, or passive enforcement.

Your snapshot builder should consume the results of FX5 and Active Pool as they are now exposed; it should not change their behavior.
