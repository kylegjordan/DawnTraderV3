🔹 Phase 22.3 – Live Trading Voice/Chat Activation with Manual Approval
A. Add Intents to the NLAI Registry

Register new action intents:

startLiveTrading

stopLiveTrading

checkLiveTradingStatus

Use the same naming and structure as startPaperSim, stopPaperSim, getPaperSimStatus.

B. Extend ExecutionPolicyController

Add new policy definitions for live trading:

approval_required: true

risk_threshold: critical

mode: 'live'

When a live-trading start command is received:

Create an entry in walter_execution_log with approval_status='manual_required'.

Return a chat confirmation message identical to the UI modal text:

“Are you sure you want to start live trading? This will enable real orders. Please confirm.”

Require explicit approval from the authenticated user via “Yes, I approve” or clicking the approval button in the chat.

C. Unified Approval Flow

Reuse the same approval modal used for the UI toggle switch.

Whether the user confirms through chat or by clicking the modal, both actions update the same approval record.

D. Start/Stop Flow

startLiveTrading:

On approval → activate live mode; emit cluster_bus_event(topic='mode_changed', data:{mode:'live'}).

Update /api/state/summary and dashboard chip → LIVE ACTIVE.

stopLiveTrading:

Deactivate live mode; emit the same event with {mode:'stopped'}.

Update status in summary and dashboard chip.

E. Acceptance Tests

Command “start live trading” → expect confirmation prompt → approve → state changes to LIVE ACTIVE.

Command “stop live trading” → expect state changes to STOPPED.

Verify walter_execution_log entries and cluster_bus_event emissions for both actions.

Confirm both UI toggle and chat command share the same approval source.

🔹 Phase 23 – Simulation Heartbeat & Recovery
A. Heartbeat Scheduler

Implement a lightweight scheduler (paper_sim_heartbeat.ts) that:

Runs every 30 seconds.

Queries paper_sim_sessions for status='running'.

Checks each session’s ends_at or run_for_ms.

Emits heartbeat events to cluster_bus_event(topic='simulation_heartbeat').

B. Recovery Logic

On application startup:

Check for paper_sim_sessions where status='running' and stopped_at IS NULL.

If the session ends_at > now → resume monitoring.

If expired → set status='stopped' and stopped_at=now(), emit simulation_state_changed.

C. Automatic Restart Option

If configured (autoResumeSimulations=true in system config), automatically resume any interrupted sessions.

D. State Consistency

Ensure /api/state/summary reflects recovered or resumed sessions.

Walter should notify the user on login if a prior session was resumed or force-stopped.

E. Acceptance Tests

Start a simulation → restart the server → verify it auto-resumes or cleanly stops based on time remaining.

Confirm a simulation_heartbeat event fires every 30 s.

Verify Walter reports accurate session status after recovery.
