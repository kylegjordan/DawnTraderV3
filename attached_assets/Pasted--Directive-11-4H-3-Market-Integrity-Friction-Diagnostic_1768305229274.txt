⚙️ Directive 11.4H.3 — Market Integrity & Friction Diagnostics Before Fix
Phase Objective

Before making any architectural corrections, we will diagnose and verify the sources of:

Global Friction Static Values (14 or 25)

Pair-Level Friction Flattening (“Moderate Liquidity” everywhere)

This directive adds auditing, tracking, and proof collection so that we can confirm the hypotheses before committing to code-level changes.

🧭 Context & Theoretical Basis
🧩 1️⃣ Global Friction — Hypothesis: Statistical Undersampling

Observation:
Global friction consistently returns 14 or 25, regardless of market conditions.

Hypothesis A (Primary):
The current calculation is based only on survivor pairs in each scan (≈17 pairs).
That sample is too small and too homogeneous, causing a narrow variance in friction values.

Expected Behavior:
If friction were calculated over the full Ideal + Rotational pools, or as a rolling accumulation, it should vary dynamically with market liquidity.

Evidence for Hypothesis A:

Survivor count ≈ 17 per scan (from telemetry).

Reported values are exact integers (14, 25) — suggests post-rounding from low-variance mean.

Logs don’t show global friction variability across scans.

Hypothesis B (Secondary):
The calculation might be rounding or flooring too early (e.g., rounding before averaging).
That would compress scores into the same rounded output repeatedly.

Hypothesis C (Less likely):
All spreads are being pulled from a cached data snapshot that’s not refreshing across cycles.

🧮 Diagnostic Plan for Global Friction

We’ll trace and log each step of the global friction computation — data source, sample size, variance, and result — to prove or disprove each hypothesis.

Diagnostic Insert (cost-metrics.ts):

logger.info(`[GlobalFriction][Audit] Sample size: ${pairs.length}`);
logger.info(`[GlobalFriction][Audit] Raw spreads: ${pairs.map(p => p.spread).join(',')}`);
logger.info(`[GlobalFriction][Audit] Mid prices: ${pairs.map(p => p.mid).join(',')}`);
logger.info(`[GlobalFriction][Audit] Individual friction scores: ${pairs.map(p => (p.spread / p.mid) * 10000).join(',')}`);
logger.info(`[GlobalFriction][Audit] Global friction value: ${computedGlobalFriction}`);


Audit Output Analysis:

Expected Finding	Meaning
Sample size ≤ 20	Confirms undersampling → supports Hypothesis A
Spread variance ≈ 0	Indicates cached snapshot issue → supports Hypothesis C
Friction rounding early (integer array)	Supports Hypothesis B
Varying raw spreads but static final friction	Confirms aggregation/rounding issue

Goal:
Produce a console/audit log confirming whether the global friction is truly static due to small-sample aggregation, stale data, or rounding errors.

🧩 2️⃣ Pair-Level Friction Flattening — Hypothesis: Cached or Uniform Source

Observation:
All pairs show identical friction labels (“Moderate Liquidity”).

Hypothesis 1 (Primary):
The percentile bands (Green/Orange/Red cutoffs) are cached and not recomputed each cycle.
If computeAdaptiveFrictionBands() is run once and cached, every cycle uses the same percentile thresholds → every score maps to the same label.

Hypothesis 2 (Secondary):
The friction scores themselves are constant because the spreads are being pulled from a static cache (e.g., a shared global ticker snapshot not updated per pair).
If all pairs use the same spread and mid, they will naturally produce identical friction scores.

Hypothesis 3 (Tertiary):
Band computation is correct, but normalization to percentile rank is flawed (e.g., division by zero or fixed normalization window).

🧮 Diagnostic Plan for Pair-Level Friction

We’ll perform pair-level logging and introduce a one-time audit function that prints every pair’s friction components per scan.

Diagnostic Insert (cost-metrics.ts):

logger.info(`[FrictionAudit] Cycle ${cycleId} - Pair Count: ${pairs.length}`);
pairs.forEach(p => {
  logger.info(`[FrictionAudit] ${p.symbol} | spread=${p.bestAsk - p.bestBid} | mid=${(p.bestAsk + p.bestBid)/2} | friction=${(p.spread / p.mid) * 10000}`);
});
logger.info(`[FrictionAudit] Band thresholds: Green<${bands.green}, Orange<${bands.orange}, Red>${bands.red}`);


Expected Diagnostic Findings:

Finding	Interpretation
All spreads identical	Supports Hypothesis 2 (shared cache)
Spreads vary, but labels same	Supports Hypothesis 1 (cached percentile bands)
Spreads vary, scores vary, labels vary	System working correctly
Bands change each cycle, labels still same	Check normalization (Hypothesis 3)
🔎 Diagnostic Phase Output Goal

We want to see at least two consecutive scan cycles of audit output showing:

Number of pairs used in global friction computation.

Spread variance per cycle.

Friction score variance per cycle.

Pair-level friction and label mapping per pair.

Once we have that data, we can prove which hypothesis is true and then proceed to targeted code correction.

🧠 3️⃣ Entropy Diagnostic Context

We already confirmed the reason entropy remains zero in audits:

In-memory telemetry resets on restart.

The audit script runs in isolation, not against live telemetry.

This is confirmed behavior — not an actual classifier fault.
We can safely say that entropy is “unknown,” not “zero.”

✅ Diagnostic Next Step:

Persist telemetry to a pair_telemetry table.

Rerun the entropy audit against that persisted dataset.

Confirm whether entropy rises as regimes diversify over runtime.

No code fix to the entropy algorithm yet — this is diagnostic infrastructure setup only.
