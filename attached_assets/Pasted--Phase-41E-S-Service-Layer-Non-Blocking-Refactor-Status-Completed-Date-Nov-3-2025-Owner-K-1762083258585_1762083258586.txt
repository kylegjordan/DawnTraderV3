globalPaperSimOperationLock contention between UI auto-start and API test request

Force-stop triggers UI recovery, which sets a lock before manual test starts

Root Cause Analysis

The system’s UI auto-recovery process launches a background start sequence immediately after a force-stop.

Manual test requests from the API collide with this sequence.

Both threads attempt to acquire globalPaperSimOperationLock.

The result is a dead wait and request timeout — not a service-layer blocking bug, but an architectural concurrency flaw.

Proposed Next Phase

Objective

Resolve concurrency and request-collision issues by introducing a sequential job execution model for trading operations.

Proposed Implementation

Replace globalPaperSimOperationLock with an async job queue that serializes start/stop operations.

Request Deduplication:
Use a (userId, mode, sessionId) key to identify duplicate or overlapping requests and discard them.

UI/API Decoupling:
Separate WebSocket-based UI recovery events from manual API commands to prevent collisions.

Enhanced Telemetry:

Expected Benefits

Eliminates concurrent lock contention.

Prevents start/stop overlap across UI and API triggers.

Ensures consistent trading state and faster recovery.

Reduces false-positive timeouts and improves reliability under load.
