Step 1 — Guardrails Mode Isolation (No Code)
🎯 Objective

Before starting paper trading, we must make sure that “Live” and “Paper” operations are fully isolated — both in data storage and runtime behavior.
This step ensures that simulated trades cannot ever touch real data, and that every query, record, and view belongs explicitly to one mode.

1.1 Purpose and Expected Outcome

Goal:
When a user switches between Paper and Live modes, the entire application context changes — displaying, writing, and calculating data only from the selected mode.

End Result:

Every database write/read includes the mode key ('paper' or 'live').

The API enforces x-app-mode on all relevant endpoints.

The UI instantly refreshes to reflect the active mode.

There is no shared or overlapping data between modes.

1.2 Scope

This step covers backend data isolation, API-layer enforcement, and frontend propagation.
It does not include new features, UI rearrangements, or trading logic changes.

1.3 Detailed Implementation Plan
Phase A — Database Layer (Schema and Persistence)

Add a mode column to all tables that hold user- or trade-specific data:

watchlists

screeners

screener_results

orders

positions

trades

Default new rows to paper mode until the user switches context.

Add composite indexes (user_id, mode) on these tables for efficient queries.

Confirm that all future SELECT/INSERT/UPDATE queries use both keys.

Acceptance Criteria

Each table now contains a non-nullable mode field.

All queries include both user_id and mode.

Legacy data (if any) is migrated safely into paper mode for continuity.

Phase B — Server /API Layer (Enforcement)

Middleware guard:

Require every incoming request to carry an x-app-mode header (paper or live).

Reject missing or invalid headers with 400 errors.

Route integration:

Apply the middleware to all trading-, screening-, and portfolio-related routes.

Request context:

Pass the validated mode into downstream services (database, business logic).

Error handling:

Return consistent structured JSON errors ({error: "Missing or invalid mode"}).

Acceptance Criteria

API calls without a valid mode header are rejected.

Logs show mode context for every request.

Each API writes/reads only mode-scoped data.

Phase C — Client Layer (Mode Propagation and UI State)

Single source of truth:

Create or confirm existence of a global “mode” state ('paper' | 'live').

Header injection:

Ensure every API request automatically attaches x-app-mode from that state.

UI toggle:

Maintain a toggle in the header, settings, or dashboard to switch modes.

When changed, all panels and cached queries reset to the selected mode’s data.

Visual confirmation:

Add subtle indicators (e.g., tag or banner) showing which mode is active.

Acceptance Criteria

Switching the toggle instantly refreshes data.

No cross-pollination of results or trades between modes.

Logs confirm mode header is sent on every call.

Phase D — Verification & Testing

Manual QA

Create one screener or watchlist entry in Paper mode → verify it’s invisible in Live.

Switch back and forth several times — no overlap.

Execute mock order in Paper mode → confirm no Live data touched.

Automated Checks

Add one test verifying that API requests without mode header fail.

Add one test verifying that switching mode changes dataset content.

Acceptance Criteria

Manual and automated tests confirm strict isolation.

Paper and Live databases remain independent throughout app lifecycle.
