🧩 Replit Preparation Guidelines
These are the standards and structure used to prepare every Replit-ready plan or implementation phase for the Dawn Trading system.
Each phase combines actionable clarity, no-code specificity, and verifiable deliverables designed for autonomous agent execution, logging, and testing.
________________________________________
🧠 1. Purpose and Intent
Every plan must begin with a clear, human-readable Objective Statement:
•	Explain what the phase accomplishes (in plain language).
•	Tie it directly to the system’s purpose (e.g., “support Walter’s mission to generate wealth efficiently and safely”).
•	Keep it goal-focused, not code-focused.
Example:
Objective: Create a weekly expert insights update system to keep Walter’s trading knowledge current and dynamic.
________________________________________
⚙️ 2. Structure and Format
Every Replit task plan must follow this exact structure:
Header
## Phase X.X – [Phase Title]
**Objective:** [Short, clear summary of the goal]
Implementation Plan and Progress Log
•	Organized as chronological progress entries (each one begins with an action phrase).
•	Each entry starts with a bolded action followed by a short log summary in a conversational progress tone.
•	Every action includes the intended result or verification step.
Format Example:
Checked code issues  
Decided on schema fix strategy (5 seconds)  
Edited server/services/behavioral-template.ts  
Restarted Start application  
Tested your app successfully  
Weekly Expert Insights Update Validation  
Watch replay
Each log should:
•	Read like a build diary, reflecting agent thought and action flow.
•	Be clear and testable, without exposing internal code.
________________________________________
🧩 3. No-Code, Descriptive Implementation
All actions should describe what is being built or fixed, not the raw code.
When referencing file edits:
•	Always use descriptive explanations like “Edited server/routes.ts to add endpoint for metrics tracking.”
•	Avoid full code blocks except for short, human-readable snippets (for clarity only).
Example:
Replaced storage.getUserById(userId) with storage.getUser(userId) to fix 500 error in strategy toggle.
This allows Replit’s internal systems to infer the implementation automatically while keeping logs readable for human review.
________________________________________
✅ 4. Actionable Checks
Each major step must end with a validation check:
•	“Server restarted successfully”
•	“Logs show no errors”
•	“API returned 200 OK”
•	“UI reflected expected state”
•	“Walter correctly identified enabled strategies”
These checks give Replit a clear pass/fail signal for that task stage.
________________________________________
🧪 5. Testing and Validation
Every phase ends with formal test runs (using Replit’s internal test runner).
Tests are described like progress logs:
Tested your app successfully  
Weekly Expert Insights Update Validation  
Watch replay
Followed by a natural-language summary of what the test confirmed.
If an issue arises, describe:
•	What failed
•	Why it failed
•	What the next fix will be
This keeps the flow of iteration transparent.
________________________________________
📊 6. Deliverables Table
Each phase concludes with a Deliverables Summary table listing every key outcome.
Example:
#	Deliverable	Status	Notes
1	Weekly insights task registered	✅	Scheduler verified
2	Duplicate prevention validated	✅	Working correctly
3	Transparency logs functional	✅	Logs recorded properly
4	Architect approval obtained	✅	Ready for next phase
This gives Replit an at-a-glance checklist of what must be working before moving forward.
________________________________________
🧱 7. Completion Statement
End each phase with a short success declaration:
🎉 Phase X.X – Completed Successfully!
✅ All deliverables verified and approved.
System stable and ready for next phase.
This line signals readiness for transition to the next implementation step.
________________________________________
🔁 8. Consistency Across Phases
Each new phase should:
1.	Begin by referencing the previous phase’s successful completion.
2.	Use consistent terminology (Walter, Bob, metrics, transparency, etc.).
3.	Maintain the same progress-log format.
4.	Include verification of zero regressions before moving on.
________________________________________
💬 9. Human Readability
Although Replit is processing these logs automatically, every entry should be human-auditable.
Anyone reading it should understand:
•	What was done
•	Why it was done
•	How success was confirmed
The style should be concise but personable — matching the tone of a human engineer reporting progress in real time.
________________________________________
🧠 10. Design Philosophy
Every Replit phase follows these principles:
1.	No ambiguity: Every action is clearly defined and independently testable.
2.	No raw code dumps: Describe intent, not syntax.
3.	Autonomous readability: Each entry can stand alone.
4.	Integrity-first: All actions must align with Walter’s wealth-generation and system-stability purpose.
5.	Transparency: Every major action logs to transparency_logs for future diagnostic access.
________________________________________
✅ Outcome of Using These Guidelines
By following these standards, every Replit task log:
•	Builds consistently and predictably
•	Passes automated and manual tests
•	Produces self-contained audit trails
•	Keeps the project human-readable and scalable
•	Aligns Walter’s and Bob’s development with your wealth-generation mission
