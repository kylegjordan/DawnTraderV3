⚙️ Directive 11.0 — TCO/TEC Separation & Trade Criteria Limiter Purification
Phase: 11

Title: Refactor the Trade Control Operator (TCO) and Trade Execution Controller (TEC) boundary; isolate the Trade Criteria Limiter (TCL) to eligibility gating only.

🧠 Background

The current architecture defines three major execution-adjacent layers:

Component	Purpose	Current Issues
TCL — Trade Criteria Limiter	Evaluates whether ready-to-buy pairs meet global criteria before being promoted to TCO.	Currently entangled with partial sizing logic and readiness checks that belong elsewhere.
TCO — Trade Control Operator	Orchestrates promotion of approved trade intents into execution orders.	Sometimes initiates sizing or exit validation instead of delegating them.
TEC — Trade Execution Controller	Handles actual trade execution, order sizing, lifecycle, and exits.	Some sizing and adaptive parameters are still being injected from TCL/TCO instead of being owned locally.

The goal of this directive is to:

Confine TCL strictly to trade eligibility logic only (no sizing, no execution).

Ensure TCO acts purely as the promoter that transitions eligible trade intents to the TEC.

Migrate all adaptive sizing, execution, and exit logic into TEC.

🎯 Primary Goals

Confirm and purge any adaptive sizing or risk logic still running in the TCL (Trade Criteria Limiter).

Move all trade sizing and exit decision logic into the TEC (Trade Execution Controller).

Validate that the TCO (Trade Control Operator) is the only intermediary allowed to promote trade intents to execution.

Update documentation and tests to reflect these role boundaries.

Task 3 — Strengthen TCO–TEC Interface

In trade-control-operator.ts, enforce this strict transition:

const eligible = tcl.evaluate(signal);
if (eligible.passed) {
  tec.enqueueExecution(signal);
}


The TCO must never compute or alter trade size.

Introduce an interface contract in interfaces/trade-flow.ts:

interface ExecutionIntent {
  signalId: string;
  instrument: string;
  entryPrice: number;
  timestamp: string;
}


TEC will enrich this intent with sizing and risk parameters internally.

Task 4 — Consolidate Adaptive Sizing in TEC

Move all dynamic sizing logic here.

Files:
server/services/execution-controller.ts
server/core/position-sizing.service.ts

Example structure:

class TradeExecutionController {
  async execute(intent: ExecutionIntent) {
    const size = await this.calculatePositionSize(intent);
    const order = this.createOrder(intent, size);
    await this.routeOrder(order);
  }

  calculatePositionSize(intent) {
    const volFactor = this.marketVolatility(intent.instrument);
    const baseRisk = this.portfolioRiskBudget();
    return baseRisk / volFactor;
  }
}


Adaptive sizing inputs that must live here:

Market volatility (VolNoise)

Account equity or drawdown limits

Regime sensitivity

Slippage tolerance
