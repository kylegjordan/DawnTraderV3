Step 8 Implementation Brief — Semantic Memory Layer

Milestone 15 — Vector Memory and Long-Term Learning Recall

🎯 Objective

Transform the trading AI’s learning history and decisions into knowledge that can be recalled and reused across sessions, users, and timeframes.

This milestone adds a semantic memory layer — a vector-based memory store that captures meaning rather than just text.
It allows the AI to answer questions like:

“What did we learn about ETH volatility in April?”
“Which strategies worked best when BTC was trending?”

and feed those insights directly into Paper→Live optimization.

🧱 Part A — Data Architecture & Storage Design

Goal:
Create a durable, searchable vector store for meaningful lessons and summaries.

Actions:

New Table: semantic_memory

Field	Type	Description
id	uuid	Primary key
embedding	vector(1536)	Vector representation of content
content	text	Human-readable summary or lesson
source_table	text	Origin (e.g. ai_lessons, portfolio_adjustments)
source_id	uuid	Reference ID
tags	text[]	e.g. ["BTC", "volatility", "paper-mode"]
created_at	timestamp	UTC timestamp
relevance	numeric	0–1 score for ranking

Index:

Vector index on embedding (for similarity search).

B-Tree index on tags.

Embedding Source:

Use OpenAI Embeddings API (text-embedding-3-small) for semantic vectors.

All embeddings ≤ 2 KB.

Deliverables:
✅ New table semantic_memory
✅ Database index and migration executed
✅ Verified schema and type definitions added to shared/schema.ts

🧩 Part B — Ingestion Pipeline

Goal:
Feed key insights and summaries from existing systems into semantic memory.

Sources:

ai_lessons → weekly summaries of learning outcomes

conversation_summaries → user context and preferences

portfolio_adjustments → actionable strategy changes

filter_calibration_log → calibration outcomes

Process Flow:

Scheduler Task: semantic-ingestion-task

Runs every 6 hours.

Selects new/updated records from the above sources.

Generates embeddings and inserts into semantic_memory.

Skips duplicates based on source_id.

Transparency Logging:

Log each batch to ai_transparency_log (taskName = "semantic-ingestion").

Include record counts and runtime.

Deliverables:
✅ Scheduler task registered in scheduler-registry.ts
✅ Transparency logging confirmed
✅ Schema cross-validation tests pass

🔍 Part C — Semantic Search & Recall API

Goal:
Allow AI and user interfaces to query semantic memory by meaning instead of exact words.

Endpoints:

POST /api/semantic/search
Body: { query: "what did we learn about BTC momentum?", limit: 10 }
Returns: top matches sorted by cosine similarity + relevance score.

GET /api/semantic/latest
Returns: latest 20 entries with tags and relevance ≥ 0.8.

GET /api/semantic/tags
Returns: distinct tags and their counts.

Integration Targets:

AI Transparency Panel → new “Semantic Insights” tab.

CLE Orchestrator → optionally consult semantic memory before applying new weights.

Deliverables:
✅ All three API routes implemented and documented
✅ Semantic results visible in Transparency Panel UI

⚙️ Part D — Learning Application and Confidence Boost

Goal:
Let CLE and AI chat layer draw on semantic memory to improve decisions.

Flow:

When Paper→Live transfer occurs, CLE queries semantic memory for similar patterns.

Incorporates insight weights into filter confidence calculation.

Updates autonomy_confidence_index using semantic boost:

Formula:
CI_new = CI_old + (0.1 × semantic_relevance_mean × 100)
(Capped at +10 points per cycle.)

Deliverables:
✅ Semantic boost logic added to CLE orchestrator
✅ Transparency log entry "semantic-boost"
✅ Confidence index updated and displayed

🧠 Developer Notes

Maintain existing scheduler intervals; add semantic ingestion only.

All timestamps UTC.

Embedding requests batched ≤ 100 records to stay under rate limits.

Handle OpenAI embedding errors gracefully with retry logic ×3.

Store raw embeddings as float8[] or Postgres vector type depending on DB version.

Tag structure should allow free-form labels (e.g. asset, strategy, mode).
