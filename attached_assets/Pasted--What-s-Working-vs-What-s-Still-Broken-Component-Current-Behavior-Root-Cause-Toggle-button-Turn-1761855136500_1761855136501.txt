🔍 What’s Working vs. What’s Still Broken
Component	Current Behavior	Root Cause
✅ Toggle button	Turns green instantly, then stops after ~2–3 min	UI driven by isTradingActive (fast), but backend stop signal takes too long to reflect due to async delay
🔵 Blue bar	Always says “STOPPED”	It’s reading from paperSimStatus.isRunning, which never gets updated by WebSocket broadcasts
🧊 Passive badge	Returns only after full refresh	The flag passiveLearning isn’t being re-broadcast on stop/start events
⏳ Portfolio value	Updates, but takes minutes	Same delayed refresh — query invalidation happens only after API completes, not when WS fires
🔔 Stop toast	Works, but late	WS handler doesn’t trigger the stop toast immediately; waits for REST confirmation
🧠 The Real Root Causes

The WebSocket broadcast and React Query invalidation are one-way.

The front-end updates only trading/status.

Other dependent queries (/api/paper-sim/status, /api/system/config) aren’t rehydrated — they wait for REST polling, hence the delay.

The TopBar’s blue bar depends on /api/paper-sim/status.isRunning, not on trading/status.active.

When trading_state_changed fires, it hydrates only /api/trading/status.

The paper-sim query remains stale, so it keeps showing STOPPED.

The backend doesn’t broadcast passiveLearning state changes.

The UI expects that flag to flip automatically when trading stops, but no event updates it.

Server stop/start endpoints are doing synchronous DB writes + recalculation before sending the WebSocket event.

That’s why you wait minutes — the server emits the WS after heavy operations complete (watchlist, goals recomputation, etc.).

⚙️ What to Fix Next (Minimal but Decisive)
🩵 1. Hydrate both trading and paper-sim caches when WS fires

In client/src/hooks/use-trading.tsx, inside the WebSocket listener:

if (payload) {
  console.log('[SYNC] trading_state_changed:', payload);

  // Hydrate both caches so TopBar blue bar + toggle match instantly
  queryClient.setQueryData(['/api/trading/status'], payload);
  queryClient.setQueryData(['/api/paper-sim/status'], {
    ...payload,
    isRunning: payload.active, // ensures blue bar updates immediately
  });

  // Force re-renders for both
  queryClient.invalidateQueries({ queryKey: ['/api/trading/status'], exact: true });
  queryClient.invalidateQueries({ queryKey: ['/api/paper-sim/status'], exact: true });
}


This ensures the blue bar (paperSimStatus) instantly mirrors the new trading state.

🟦 2. Update backend broadcasts to include passiveLearning

In server/services/trading-state-sync.ts, where contextBridge.broadcast is called:

await contextBridge.broadcast({
  type: 'trading_state_changed',
  payload: {
    userId: 'system-reconciliation',
    mode: currentMode,
    status: isEngineActive ? 'ACTIVE' : 'STOPPED',
    isEngineActive,
    active: isEngineActive,
    isEngineActivePaper,
    isEngineActiveLive,
+   passiveLearning: !isEngineActive, // show passive badge when stopped
  },
  mode: currentMode
});


Now the passive badge will reappear instantly after stopping.

⚡ 3. Fire the WebSocket before heavy backend tasks

In server/services/paper-sim-service.ts, inside startPaperSimulation() and stopPaperSimulation():

Move the broadcast up, right after state change but before expensive watchlist population or cleanup.

// Immediately broadcast the start so UI updates fast
await contextBridge.broadcast({
  type: 'trading_state_changed',
  payload: { mode: 'paper', active: true, passiveLearning: false },
});

// Continue background tasks...
populateWatchlistAsync();
recalculateGoals();


This cuts UI lag from minutes → milliseconds.

💬 4. Fire toasts for both transitions in WS listener

Still in use-trading.tsx, right after setQueryData:

if (payload.active) {
  toast.success('Paper trading started');
} else {
  toast.info('Paper trading stopped');
}


You’ll then see a consistent “Started / Stopped” feedback, matching the actual toggle state.
