🧪 Method — Exact Work Packages
A) Repository Mapping (DB → API → Client)

Database Map → audit/db_map.json
For each relevant table (examples): guardrails, screener_filters, strategy_settings/parameters, system_context, paper_sim_* (for current behavior references), trading_settings (if any legacy remnants), and LATTI-related config. Capture: table, columns, types, constraints, mode scoping, default sources. Note any per-user columns that still exist and whether they should be global-per-mode per the current architecture.

Endpoint Map → audit/endpoints_map.json
Enumerate all GET/PUT/POST routes that read or write guardrails/filters/strategy settings, scanner, and engine state. For each endpoint record: path, method, service/file owner, mode derivation, source-of-truth (DB table), returns, and known subscribers (WebSocket broadcasts).

Client Map (UI)
Catalog the components/containers that display or edit guardrails/filters/goals (e.g., guardrails-tab, filters-tab, Goals Engine panes, LATTI widget, Filter Insights/Filtered Pairs). Note read-only vs editable states, existing “Managed by Lottie” toggles, and any disabled controls tied to Live mode. Output a section inside audit/Phase1_recommendations.md.

B) Inventories (authoritative CSVs)

Guardrails Inventory → audit/guardrails_inventory.csv
Columns: name, description, unit, scope (mode/global), default_source (DB/env), client_surface (Y/N), api_endpoint(s), db_table.column, used_by (service).
Include current “core four” candidates you plan to keep visible: Portfolio Risk per Trade (%), Symbol Cooldown (minutes), Max Open Positions (count), Daily Loss Kill Switch (%) — plus all legacy items encountered. (Phase 2 will collapse to the core four and mark redundancies like max_drawdown, max_risk_$, max_position_size_cap for deprecation.)

Filters Inventory → audit/filters_inventory.csv
Columns: name, category, type (range/list/boolean), scope (mode/global), db_table.column, default_source, api_endpoint(s), used_by (scanner/strategy).
Include active inputs used by MarketScanner, as well as any newer behavioral knobs surfaced/planned on the Filters tab (universe/timeframes, confidence threshold, quotes list) so we know exactly where they bind in backend services.

C) Conflict & Overlap Analysis

Conflicts Matrix → audit/conflicts_matrix.csv
Rows = parameters; Columns = clash_with, clash_type (duplicate/contradict), effective_priority (today), recommended_resolution.
Examples: duplicated risk caps across guardrails vs trading_settings; volume thresholds specified in both “filters” and “strategy pre-checks”; cooldown in two places. Mark each with a Phase 2 action: merge → guardrails, merge → filters, deprecate, or rename + normalize (percent-based).

D) Coherency Baseline & SoT (Source-of-Truth)

Effective-Value Rules — draft for Phase 2
In audit/Phase1_recommendations.md, draft coherency constraints you’ll enforce later, e.g.:

risk_per_trade_pct ≤ daily_loss_kill_switch_pct / 10

max_open_positions * risk_per_trade_pct ≤ portfolio_exposure_cap_pct

symbol_cooldown_minutes ≥ strategy_min_cooldown_minutes (if both exist)

All risk magnitudes are percent-based and portfolio-relative (no absolute $)

Source-of-Truth callouts
