Directive: Phase 8.8.3-AJ9 — Intelligent Sizing Buffer & RTB Metrics/Display Corrections

Context & Current State

Paper mode portfolio sizing now uses storage.getPortfolioState({ mode: 'paper' }).balance as the single source of truth.

Position sizing helper (paper-position-sizing.ts) calculates quantity and estimatedValue per RTB signal and uses guardrails v2 values (portfolioRiskPerTradePct, maxPositionPercentPct).

LPCP (Low-Priced Coin Protection) is dormant by design (always returns ok: true) and must stay that way in this phase.

RTB execution metrics:

Use session-based 24h metrics that reset when the engine stops (AJ8).

Show overall attempts / opened / blocked, a “Blocked Breakdown” by reason, and strategy “chips” at the bottom.

The RTB metrics panel still has several issues:

Blocked count sometimes doesn’t match the per-reason totals.

Blocked breakdown shows only 4–5 reasons even though there are 13 enum reasons.

Strategy chips only show 5 strategies, not all 9.

There is no “Opened by Strategy” table.

We want AJ9 to be targeted and minimal: fix sizing so trades can actually open, and complete the RTB metrics display, without destabilizing other systems.

2. AJ9 Goals

Intelligent Sizing Buffer

Add a small, configurable safety buffer so quantities are sized below the max position cap, giving “wiggle room” for price changes and execution slippage.

Result: trades that meet guardrails should actually open, rather than being blocked 100% by MAX_POSITION.

RTB Metrics Accuracy & Completeness

Ensure RTB metrics (last 24h, session-gated) are internally consistent:

Blocked total equals the sum of all per-reason counts for the current session.

Strategy counts (blocked and opened breakdowns) align with summary totals.

Make the UI show all data, even when some categories/strategies are zero.

RTB UI Completeness

All 13 block reasons (even if zero).

Add a new “Opened Trades by Strategy (Last 24h)” table.

3. AJ9 Tasks
AJ9.1 — Add Sizing Buffer Below Max Position Cap

Objective:
Prevent legitimate trades from being blocked by MAX_POSITION due to tiny price changes between RTB sizing and execution.

Implementation details:

In paper-position-sizing.ts:

Introduce a constant buffer factor for the max position, e.g.:

const MAX_POSITION_BUFFER_FACTOR = 0.97; // 3% below max cap


When computing the notional cap from guardrails, use:

const maxNotional = portfolioValue * (maxPositionPercentPct / 100);
const bufferedMaxNotional = maxNotional * MAX_POSITION_BUFFER_FACTOR;


Use bufferedMaxNotional when deriving maxQty:

const maxQty = bufferedMaxNotional / entryPrice;


Keep the existing risk-based sizing path, but ensure the final chosen quantity is still:

quantity = Math.min(riskQty, maxQtyWithBuffer);


Do not change the guardrails v2 structure or add new DB fields; the buffer can be a constant in code for now, clearly documented so we can make it configurable in a future phase.

In executeSimulatedTrade (paper execution):

Continue to use the pre-sized quantity stored on the trading signal (do not recalc differently).

Ensure the notional used for MAX_POSITION checks at execution time is:

executionNotional = currentPrice * quantity;


MAX_POSITION guardrail should still compare against the full max position cap from guardrails (not the buffered value) so the buffer provides real slack.

Logging & diagnostics:

If you log any diagnostic for AJ9, keep it temporary and remove it in this phase once validated.

Success criteria:

With:

Portfolio ≈ $800–900 in paper mode

portfolioRiskPerTradePct ≈ 2–3%

maxPositionPercentPct ≈ 10–20%

At least some RTB signals should successfully open trades, not be 100% blocked by MAX_POSITION.

AJ9.2 — Fix RTB Blocked Totals vs Per-Reason Counts

Problem:
We have observed cases where:

Blocked (summary row) < Max Position count in the breakdown.

This should never happen for the same session.

Required behavior:

For the current engine session (Last 24h):

Blocked (summary) must equal the sum of all 13 block reason counts.

Any difference due to query limits or out-of-sync filters must be eliminated.

Implementation:

In the RTB metrics backend:

Reuse the same underlying query / filter for:

Summary Blocked total.

Per-reason breakdown.

Ensure both:

Use the same sessionStart and isSessionActive gating.

Apply the same time window and mode filters.

Use the same dataset (no extra filters on one side).

Confirm that no client-side filtering or partial result limiting is causing mismatches.

If you must introduce a separate internal helper to compute “blocked totals,” document it in the AJ9 audit and ensure both summary and breakdown functions call it.

AJ9.3 — Always Show All 13 Block Reasons

Objective:
The RTB “Blocked Breakdown” table must always show all 13 executionBlockReasonEnum values, even when the count is 0.

Implementation:

Backend:

Ensure the RTB blocked summary endpoint always returns an entry for each enum value with a count (default 0 if none recorded this session).

Frontend (execution-metrics.tsx):

Render all 13 reasons as table rows:

If count is 0, still show the row with 0.

Avoid any filtering logic that hides zero rows.

Verify that adding more reasons in the future (enum expansion) remains safe (e.g., using a mapped list from backend rather than hardcoded subset).

AJ9.4 — Always Show All 9 Strategies in RTB Strategy Chips

Objective:
The RTB metrics panel currently shows only 5 strategy chips; it must always show all 9 strategies, even when a strategy has 0 attempts/blocks/opens for the session.

Implementation:

Backend:

Ensure strategy breakdown data includes all 9 strategies with counts (default 0 where applicable).

Frontend:

Render all 9 strategy chips in the RTB Execution Metrics panel:

Show the count for each chip.

Use consistent ordering (e.g., same as strategy engine or shared enum).

Do not hide chips with 0 counts.

Ensure that the sum of counts across all strategy chips:

For “blocked by strategy” view → matches blocked total.

For “opened by strategy” view (see AJ9.5) → matches opened total.

AJ9.5 — Add “Opened Trades by Strategy (Last 24h)” Table

Objective:
We need a dedicated table showing which strategies actually open trades.

New section in RTB Execution Metrics, below “Blocked Breakdown”:

Title: “Opened by Strategy (Last 24h)”

Columns:

Strategy

Opened (count)

Optional (if cheap): Total Notional ($) per strategy (but not required in AJ9).

Implementation:

openedCount

Use the same sessionStart and last-24h filters as the main summary.

Frontend:

Render the “Opened by Strategy” table even when all counts are zero.

Ensure the sum of openedCount equals the Opened value from the summary table.
