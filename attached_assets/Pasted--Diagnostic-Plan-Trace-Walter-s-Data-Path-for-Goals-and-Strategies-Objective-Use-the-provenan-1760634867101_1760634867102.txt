🧭 Diagnostic Plan: Trace Walter’s Data Path for Goals and Strategies
🎯 Objective

Use the provenance chain to identify what source Walter is actually pulling from when asked about:

Enabled strategies (paper vs live)

Goal settings (paper vs live)

Balances (paper vs live)

This will tell us if:

He’s getting the data from the correct BoB module,

The Cortex cache (possibly stale), or

A legacy or semantic memory snapshot (incorrect source).

🔧 Step-by-Step Instructions for Replit
Step 1 — Enable Provenance Debug Mode

Ask Replit to temporarily enable verbose provenance logging.

“Enable full provenance debugging mode for Walter’s data lineage, including database, BoB, Cortex, and Walter memory layers.”

This ensures that each data fetch call logs a traceId and its source.

Expected console output when active:

[Provenance] traceId=TRC-83GH2 Portfolio source=portfolio_state (globalContextId='default', mode='live')
[Provenance] traceId=TRC-83GH2 Goals source=user_goals_live
[Provenance] traceId=TRC-83GH2 Strategies source=legacy_cache_snapshot (!)


That “(!)” is what we’re looking for — a red flag that data came from somewhere unexpected.

Step 2 — Generate a Trace by Asking Walter

Once provenance debugging is on, go back to Walter and issue the same query you showed above:

“Please refresh and provide the list of enabled strategies for paper and live mode and the balances for paper and live mode. Also, provide the list of settings for the goals tab in the goals engine for paper and live mode.”

This will cause Walter to trigger a fresh fetch cycle with traceIds.

Step 3 — Query the Provenance Tables

Ask Replit to provide all recent trace records for that transaction:

“Show me the last 10 entries from data_lineage and bob_trace_log tables, filtered by the most recent traceId generated by Walter’s response.”

That command should return rows like:

From data_lineage:

traceId	source_service	target_service	source_table	mode	timestamp
TRC-83GH2	database	BoB-Config	user_goals_live	paper	...
TRC-83GH2	database	BoB-Strategy	strategy_settings	live	...
TRC-83GH2	cortex	Walter	goals_snapshot_2024	—	... ❌

From bob_trace_log:

traceId	bob_module	operation	source_table	execution_time_ms
TRC-83GH2	ConfigBob	fetchGoals	user_goals_live	47
TRC-83GH2	StrategyBob	fetchStrategies	strategy_settings	83
TRC-83GH2	—	—	legacy_snapshot	— ❌

These tables will tell us exactly which table or cache each piece of information came from.

Step 4 — Confirm Cortex Cache Status

Ask Replit:

“Show me the current entries in the cortex_cache for keys related to ‘goals’, ‘strategies’, and ‘portfolio_state’, including their timestamps and source tags.”

You’re looking for mismatched timestamps — e.g., paper mode entries recent, live mode entries 48 hours old.
If you see:

goals_live → 2025-10-14 18:10:00 (stale)


then you know Walter’s still reading from the Cortex layer’s old cache, even though provenance is correct underneath.

Step 5 — Check Walter’s Semantic Memory

Walter himself has a lightweight memory system (walter_memory table).
Ask Replit:

“Search the walter_memory table for any entries where memory_key LIKE '%goal%' OR '%strategy%' OR '%balance%' and return memory_source and last_updated.”

If you find something like:

memory_key=goals_snapshot, source=legacy_context, last_updated=2025-09-29


then the issue is not BoB or Cortex — it’s that Walter’s own memory is overwriting fresh data when forming responses.

Step 6 — Compare the Provenance Chain

Replit can now cross-reference these results using the traceId correlation.
Ask:

“Correlate traceId TRC-[latest] across data_lineage, bob_trace_log, and cortex_cache to identify any mismatched or missing lineage entries.”

If there’s a break (for example, missing “BoB → Cortex” record for strategies), then that’s the leak — the data pipeline isn’t delivering the new info to Walter.

Step 7 — Request the Provenance Summary Report

Replit can generate the built-in governance/provenance continuity report:

“Run the daily provenance governance report and include lineage continuity for goals, strategies, and portfolio_state by mode.”

That report should show something like:

Data Source	Mode	Lineage Continuity	Cache Freshness	Last Update
Goals	Paper	100%	Fresh	✅
Goals	Live	100%	Fresh	✅
Strategies	Paper	100%	Fresh	✅
Strategies	Live	83% (Cache Fallback)	❌	
Portfolio	All	100%	Fresh	✅

That “Cache Fallback” line will confirm whether the live strategies are being pulled from old memory.

🧩 What This Will Tell Us

From this full trace, you’ll know whether:

Walter’s data issue is in the fetch layer (BoB),

in the caching layer (Cortex), or

in the conversational layer (Walter memory).

If provenance shows correct table references but Walter’s output is still wrong, we’ll know his response generation is reusing cached semantic blocks instead of the live context — which is likely, based on your observations.

🔁 After the Diagnosis

Once the trace confirms where the data is breaking:

If it’s BoB → Replit needs to rebind StrategyBob’s fetch to the global context.

If it’s Cortex cache → Purge stale cache keys (goals_live, strategies_live).

If it’s Walter memory → Clear memory entries tied to “legacy_context” and rebuild context from Cortex.
