Goal: Confirm that for the currently active paper positions:

Cache updates broadcast to frontend

Use the existing diagnostics:

Subscription coverage (I7-WS-A + I7-WS-F):

curl -s "http://localhost:5000/api/diagnostics/i7-ws/subscription-map?mode=paper" \
  -H "Authorization: Bearer $TOKEN" \
  | tee docs/diagnostics/I7-VER/subscription_map.json | jq '{summary, gaps}'

curl -s "http://localhost:5000/api/diagnostics/i7-ws-f/coverage" \
  -H "Authorization: Bearer $TOKEN" \
  | tee docs/diagnostics/I7-VER/wsf_coverage.json | jq '{summary, health}'


Confirm all active trade symbols are subscribed (not never_requested or stuck pending).

Note any exceptions in the I7-VER report.

Tick and pipeline stages (I7-WS-C):
After ~2–3 minutes of runtime:

curl -s "http://localhost:5000/api/diagnostics/i7-ws-c/trace-history" \
  -H "Authorization: Bearer $TOKEN" \
  > docs/diagnostics/I7-VER/trace_history.json

cat docs/diagnostics/I7-VER/trace_history.json \
  | jq '{ totalTraces: .totalTraces,
          stageCounts: [.traces[].stages[].stage]
            | group_by(.) | map({stage: .[0], count: length}) | sort_by(.stage) }'


Verify that for at least several active symbols, you see stages 1,2,3,4 in traces:

1 = INCOMING_WS_TICK

2 = symbol mapped

3 = cache updated

4 = broadcast

If some symbols only show engine stages (7/8) but no WS stages (1–4), note that in the report.

Delivery parity check (I7-WS-D logs):

In /tmp/logs/Start_application_*.log, confirm:

[I7-WS-D][CACHE_WRITE] and [I7-WS-D][BROADCAST_SEND] are present.

For WS-driven symbols, counts should be reasonably close (difference explained by 150ms throttle and REST updates).

Capture a small excerpt of these logs into docs/diagnostics/I7-VER/i7-ws-d_sample.txt.

I7-VER-5 – Verify Trade Closures (Stop/Target Hits)

This is the core business outcome check.

Let the paper session run long enough for exits to happen (or until at least a few trades close). During this period, every ~5 minutes, capture:

# Active trades snapshot
curl -s "http://localhost:5000/api/paper-sim/active-trades" \
  -H "Authorization: Bearer $TOKEN" \
  > docs/diagnostics/I7-VER/active_trades_t${TS}.json

# Trade history snapshot
curl -s "http://localhost:5000/api/paper-sim/trade-history?limit=100" \
  -H "Authorization: Bearer $TOKEN" \
  > docs/diagnostics/I7-VER/trade_history_t${TS}.json


where TS can be start, mid, end for simplicity.

In the Trade History API responses, check for trades with:

status = closed (or equivalent)

exitReason / close_reason indicating TP hit or SL hit (names depend on your schema – inspect the existing data).

Cross-check for at least 1–3 example trades:

Confirm they existed earlier in active_trades_* and later appear closed in trade_history_*.

Note symbol, side, entry price, TP/SL, and close price if available.

In the frontend Trade History tab, confirm:

You see closed trades accumulating.

They correspond to what you see in the API data.

If no trades close at all during a reasonable test run, note that clearly in the report and, if possible, inspect engine logs for [EXIT_EVAL] or equivalent exit evaluation logs to make sure the engine is trying to close as prices approach TP/SL.
