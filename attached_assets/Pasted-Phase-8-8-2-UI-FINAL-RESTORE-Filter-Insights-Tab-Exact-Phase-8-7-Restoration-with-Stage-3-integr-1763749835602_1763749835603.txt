2. Section-by-Section Specification
2.1 Section 1 – Scan & Filter Overview

This section shows a snapshot for the current / last FX5 scan cycle.

2.1.1 Layout

Use the same layout as the 8.7 screenshots:

Card title: “Scan & Filter Overview”

Within the card: 3 stacked sub-blocks

Kraken Universe

Cycle Info

Last Scan Result

Each sub-block is a two-column row: label on left, metrics on right.

2.1.2 Data Fields & Mapping

A. Kraken Universe

Label: “Kraken Universe”

Sub-label: “Total Kraken Trading Pairs:”

Value:

Field: krakenUniverseSize

Source: same endpoint / contract used in Phase 8.7 (you previously implemented this cache in market-scanner and exposed it via /api/market-scanner/scan-summary).

If that field was renamed, re-align so this row shows the total count of all tradable pairs on Kraken, not per-scan evaluatedCount.

B. Cycle Info

Fields (all must be present):

Last Scan Cycle ID:

Example: cycle_paper_u7z0yhW0Bv3

Source: Stage-3 cache cycleId for the current mode (paper / live).

Last Scan Time:

ISO timestamp converted to user’s local timezone, matching previous formatting.

Source: Stage-3 cache lastScanEndTimestamp for the current mode.

Next Scan In:

Countdown in seconds to the next FX5 scan.

Based on fixed 30-second schedule and lastScanEndTimestamp.

If scanner or engine is stopped, show "—" or a gray “Not scheduled” label.

Cycles per Hour:

Display Stage-3’s computed value.

Expected ~0.3–0.9 depending on rotation & engine state.

Source: Stage-3 cache cyclesPerHour (for the mode).

Scan Frequency:

Static text: “every 30 seconds”

This is purely informational and should not be computed from the backend.

C. Last Scan Result

Rows:

Evaluated This Scan:

The number of pairs evaluated in the last FX5 scan for this mode.

Source: Stage-3 evaluatedCount for last cycle.

Eligible This Scan:

Number of pairs that passed all FX5 filters in the last scan.

Source: Stage-3 eligibleCount.

Display format:

Main number (e.g., 48)

Small percentage next to it: (xx.x%) where:

eligiblePct = eligibleCount / evaluatedCount * 100 rounded to 1 decimal.

Ineligible This Scan:

Number of pairs that failed at least one filter in the last scan.

ineligibleCount = evaluatedCount - eligibleCount.

Display:

Main number

Small percentage: (xx.x%) where:

ineligiblePct = ineligibleCount / evaluatedCount * 100.

Percentages must sum to ~100% (rounding tolerance ±0.1%).

2.1.3 Behavior – ACTIVE vs STOPPED

When Paper mode is ACTIVE (trading engine running):

All fields above must be live and updated every 30 seconds via Stage-3 scan events.

When Paper mode is STOPPED (passive learning only):

Behavior must mimic Phase 8.7:

Kraken Universe: still shown (it’s static).

Cycle Info:

Show Next Scan In and Scan Frequency as before (we still scan every 30s).

Last Scan Cycle ID and Last Scan Time may still show the last cycle, but it’s OK.

Last Scan Result:

Counts must remain very small or zero, not accumulate massive values.

You can leave the per-scan numbers as they are (0–3 is fine), but don’t allow them to be misinterpreted as “trading activity.”

Key rule: No accumulating 24h totals, no large numbers from passive scans in this section.

2.2.2 Data Source & Aggregation

We are OK using the /api/paper-sim/diagnostics/scan-24h endpoint you just built, but you must harden it as follows:

No monkey-patching contextBridge.

Replace the “patch broadcast to intercept events” approach with a explicit subscription:

Stage-3 emitter should explicitly call a Scan24hAggregator.recordCycle(mode, scanSummary) or similar when a scan is completed.

This can be wired where you already emit scanner:breakdown:<mode>.

Aggregator semantics:

For each FX5 scan cycle (per mode):

evaluatedCount – total evaluated in that cycle

eligibleCount – total passed all filters

Aggregator maintains a rolling window of last 24 hours only for cycles while trading engine is ACTIVE (see gating below).

Total Evaluated (24h)

sum(evaluatedCount) for all cycles in last 24h (ACTIVE only).

Total Survived Filters (24h)

sum(eligibleCount) for all cycles in last 24h (ACTIVE only).

Unique Evaluated (24h)

Count of distinct symbols seen at least once in any cycle in the last 24 hours.

Unique Survived Filters (24h)

Distinct symbols that passed all filters at least once in last 24 hours.

Cycles (24h)

Count of scan cycles seen in last 24 hours.

Engine-state gating (critical):

Aggregator must only record cycles when paper mode is ACTIVE.

Obtain state from existing trading engine state (you already emit trading_state_changed).

When state is STOPPED for a mode, aggregator must not record new cycles.

On transition from ACTIVE → STOPPED for a mode:

Either:

Reset the window (clear stored cycles), or

Mark a boundary so the next ACTIVE session starts from a clean 24h view.

Result: When trading is STOPPED (passive learning only), the 24h metrics will be empty or near zero, as in Phase 8.7.

Endpoint contract:

GET /api/paper-sim/diagnostics/scan-24h?mode=paper

Respond with JSON:

{
  mode: "paper" | "live",
  windowStart: string, // ISO timestamp, 24h ago
  windowEnd: string,   // ISO timestamp, now
  totalCycles: number,
  totalEvaluated: number,
  totalSurvived: number,
  uniqueEvaluated: number,
  uniqueSurvived: number
}


Same structure for mode=live if used.

2.2.3 UI Behavior

ACTIVE (paper):

All metrics above populated and updating as scans occur.

STOPPED (paper):

Either:

“24h metrics will start accumulating when paper trading is ACTIVE.”

In any case, do not display large carried-over values from previous passive runs.

2.4.4 Data Aggregation & Truth Constraint

Back-end rule (already implemented in Stage-3 – make sure UI uses it correctly):

For each 24-hour window (ACTIVE cycles only):

Let evaluated24h be the total evaluated across all cycles.

For each failure category, have a count (e.g. failed_min_volume, failed_spread, …).

already_active24h – pairs rejected because they are already active.

passed_all_filters24h – total survivors.

The truth constraint must hold:

evaluated24h
  =
sum(all failure category counts across the 7 failure categories)
  + passed_all_filters24h


Notes:

“Passed All Filters” is not a failure category; it’s the success bucket.

“Already Active” is considered a “failure bucket” for the purpose of accounting (i.e., these are pairs not allowed into the new active pool).

The frontend:

Must display:

Total Evaluated (24h): evaluated24h

Total Survived Filters (24h): passed_all_filters24h

Per-category counts for the 7 filter buckets plus “Passed All Filters.”

MUST NOT show any counts that break the truth constraint; if the backend reports mismatches, show a small “data out of sync” warning rather than rendering wrong numbers.

2.4.5 Behavior – ACTIVE vs STOPPED

ACTIVE: show 24h breakdown normally (aggregating only ACTIVE cycles).

STOPPED: may show old values from the last ACTIVE run, or show an empty state.

It must not keep growing due to passive scans.
