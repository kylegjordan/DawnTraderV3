⚠️ Root Cause Identified

This is not a traditional blocking issue inside the service code.
It’s a concurrency architecture problem:

Force-stop correctly ends the session but triggers UI auto-restart via WebSocket recovery.

The UI restart request sets a new operation lock.

The developer test request arrives within that 5–10 s window.

Both requests contend for globalPaperSimOperationLock → dead wait → timeout.

The current safeguards (busy-flag and stale-lock auto-clear) help with recovery but cannot prevent this collision.

🧩 Architectural Recommendations

To permanently resolve:

Introduce a job queue / sequential task runner for start/stop operations.

Implement request deduplication (keyed by user + mode + session ID).

Separate UI-triggered vs API-triggered start events to prevent overlap.

Optionally, move operation-lock ownership from global to per-user context.
