1. Desired Behavior – Passive Learning (Truth Spec)

This is what must be true again, end-to-end:

No manual toggle.
Passive learning is derived, not a third mode and not manually set anywhere.

Derivation rule (per TradingStateSync truth):

const tradingActive = paperTradingActive || liveTradingActive;
const isPassiveLearning = !tradingActive;


When either paper or live trading is running → tradingActive = true → isPassiveLearning = false.

When neither is running → tradingActive = false → isPassiveLearning = true.

Backend truth & persistence:

This derived isPassiveLearning must be:

Stored in the system state (e.g. TradingStateSync / state cache).

Exposed via the status API (e.g. /api/system/state or equivalent).

Persisted in SystemConfig.passiveLearning (see REB 2.6 dual-gate spec) so services that gate behavior can read a single authoritative flag.

Broadcast & UI behavior (truth that used to work):

All trading_state_changed / trading_state_ack broadcasts include passiveLearning and it matches the derived flag above.

In the client (TradingModeContext + Trading top bar + Filter Insights banner), systemFlags.passiveLearning (or equivalent) updates correctly:

Engine OFF / not trading → Banner/indicator shows “Passive Learning active”.

Engine ON (paper or live) → Banner/indicator is hidden.

Side-effects of passive learning (from REB 2.6 checklist):

When SystemConfig.passiveLearning = true:

Metrics & pools are gated (no 24h metrics writes, no activeFilteredPool writes).

When SystemConfig.passiveLearning = false and engine is ACTIVE:

Normal metrics recording and pool population resume.

3. Task B – Active Filtered Pool Behavior

Once passive learning truth is restored, wire the Active Filtered Pool to it correctly.

B.1. Expected behavior (truth spec)

Passive learning (no trading):

isEngineActive=false for the relevant mode.

passiveLearning=true.

Behavior:

FX5 scanner may still evaluate for observation, but:

No writes to activeFilteredPool.

Pool is cleared when engine stops.

Filter Insights “Active Filtered Pool” table should be empty.

Active trading (paper or live):

isEngineActive=true for that mode.

passiveLearning=false.

Behavior:

Each FX5 scan can add candidates (survivors) into the mode-specific active pool.

Pool obeys TTL (5-minute expiry) and deduplication.

The Active Filtered Pool (Deduped, Non-Expired) table on Filter Insights should show symbols when there are eligible pairs.

Transitions:

When trading transitions ACTIVE → STOPPED:

enforcePassiveModeIfStopped(mode, isEngineRunning) (existing method) must be called so the pool is cleared and the UI table falls back to “No Eligible Pairs”.

When trading transitions STOPPED → ACTIVE:

Pool starts empty; new scans repopulate it normally.

B.2. Wiring the gates (backend)

Use the dual-gate pattern already defined in REB 2.6 – but apply it to the current FX5 / active pool path, not the removed legacy aggregator:

In the FX5 scanner / pool update path (wherever survivors are written into activeFilteredPool):

Ensure you have access to both:

const config = SystemConfigService.getConfig();

const isEngineActive = /* per-mode engine state */;

Apply the dual gate from REB 2.6:

// Guard 1: persistent passive learning flag
if (config.passiveLearning) {
  console.log('[8.6.9][PassivePool] Passive learning enabled - Active Pool not populated');
  return []; // or skip pool update
}

// Guard 2: engine state

  // Engine not running → no pool updates
  return [];
}

// Only here do we update activeFilteredPool

Don’t re-introduce the legacy scan-24h-aggregator. This logic belongs in the FX5 scanner + activeFilteredPool services only.

Hook up enforcePassiveModeIfStopped

In the place where engine state transitions are handled (e.g. when stopPaperSimulation / stopLiveTrading succeed and the engine is now STOPPED):

Call:

activeFilterPool.enforcePassiveModeIfStopped('paper' | 'live', isEngineRunning);


as per REB2.3C current implementation audit.

Also ensure this is run at startup for safety if engine comes up as STOPPED.
