F-A-01: Drift Data Missing in Mapping Drift Tab
Root Cause: The computeMappingDrift() function in telemetry-aggregator.ts (lines 405-530) calculates drift based on regime distribution but does NOT use the mapping-drift-calculator.ts functions which compute per-regime DriftScore using volZ/trendZ.

Affected Files:

server/routes.ts (lines 2200-2212) — Calls telemetryService.computeMappingDrift()
server/services/telemetry-aggregator.ts (lines 405-530) — Current implementation
server/core/analytics/mapping-drift-calculator.ts — Not wired to API
Issue: The API endpoint returns regime distribution counts, NOT actual DriftScore computations from the calculator. The calculator functions (computeDriftScore, computeBatchDriftScores) exist but are never called.

Proposed Solutions:

Short-term: Wire mapping-drift-calculator.ts into the API route, passing volZ/trendZ arrays from telemetry
Long-term: Create a dedicated DriftAnalysisService that aggregates Z-scores per regime and computes DriftScore
Risk: Medium — UI shows partial data, misleading users about drift status
Complexity: Medium

F-A-03: Regime Distribution Graph Shows No Data
Root Cause: The normalizedDistribution field IS populated by computeMappingDrift() but requires MIN_SAMPLES = 30 pairs with valid pairRegime data. The UI displays normalizedDistribution but may show empty if:

VTS hasn't run enough cycles
pairTelemetry map is empty at startup
Affected Files:

server/services/telemetry-aggregator.ts (lines 436-442, 461-478)
client/src/pages/analytics.tsx (lines 859-875)
Issue: The graph renders Object.entries(driftData?.normalizedDistribution || {}) — if telemetry is sparse or VTS just started, this is empty.

Proposed Solutions:

Short-term: Add logging to /api/system/mapping-drift to expose pairTelemetry.size count
Long-term: Persist telemetry across restarts; seed with historical data
Risk: Low — Data populates after VTS runs ~30+ pairs
Complexity: Low

F-A-04: DriftScore Calculated Per-Regime, Not Per Regime-Strategy Pair
Root Cause: Confirmed — computeMappingDrift() computes a single aggregate driftScore using formula:

const driftScore = (extraEmpirical.length * 0.5) + (missingCanonical.length * 0.1);
This is a coverage-based score, NOT the weighted Euclidean DriftScore formula from mapping-drift-calculator.ts.

Affected Files:

server/services/telemetry-aggregator.ts (line 496) — Simple formula
server/core/analytics/mapping-drift-calculator.ts — Per-regime DriftScore (unused)
Issue: The calculator's computeDriftScore(actualVolZ[], actualTrendZ[], regime) function requires Z-score arrays per regime, but telemetry doesn't store volZHistory or trendZHistory arrays — only pairRegime strings.

Proposed Solutions:

Short-term: Extend PairTelemetry interface to store rolling volZ[] and trendZ[] arrays per pair
Long-term: Create per-regime-strategy aggregation buckets with Z-score history
Risk: High — Current DriftScore doesn't reflect mathematical drift
Complexity: High

F-A-05: Telemetry Missing volZ/trendZ Keys

interface PairTelemetry {

  // volZ, trendZ NOT PRESENT

VTS calculates Z-scores in vts-runner.ts (line 300) but only logs them — doesn't persist to telemetry:

console.log(`[11.5][ZScore] ${symbol}: zScores={adx=${...}, vol=${zScoreResult.zScores.volZ...}}`);
Affected Files:

server/services/telemetry-aggregator.ts — Missing Z-score storage
server/services/vts-runner.ts (line 300) — Logs but doesn't persist
Proposed Solutions:

Short-term: Add volZ?: number and trendZ?: number to PairTelemetry interface; populate from VTS
Long-term: Create ZScoreHistoryBuffer per symbol for rolling 50-sample window
Risk: High — Core data required for DriftScore formula is missing
Complexity: Medium
