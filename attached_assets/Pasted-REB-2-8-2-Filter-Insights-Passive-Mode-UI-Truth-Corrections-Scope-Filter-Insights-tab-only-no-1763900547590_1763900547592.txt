1. Passive Learning Mode & Data Behavior (Engine STOPPED)
1.1. Target Behavior (Engine STOPPED, Passive Learning ON)

When Trading Engine = STOPPED (Paper mode) and the app is in Passive Learning:

Allowed to tick:

Next Scan In: live 30s countdown continues as normal.

Last Scan Result: may occasionally show small “mini-ticks” (e.g., 1–2 evaluated / eligible) reflecting background FX5 scans in passive learning mode. This is acceptable.

Should not carry stale data:

24h Filter Activity (all 5 metrics) must not show old values from the last ACTIVE session if we’ve turned trading off.

Filter Breakdown (Last 24h) counts must not show old values; if nothing has been trading in the last 24h, these must be zero (or treated as “no data yet”).

Kraken Universe:

May continue to show the current universe size (e.g., 1,386 pairs); this value updates infrequently and is fine to keep non-zero while stopped.

1.2. Required Checks & Fixes

Trace data sources for these fields in client/src/components/trading/filter-insights.tsx:

Last Scan Result (Evaluated / Eligible / Ineligible / Eligible %)

24h Filter Activity metrics

Filter Breakdown counts

Verify that all of them are populated from the FX5 REST endpoints specified in the authoritative mapping (11/20 directive), not from:

WebSocket-only payload state

Hardcoded / mock values

Static snapshots from a previous ACTIVE session

Verify passive-mode correctness:

With engine STOPPED for a fresh 24h period (i.e., after a clean stop & some time elapsed), the following should be true:

24h Total Pairs Evaluated = 0

24h Total Pairs Survived = 0

24h Unique Pairs Evaluated = 0

24h Unique Pairs Survived = 0

Total FX5 Cycles (24h) = 0 (or “No 24h data yet” state)

All Filter Breakdown categories show 0 (or “No 24h data yet” at top) — no stale counts.

The only exceptions are:

Kraken Universe (non-zero, as above)

Occasional small Last Scan Result values from FX5 passive scans

“Next Scan In” countdown

No frozen session snapshots:

Ensure that when we transition ACTIVE → STOPPED, the UI does not simply continue showing the last ACTIVE 24h metrics and breakdown counts indefinitely.

If the REST endpoints currently return “last 24h including past ACTIVE cycles,” you must either:

Use mode / active-flag aware REST fields that only aggregate ACTIVE cycles, or

Apply a client-side guard such that, once the engine is STOPPED and there are no new active cycles, the UI shows zeros / “No 24h data yet” rather than stale non-zero values.

Mini-ticks explicitly allowed:

Do not suppress the small evaluated/eligible counts in Last Scan Result that occasionally appear in passive learning.

The user expects these “mini-ticks” as a sign that the scanner is still alive; they just don’t want stale 24h or breakdown metrics.

Use the 11/18 truth top-section screenshots as your visual source of truth, plus the adjustments below.

2.1. Card / Border Structure

Current 2.8.1 implementation uses separate cards/boxes for each of the four sections.

Change this to:

One single parent card enclosing all four sections:

Kraken Universe

Cycle Info

Last Scan Result

24h Filter Activity

Remove the individual border boxes around each section.

Instead, use horizontal divider lines between the sections, matching the 11/18 screenshots:

Divider below Kraken Universe section

Divider below Cycle Info section

Divider below Last Scan Result section

No divider below 24h Filter Activity (it’s the last section in the card).

2.2. Section Headers & Font Sizes

Across all four sections:

Section titles (e.g., “Kraken Universe”, “Cycle Info”) should:

Match the font size and weight in the 11/18 truth screenshots.

Numeric values:

Slightly larger and bolder than their label text.

Do not use the oversized font currently applied to the Kraken Universe count.

Concretely:

Kraken Universe (1,386) should be the same number font size/style as the other metrics, not dramatically larger.

2.3. Kraken Universe Section (Section 1)

Shows only:

Label: “Total tradable pairs in Kraken universe”

Value: <N> pairs (e.g., 1,386 pairs)

No Evaluated / Eligible / Ineligible metrics in this section (those belong in Last Scan Result).

2.4. Cycle Info Section (Section 2)

Restore all fields that were present in the 11/18 truth state and lay them out in three rows, as in the screenshot.

Fields required:

Row 1:

Last Scan Time: includes date + time, e.g.
11/18/2025, 12:40:13 AM

Next Scan In: live countdown (e.g., 27s)

Row 2:

Cycle ID: shows the current FX5 cycle ID (e.g., cycle_paper_u2Ywh0By3)

Scan Frequency: “Every 30 seconds” (static label text)

Row 3:

Cycles per Hour: numeric value (e.g., 0.4)

Also:

Use the same fonts, spacing, and colors as in the 11/18 screenshot.

Keep the Cycle Info header exactly as in truth; no extra description is necessary.

2.5. Last Scan Result Section (Section 3)

Remove the small sub-header text “Most recent FX5 scan cycle statistics” (not present in truth).

Ensure it shows exactly these four metrics:

Evaluated (This Scan)

Eligible (This Scan)

Ineligible (This Scan)

Eligible %

Layout: match the 11/18 screenshot’s grid (two rows or one row of four, whichever the truth shows — use the truth screenshots you’ll be given).

Eligible % should be calculated exactly as in 2.8.1 (eligible / evaluated × 100), but must always be consistent with the other three metrics.

2.6. 24h Filter Activity Section (Section 4)

Match the truth layout: three stacked rows:

Row 1:

Total Evaluated (24h)

Unique Evaluated (24h)

Row 2:

Total Survived Filters (24h)

Unique Survived Filters (24h)

Total FX5 Cycles (Last 24h) — this always appears last

Important behaviors:

When no valid 24h data exists (e.g., engine STOPPED and no active cycles in last 24h):

Either show all zeros or a clear “No 24h data available yet” message instead of misleading non-zero values.

Use the same typography for labels and numbers as in the truth top-section screenshots.

4. Filter Breakdown (Last 24h) – Behavior & Styling Fixes

Use the truth Filter Breakdown screenshot and the Phase 8.7 filter table below.

4.1. Categories (Final List)

Exactly these 9 visible categories, in a sensible order (truth order is preferred):

Passed All Filters

Min Price

Min Volume

Max Spread

Min Daily Range

Exclude Stablecoins

Valid Quote Currency

Already Active

History

Descriptions should match the Phase 8.7 truth descriptions (which you already wired in during 2.8.1).

4.2. Counts, Not Pass/Fail Pills

Current behavior shows “Pass/Fail” pills on each row. This is incorrect.

Required behavior:

Each category shows:

Label (e.g., “Min Volume”)

Short description (already implemented)

Threshold (already implemented)

Numeric count for the last 24h window (e.g., 180)

Remove any Pass/Fail badge for these categories. The only “summary” concept is the count of pairs that failed that filter in the last 24 hours.

“Passed All Filters”:

Also shows a numeric count — the number of pairs that passed every filter in that last scan cycle / 24h window.

The sum of:

“Passed All Filters” count

All individual failure category counts
≈ Total Evaluated (24h), subject to the same semantics as truth.

4.3. No Greyed-Out Categories

Do not render any of the 9 categories as “greyed out” or visually disabled.

All 9 should appear active and readable, even when their count is 0.

4.4. Passive-Mode Zeroing

When the engine has been STOPPED and there are no qualifying active cycles in the last 24h:

All category counts must be 0, and/or a clear header message (e.g., “No 24h data available yet”) should be shown.

Do not show residual counts from old sessions while engine is stopped.
