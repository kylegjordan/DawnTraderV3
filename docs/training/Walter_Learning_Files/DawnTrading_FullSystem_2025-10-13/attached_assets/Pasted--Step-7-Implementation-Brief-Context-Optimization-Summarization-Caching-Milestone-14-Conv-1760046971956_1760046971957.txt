⚙️ Step 7 Implementation Brief — Context Optimization (Summarization + Caching)

Milestone 14 — Conversation Summarization, Context Retention & Response Caching

🎯 Objective

Optimize how the system (AI + backend) manages conversation memory and repeated data requests to:

Preserve long-term understanding without exceeding token or cost limits.

Make responses faster, cheaper, and more consistent.

Maintain continuity across features like the Goals Engine, AI Transparency Panel, and trading sessions.

This milestone introduces two new subsystems:

Conversation Summarization Engine

Response Caching Layer

🧱 Part A — Conversation Summarization Engine

Goal:
Convert long chat histories into compact summaries once a conversation passes ~20–30 messages.

Functional Flow:

Detect conversation length > threshold.

Compile older messages into a temporary buffer.

Generate a summary record containing:

conversation_id

time window (start + end timestamps)

participant roles (system / user / assistant)

compressed summary text (≤ 200 tokens)

last message id included

Store summary in conversation_summaries table.

Replace original raw messages with the summary when loading conversation context.

Tag summary entries as "system-summary" when feeding back into AI context.

Requirements:

Summaries must retain decisions, action items, and user preferences.

Each new summary appends — never overwrites previous ones.

Apply summaries per conversation_id (scope = one user thread).

Summaries must load automatically when conversation is reopened.

Deliverables:
✅ New database table conversation_summaries with fields as listed.
✅ Summarization trigger running every 5 messages after threshold.
✅ API endpoint GET /api/conversations/:id/summaries (return recent summaries).
✅ UI Verification: Long chats still show smooth continuity with no message loss.
✅ Architect review + approval log.

⚙️ Part B — Response Caching Layer

Goal:
Reduce duplicate API calls and response latency for repeated queries (e.g., symbol analysis, trade lookups).

Functional Flow:

Before making an external AI call (or any heavy computation):

Create a cache key = hash(user_id + endpoint + payload).

Check cache store (Redis preferred; Postgres JSON fallback).

If cache hit → return cached response immediately.

If cache miss → perform request, store response with TTL = 900 seconds (15 min).

Return response + timestamp for transparency.

Requirements:

Store cached responses per user_id + query context.

Purge expired entries hourly.

Exclude caching for dynamic actions (like placing trades).

Add API endpoint GET /api/cache/stats for monitoring (hit/miss ratios).

All cache operations logged to ai_transparency_log (taskName = "cache-layer").

Deliverables:
✅ New cache service module with set/get/clear methods.
✅ Integration into AI response pipeline (pre-call check).
✅ API endpoint for cache stats (hit %, miss %, size).
✅ UI Verification: Response time reduction ≥ 30 %.
✅ Architect review confirmation.

🧠 Developer Notes

Do not alter CLE (CLE orchestrator) timers or scheduler intervals.

Summarization and caching should run in parallel — not depend on each other.

Summaries may use existing OpenAI API for short context compression (< 300 tokens).

All summary and cache operations must be recorded in ai_transparency_log.

Include basic error handling: if summary fails, keep raw messages untouched.
