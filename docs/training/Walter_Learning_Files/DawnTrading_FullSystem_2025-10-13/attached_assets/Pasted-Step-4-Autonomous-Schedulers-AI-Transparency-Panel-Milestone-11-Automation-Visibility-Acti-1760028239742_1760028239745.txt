Step 4 — Autonomous Schedulers + AI Transparency Panel

(Milestone 11 — Automation & Visibility Activation)


---

🎯 Objective

Introduce two major capabilities:

1. Autonomous Schedulers — background services that automatically run periodic data scans, recalibrations, and learning routines without user initiation.


2. AI Transparency Panel — a front-end dashboard that shows the system’s automated reasoning, learning adjustments, and recent scheduler actions, allowing the user to audit what the AI is doing and why.



These upgrades transform the app from reactive (user-driven) to proactive (self-optimizing), while keeping complete visibility and manual override for safety.


---

🧱 Part A — Autonomous Schedulers (Backend Logic)

A-1  Scheduler Architecture

Create a centralized Scheduler Registry to manage recurring tasks. Each task should run independently, log its last run time, success status, and next scheduled time.
Use existing Node/Firebase server capabilities (no external cron services).

A-2  Core Tasks to Implement

1. Screener Recalibration Task

Frequency: every 4 hours (default)

Function: analyze recent paper-mode results → adjust filter thresholds in filter_calibration_log.

Inputs: latest trade outcomes, system alerts, AI lessons.

Output: updated calibration entry + log in scheduler_activity_log.



2. Market Scan Task

Frequency: every 10 minutes (default; same as scanner interval).

Function: run screening for both Paper and Live modes → store eligible symbols in screening results table.

Must respect mode isolation and headers (x-app-mode).



3. AI Summary Task

Frequency: daily (UTC midnight).

Function: compile system summary for the Daily Brief (Paper + Live combined overview).

Output: stores entry in ai_transparency_log and refreshes Briefings panel.



4. System Health Check Task

Frequency: hourly.

Function: verify data latency, failed API calls, and service uptime → push alerts to system_alerts.




A-3  Scheduler Logging Requirements

Add ai_transparency_log table with these fields:

id

task_name

executed_at (timestamp)

duration (seconds)

result summary (text)

success (boolean)

notes (text)


Each task writes one row per run.

A-4  Manual Control API

Add simple API endpoints:

GET /api/schedulers/status → list all tasks + last run/next run times.

POST /api/schedulers/run → trigger specific task manually (for testing).


No UI needed beyond Transparency Panel yet.


---

🧭 Part B — AI Transparency Panel (Frontend UI)

B-1  Panel Placement & Navigation

Add a new panel in the sidebar named “AI Transparency”, positioned after Systems Monitoring and before Settings.
This panel consolidates scheduler activity, learning events, and AI rationales.

B-2  Panel Tabs

1. Recent Automation Logs (default)
Displays entries from ai_transparency_log:



Timestamp

Task Name

Duration

Success / Failure Indicator

Short Result Summary


2. Learning Adjustments
Shows recent filter calibrations and portfolio adjustments (Paper → Live transfer records).


3. System Health Alerts
Displays records from system_alerts, color-coded by severity.



B-3  Functional Requirements

Auto-refresh every 60 seconds.

Use existing API clients with x-app-mode headers.

Pagination for ≥ 100 entries.

Mode switch retains panel context (so Live/Paper history stays separate).

All cards should include data-testid attributes for testing.

🧩 Part C — Testing & Verification

C-1  Automated and Manual Tests

1. Scheduler Activation Test



Verify all four tasks register and show in /api/schedulers/status.

Manually trigger each task → confirm log entries appear in ai_transparency_log.


2. Transparency Panel Rendering Test



Panel loads in sidebar and renders all tabs.

Each tab shows correct data source and pagination works.

Mode toggle resets panel content appropriately.


3. Error Handling Test



Simulate scheduler failure → entry logged with success = false.

Transparency panel shows red indicator for failed task.


4. Performance Verification



Confirm background tasks run without blocking main API requests.

Check no memory leaks or restarts in Replit logs over > 2 hours.
