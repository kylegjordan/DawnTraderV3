Phase 1 — Enforce Authentication on All User Routes (No-Code Instructions)
Objective

Lock down every user-scoped API so it rejects requests without a valid JWT (401), accepts requests with a valid JWT (200), and never accepts the old user-id header.

Scope (Protect these route families)

/api/strategies/*

/api/goals/*

/api/trading/* and /api/paper/trading/*

/api/portfolio/*

/api/trades/* and /api/paper/trades/*

/api/watchlist/*

/api/reports/* (incl. daily briefs)

/api/ai/* (chat, opportunities, analysis tied to a user)

/api/settings/*

/api/system/* endpoints that expose user data (leave purely generic health public)

Public routes only:

/api/health

/api/auth/login

/api/auth/refresh

/api/auth/register (if kept; for single user you can disable or guard)

Tasks
1) Confirm middleware is ready

Verify the JWT auth middleware (named authenticateToken) exists and:

Reads Authorization: Bearer <token> header

Verifies JWT with JWT_SECRET

Attaches { id, username } as req.user

Returns 401 for missing/invalid tokens

Do not access req.user before the middleware runs.

2) Apply middleware to protected routes

For each route family listed in Scope, attach authenticateToken to all HTTP methods (GET/POST/PUT/DELETE) in that family.

Ensure nested “paper” versions are also protected (e.g., /api/paper/trades/*, /api/paper/trading/*).

3) Remove legacy header usage

Search for any use of req.headers['user-id'] or similar.

Replace usage with the already-attached req.user.id (which the middleware sets).

If any route still references user-id headers, report it and update it.

4) Validate request typing (to prevent 500s)

Make sure route handlers do not access req.user unless the middleware is applied.

Fix any type assumptions that cause 500s when req.user is missing (they should never run without the middleware).

5) Secrets configuration (one-time)

Confirm these Replit Secrets exist and are non-default strong values:

JWT_SECRET

JWT_REFRESH_SECRET

If missing or default, set new 64+ char random values and restart the app.

6) (If feasible now) Disable open registration for single-user mode

If the app is single-user, ensure /api/auth/register is either disabled or guarded so new accounts can’t be created arbitrarily.

If you keep it, apply a feature flag or require a server-side secret/passcode parameter.

Verification (must pass)
A. Unauthorized requests are rejected

Run these (or equivalent) without Authorization:

GET /api/strategies/settings → 401

GET /api/goals/get → 401

GET /api/trades/active → 401

GET /api/paper/trades/active → 401

GET /api/portfolio/overview → 401

POST /api/trading/start → 401

GET /api/ai/opportunities → 401

B. Public endpoints still work

GET /api/health → 200

POST /api/auth/login (with known user) → 200 returns access + refresh tokens

POST /api/auth/refresh (with valid refresh) → 200 returns new tokens

C. Authorized requests work

After login, call the same endpoints from A with Authorization: Bearer <access_token>:

Each should return 200 and normal data/empty states (not 401/500).

D. Legacy header is ignored

Call a protected endpoint with only user-id header (no JWT) → 401

Confirm no route accepts user-id alone.

E. Logs & diagnostics

No 500s in server logs during the tests.

No TypeScript/LSP errors after changes.

Confirm count of protected endpoints:
“Protected endpoints: X of Y user-scoped routes (100%)”.
