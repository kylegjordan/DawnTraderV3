Verification Query — Existing Authentication & Security Audit
🎯 Objective

Perform a complete inspection of the existing username + password authentication system and API security configuration to verify what’s already protected and identify any remaining vulnerabilities.

The goal is to confirm whether the current implementation already satisfies the requirements for a single-user secure setup (only one authorized user, secure login, private APIs, and protected Kraken keys).

🧱 Verification Tasks
1️⃣ Authentication & Password Security

Check:

Whether passwords are hashed using bcrypt or another strong algorithm before being saved to the database.

That no plaintext passwords exist in any database or logs.

Whether the login endpoint correctly verifies the hashed password.

Confirm that a JWT (JSON Web Token) or equivalent token is issued after successful login.

Deliverable:

List the functions or files where hashing occurs (e.g., bcrypt.hash / bcrypt.compare calls).

Confirm the JWT secret and expiry are properly set and not hard-coded in public code.

2️⃣ API Protection & Access Control

Check:

Whether all backend routes (in server/routes.ts and any other route files) are protected by authentication middleware.

Specifically look for any routes that still use user-id header or do not validate tokens.

Confirm that a valid token is required for sensitive operations such as:

/api/strategies/*

/api/goals/*

/api/system/*

/api/trades/*

Verify that unauthorized requests (missing or invalid token) receive HTTP 401 Unauthorized responses.

Deliverable:

Table or list of all API routes that are authenticated vs. any that are still open.

If any route is exposed without protection, note it clearly.

3️⃣ User Access Limitation (Single-User Mode Readiness)

Check:

Whether the app currently allows new users to register.

Confirm if we can easily restrict registration to one predefined account (e.g., your account only).

Verify whether the system supports manual user creation (so we can disable public sign-ups later).

Deliverable:

Answer: “Yes, registration is open” or “Registration can be restricted.”

Indicate what file or endpoint controls user creation.

4️⃣ Kraken API Key Security

Check:

Where the Kraken API keys are stored. They should exist only in server environment variables (e.g., .env file).

Verify they are never sent to the frontend or exposed in any fetch or network request.

Confirm that only the backend communicates with Kraken via secure signed requests.

Deliverable:

Confirm key storage location (e.g., .env variables).

Report if any instance of KRAKEN_API_KEY or similar is found in frontend code.

Validate that all Kraken requests originate from the server side only.

5️⃣ CORS, Firewall, and Request Validation

Check:

Ensure CORS settings limit API access to trusted origins only (not *).

Confirm rate limiting or brute-force protection is configured on login routes.

Verify that incoming data (usernames, passwords, parameters) are sanitized and validated before database write operations.

Deliverable:

Summary of CORS configuration and allowed origins.

Note any missing rate-limit or validation protections.

How passwords are handled (hashed / verified)

Token validation process

List of authenticated vs. unauthenticated routes

Kraken key security verification

CORS and access-control configuration

Security Rating:
Provide a 1-to-5 safety rating for each of these categories:

Password Handling

Token Authentication

API Protection

Kraken Key Security

Recommendations:

Short list of steps needed (if any) to fully meet Single-User Secure Mode.

🧪 Testing Steps

To verify results:

Attempt to access any /api/strategies/* or /api/goals/* route without a token — should return 401 Unauthorized.

Confirm that valid login returns a token, and protected routes only work when the token is supplied.

Check for any references to Kraken keys in frontend code — there should be none.

Review database users table — confirm password hashes, not plain text.

📦 Final Deliverable

A concise written report that confirms:

What is already secure

What (if anything) remains exposed

Confirmation that the app is ready to proceed to Single-User Secure Mode implementation
