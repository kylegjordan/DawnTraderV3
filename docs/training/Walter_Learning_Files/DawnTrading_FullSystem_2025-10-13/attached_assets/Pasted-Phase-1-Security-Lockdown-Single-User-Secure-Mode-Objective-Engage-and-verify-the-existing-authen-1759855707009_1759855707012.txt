Phase 1 Security Lockdown (Single-User Secure Mode)

Objective
Engage and verify the existing authentication system so every protected API requires a valid JWT, remove any plaintext passwords from the database, and set strong JWT secrets. No functional features should change.

Scope (Phase 1 only)

Apply authentication middleware to all protected routes

Remove plaintext passwords from the DB

Set strong JWT secrets
(Registration disable, CORS, rate-limits come later.)

Step 1 — Enforce Auth on All Protected Routes

Where: server/routes.ts

Use the existing authentication middleware (already defined in the file) and attach it to all protected API route groups.

Protect everything that reads or changes user data, including (but not limited to):
/api/strategies/*, /api/goals/*, /api/trading/*, /api/settings/*, /api/portfolio/*, /api/trades/*, /api/watchlist/*, /api/reports/*, /api/daily-brief/*, /api/system/*, /api/ai/* (except any explicit public endpoints you know are safe to leave open).

Leave public only: /api/health, /api/auth/login, /api/auth/refresh (and /api/auth/register if it must remain for now).

Stop relying on the user-id request header for access control; all protected handlers should resolve the user from the verified token (the middleware already places the user on the request object).

Acceptance checks for Step 1

Calling any protected endpoint without Authorization: Bearer <token> returns 401 Unauthorized.

Calling the same endpoint with a valid token returns 200 OK.

No route that reads/writes user data is accessible without a valid token.

Step 2 — Remove Any Plaintext Passwords

Where: Database (users table)

Identify any user records whose password is not a bcrypt hash.

Remove or re-hash those records (prefer removal if they are test accounts).

Ensure all passwords start with a bcrypt signature (e.g., $2b$…).

Acceptance checks for Step 2

Querying users.password shows only bcrypt hashes.

No rows with readable/plain text passwords remain.

Step 3 — Set Strong JWT Secrets

Where: Replit → Secrets (Environment Variables)

Set JWT_SECRET and JWT_REFRESH_SECRET to long, random values (64+ bytes).

Restart the app to apply.

Confirm that tokens issued before the change are rejected (expected) and new tokens work.

Acceptance checks for Step 3

New login/refresh flows succeed.

Old tokens (issued before secret change) are no longer valid.

Same endpoint with a valid token → 200

Password storage audit

Screenshot or snippet showing all users.password values are bcrypt hashes (start $2b$).

JWT secrets set

Show Replit Secrets panel entries for JWT_SECRET and JWT_REFRESH_SECRET (values redacted).

Confirm new tokens are issued and work.

Route coverage

List of route prefixes now protected (as above).

Confirm public endpoints still work: /api/health, /api/auth/login, /api/auth/refresh (and register only if intentionally public).

Success Criteria (Phase 1 Complete)

Every protected route requires a valid JWT (no exceptions).

Database contains no plaintext passwords.

Strong JWT secrets are set and in use.

App still functions normally when logged in.
