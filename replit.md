# Crypto Day Trading Web App

## Overview
This project is a long-only, spot-trading cryptocurrency day trading web application for Kraken. It automates advanced trading strategies, integrates real-time market scanning, and incorporates disciplined risk management. The application supports both live and paper trading, leveraging OpenAI's GPT models for AI analysis, trade tracking, performance analytics, error diagnosis, and an autonomous learning engine. Its core purpose is to deliver a comprehensive, resilient, and continuously self-optimizing trading platform with significant market potential in automated crypto trading.

## User Preferences
Preferred communication style: Simple, everyday language.

## System Architecture
The application features a React, TypeScript, Vite frontend with a mobile-first, responsive design, and a Node.js/Express backend providing a RESTful API and WebSocket support. PostgreSQL, utilizing Neon serverless driver and Drizzle ORM, handles data persistence. Authentication uses username/password, bcrypt, JWT, and WebAuthn.

Core services include `KrakenService`, `TradingEngine`, `StrategyEngine`, `MarketScanner`, `RiskManager`, `AIAnalyst`, and `AIOpportunitiesService`. An AI Orchestrator & Command Center, powered by GPT-4o, includes an AI SysAdmin Co-Pilot named Walter, featuring a Unified Command & Conversation Layer, Semantic Memory Layer, Intelligence Refinement Layer, Real-Time Execution Layer, and a Unified Portfolio & Strategy State. It employs a Hybrid Cognitive-Operational design with an Intent Gateway, `SecureCoreService`, Continuous Learning Pipeline, `StateAwarenessService`, Intent Execution Framework with a `Pre-Execution Validator`, and an Autonomy Layer with Safety Guardrails & Operational Kill Switch. The system supports paper trading simulation with a database-first architecture and multi-intent command processing. Live trading includes voice/chat activation with manual approval workflows.

The architecture uses a global mode-based engine (one per live/paper mode) shared by all users. `ModeRegistry` provides production telemetry via WebSocket broadcasts, and `/api/system/health` offers dual-mode telemetry. `MetricsCore` centralizes metrics calculation with strict mode isolation for portfolio, risk, and execution KPIs, broadcasting real-time data via WebSockets. Live pricing is managed by a `LivePricingAdapter` with dual-source integration and WebSocket broadcasts.

The Goals Engine UI offers advanced universe and signal controls, execution rhythm controls, and simplified daily target goals with Trading Pace presets. A Goal Feasibility Validation & Audit System tracks and validates goal changes, calculating and displaying a rolling Average Daily Earnings % (ADE%). The Dashboard LATTI widget mirrors Goals Engine Target Daily Goals, displaying calculated values like Risk per Trade ($), Trades per Day, and Projected Portfolio Growth, with "Risk per Trade ($)" converted to "Portfolio Risk per Trade (%)".

The system incorporates a modern `guardrails_v2` schema with four core guardrail parameters: Portfolio Risk per Trade %, Symbol Cooldown (minutes), Max Open Positions, and Daily Loss Kill Switch %. It features dual-mode operation with independent guardrail sets, coherency validation (12 rules), backend API endpoints for GET/PUT guardrails, and real-time WebSocket broadcasts for configuration changes. Toggle controls allow switching between LATTi autonomous optimization and manual user control for individual parameters. A unified dashboard widget and Goals Preset Grid implement a 4+1 preset structure (Conservative, Baseline, Optimistic, Maximum, Custom) with coherency analytics. The **GuardrailPolicy Service** (`server/services/guardrail-policy.ts`) serves as the single backend source of truth for guardrail values, enforcing runtime coherency, managing effective value resolution, coherency validation, kill switch management, and conflict detection. The Goals Engine features an adaptive learning system that automatically optimizes preset boundaries based on 30-day performance metrics.

All legacy screener variable inputs have been removed, with the Screeners tab now exclusively using the unified v2 filter configuration with modern fields (Volume, Price, Market Quality, RSI, Volatility, Asset Type, Universe & Signal Controls). A comprehensive audit system ensures that only current, visible fields influence the trade engine through runtime validation, database views (`v_guardrails_active`, `v_filters_active`, `v_goals_active`), diagnostic endpoints, and startup telemetry. An automated anomaly detection system for override configuration changes, `AuditAnomalyDetectionService`, analyzes audit logs for unusual patterns.

**Adaptive Guardrails (v2.3)** introduces a local-only learning system (`AdaptiveGuardrails` service) that allows LATTI to adaptively tune parameters based on trading outcomes using variance-based statistical analysis of 30-day performance metrics. A strict throttle mechanism limits changes to 3 per 24 hours. `behavioral_log` tracks changes, and `learning_history` maintains versioned snapshots for rollback. Override influence weighting adjusts AI aggressiveness based on user manual overrides. The `LearningCycleService` runs autonomously every 24 hours.

**DHMA Strategy (v2.4)** implements Dual-Horizon Microstructure Alpha, a microstructure-based trading strategy. The `DHMAStrategy` module (`server/strategies/dhma.ts`) provides simplified microstructure features using OHLCV data. Entry logic requires dual-horizon alignment, configurable thresholds, and safety controls. Position sizing uses dynamic down-weighting based on spread and toxicity. The strategy integrates with `StrategyEngine.detectDHMA()` and validates trades through `guardrailPolicy.validate()`. DHMA parameters are configurable via a flexible, mode-aware parameter configuration system stored in a `strategy_param_schema` table, allowing dynamic adjustment and independent configurations for paper and live trading modes. The `DHMATuningService` implements intelligent adaptive parameter optimization for DHMA based on real-time trading performance metrics.

**Strategic Drive & Profit Optimization Engine (Phase 31)** tracks 5 strategies (DHMA, QuantFlow, TrendPulse, VolSurf, MomentumX) with hourly performance analysis and computes a global Strategic Drive Index (SDI) with EMA smoothing and forecast logic with confidence scores. "Soft Guardrails, Hard Coherency" is implemented via `StrategicDriveGuardrailService` controlling reallocation behavior based on six parameters. This service acts as a dynamic stabilizer for reallocations while coherency rules provide hard safety stops. The Motivational Incentive Engine tracks `driveIndex` and `personalBest` based on SDI performance, with configurable reward and penalty factors. A System Configuration Service, using a `system_config` table, manages global flags, including a `passiveLearning` mode, with in-memory caching and API endpoints for configuration. A LATTI Tuning monitoring tab displays tuning cycle metrics, confidence scores, and parameter adjustments. LATTI Learning Insights provide visibility into internal learning observations, generating dynamic insights on Spread Tightness, Burst Alignment Accuracy, and Toxicity Ratio with correlation scores and simulated adjustments. Cross-Strategy Learning Correlations display how LATTI associates market conditions with success probabilities for 8 strategies.

Comprehensive monitoring and default operational state enhancements include strategy usage summary, passive learning as default, cross-user mode synchronization via WebSocket, a `/api/system/health-sdpoe` endpoint, telemetry heartbeat logging, and a trade execution verifier. The system now uses an authoritative trading state contract via `/api/trading/status` and `trading_state_changed` WebSocket events for consistent state synchronization.

WebSocket Optimization and State Synchronization improvements include a singleton WebSocket connection pattern, hydrate-first state management for critical caches, an invalidation loop guard, polling optimization, and price broadcast throttling. Authentication and Portfolio Balance Unification was achieved by creating a unified `apiFetch` base fetcher, fixing query key formats, enhancing `trading_state_changed` WebSocket broadcasts to include `portfolioOverview`, and standardizing portfolio overview query keys.

**Phase 36: Live Trade Simulation Reliability Validation** successfully validated system stability under sustained 10-minute live-mode operation. Two critical bugs were fixed: the earnings chart API endpoint (was passing userId instead of mode parameter, causing enum errors) and the performance profiler component (changed from useEffect to useMemo to capture mount timing correctly, fixing >5-minute first-paint skew). The 10-minute live simulation demonstrated excellent performance: 8,963 Dashboard renders with 3.4ms average update time (99.99% success rate), one acceptable outlier at 404.5ms (0.01% of renders), zero crashes or WebSocket disconnections, and all API endpoints stable. Production-ready thresholds established: first-paint <200ms, average render <30ms, max render <500ms. Phase 35.3 optimizations (debounced invalidation, 30s reconciliation interval) validated working correctly. Comprehensive validation report archived at `diagnostic-reports/phase-36-live-simulation-results.md`.

**Phase 37: SignalOrchestrator Integration & Type System Corrections** successfully integrated the hybrid timer-based (30s) + event-driven signal generation system. Critical bug fixed in `FilteredPairsService`: resolved type mismatch where non-existent `ScreenerFilter` (singular) was used instead of correct `ScreenerFilters` (plural) from database schema, causing `TypeError: Cannot read properties of undefined (reading 'minVolume')`. Fixes included: corrected imports to use `ScreenerFilters` type, updated method signatures, fixed `KrakenService.getEligiblePairs()` integration to pass settings object instead of individual parameters, properly mapped all filter fields (`maxBidAskSpread` instead of non-existent `maxSpread`, removed references to non-schema fields like `minVolumeUsd`, `maxVolumeUsd`, `minDailyRange`, `maxDailyRange`, `maxMarketCap`, `blacklist`), and added JSON parsing error handling with try/catch blocks for `quoteCurrencies` and `activeTimeframes` fields per architect recommendations. The SignalOrchestrator now successfully evaluates market conditions every 30 seconds with proper type safety and field mapping.

**Phase 38: Unified Filtering & Insights Refactor** successfully eliminated redundant filtering logic and created a Single Source of Truth (SSOT) for market evaluation. The `MarketEvaluationService` (`server/services/market-evaluation.ts`) unifies all filtering under one service, wrapping `FilteredPairsService` with a 15-second cache. All user-facing endpoints now use the SSOT, eliminating the 17 vs 658 pair discrepancy from Phase 37. Critical cache fix applied: Cache keys now include filter hash (`mode:filterHash`) to prevent cross-user contamination when users have different screener settings. The `/api/paper-sim/filtered-pairs` endpoint migrated to SSOT, achieving 0 pair difference across all production endpoints (SignalOrchestrator, Filtered Pairs UI, Insights Tab). Walter Compatibility Adapter (`server/adapters/walter-compat.ts`) created with `WALTER_COMPAT_MODE` feature flag for future analytics integration. Admin diagnostic endpoint (`/api/paper-sim/diagnostics/scan`) retained with broader filtering for debugging purposes. Comprehensive validation achieved: <300ms latency (actual: ~145ms), 15s cache TTL, source tagging (`market_evaluation_ssot`), and WebSocket broadcasting. Four diagnostic reports archived: reference inventory, Walter compatibility parity, unified validation metrics, and final summary. Architect approved production readiness with recommendation for multi-filter regression testing in Phase 39.
