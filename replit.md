# Crypto Day Trading Web App

## Overview
This project is a long-only, spot-trading cryptocurrency day trading web application for Kraken. It automates advanced trading strategies, integrates real-time market scanning, disciplined risk management, and offers both live and paper trading capabilities. The application leverages OpenAI's GPT models for AI analysis, trade tracking, performance analytics, error diagnosis, and an autonomous learning engine. Its primary goal is to provide a comprehensive, resilient, and continuously improving self-optimizing trading platform, delivering a leading-edge solution in automated crypto trading with significant business and market potential.

## User Preferences
Preferred communication style: Simple, everyday language.

## System Architecture
The application features a React, TypeScript, Vite frontend with a mobile-first, responsive design. The backend uses Node.js and Express, providing a RESTful API and WebSocket support. Data persistence is managed by PostgreSQL via Neon serverless driver and Drizzle ORM.

Core services include `KrakenService`, `TradingEngine`, `StrategyEngine`, `MarketScanner`, `RiskManager`, `AIAnalyst`, and `AIOpportunitiesService`. Authentication uses username/password, bcrypt, JWT, and WebAuthn.

An AI Orchestrator & Command Center, powered by GPT-4o, features an AI SysAdmin Co-Pilot named Walter. Walter's architecture includes a Unified Command & Conversation Layer, Semantic Memory Layer, and an Intelligence Refinement Layer, incorporating a multi-module intelligent caching system (Bob Core) and a Hybrid Cortex Intelligent Memory Layer. The system includes a `SystemHealthMonitor`, `SelfRepairService`, a Natural Language Action Interpreter (NLAI), and a Contextual Intent Engine (CIE). The Real-Time Execution Layer manages market data, execution timing, slippage modeling, and rate control. A Unified Portfolio & Strategy State ensures a single source of truth. Walter's architecture is Hybrid Cognitive-Operational, with an Intent Gateway for validating operational commands and a `SecureCoreService` for domain restriction. A Continuous Learning Pipeline extends the Event Broker to capture trade events and transfer knowledge. A `StateAwarenessService` provides system state snapshots. An Intent Execution Framework provides safe, audited execution of validated intents, with a `Pre-Execution Validator`. The Context Bridge enables real-time, bidirectional synchronization between Walter's panel, chat widget, and backend systems via WebSocket broadcasting.

The Reasoning Orchestrator enables Walter's multi-step transparent reasoning via Domain Bobs (DevOps, FullStack, UX, TradingBob). The Memory Lifecycle Manager ensures semantic memory integrity. An Async Task Queue provides distributed multi-domain reasoning with parallel execution. Cognitive Tuning & Testing provides automated performance validation.

The Autonomy Layer introduces self-directed analysis, meta-reasoning, exploratory learning, and automated optimization capabilities through `AutonomyController`, `MetaReasoningEngine`, `CuriosityEngine`, and `SelfOptimizer`. The Emergent Awareness Layer enables meta-cognitive state tracking and self-reflection via `AwarenessCoreService`. The Adaptive Learning & Goal Alignment Foundation enables experience-based learning and policy-aligned adaptation through `ExperienceMemoryService` and `AdaptiveObjectiveEngine`.

Safety Guardrails & Operational Kill Switch provides comprehensive safety controls with database tables, a `SafetyGuardrails` service, and admin-only API endpoints to halt all trading/execution.

Ethical Alignment Framework establishes comprehensive ethical reasoning across all autonomous decisions with database tables and an `EthicalReasoner` service integrated into the Autonomy Controller execution chain.

Controlled Web Intelligence & Knowledge Retrieval uses a `KnowledgeRetrievalService` for policy-bound web acquisition and a `SemanticCorrelationEngine`.

The Autonomous Execution Layer provides Walter with complete autonomous command execution capabilities. The `ExecutionPolicyController` evaluates every Walter command against approval matrix settings and risk thresholds, creating comprehensive audit trails in the `walter_execution_log` database table. The NLAI Execution Broker orchestrates the execution pipeline: policy evaluation → action execution → result logging → cluster bus event emission.

Paper Trading Simulation State Management uses a database-first architecture with comprehensive reconciliation diagnostics.

Multi-Intent Command Processing enhances Walter's NLAI to detect, parse, and execute multiple intents from single user messages.

Live Trading Voice/Chat Activation enables Walter to manage live trading mode through voice or chat commands with comprehensive manual approval workflows.

The Automatic Test Harness provides automated end-to-end validation of conversational and operational flows with an `AutoTestHarness` framework.

Context Persistence Framework enables Walter to automatically internalize mission context and development history on startup by scanning designated markdown files (`/replit.md` and `/context_uploads/*.md`). This framework includes a 10-layer sanitization pipeline to ensure production readiness and security.

Inline Approval Prompts & Interactive Notifications provide seamless manual approval workflows through dual interfaces: inline chat approvals and bell notification center. This includes comprehensive API endpoints for approval management and real-time WebSocket integration for automatic notification refresh.

Frontend Permission Integration implements comprehensive role-based access control (RBAC) on the frontend with fail-closed security, using a `useUserRole` hook and `can(permission)` helper for granular checks. Server-side validation with `requirePermission` middleware ensures database is the source of truth.

Trading State Synchronization & Fail-Safe Recovery provides database-backed trading mode persistence with automatic recovery and cross-service coordination via the `system_context` table and `TradingStateSync` service. It includes kill-switch integration and broadcasts state changes via WebSocket for real-time synchronization.

Goals Engine Persistence & Audit Logging provides comprehensive audit trails for all goal changes in the Goals Engine via the `goal_audit_log` table, ensuring durable persistence and server-authoritative hydration.

Goals Engine Canonical Metrics (Phase 27.F) implements metric name canonicalization to prevent duplicate goals from being created. The `canonicalizeMetricName` function normalizes metric names (lowercase, remove spaces/special chars) to create a canonical `metric_key` for lookups. Database schema includes unique constraint on `(user_id, metric_key)` to enforce integrity. Migration backfilled 28 existing records, removed 1 duplicate ("Earnings per Day" vs "EarningsPerDay"), and verified all records have canonical keys. Storage layer upserts use `metric_key` for lookups while preserving display-friendly `metric_name`. Comprehensive verification tests confirm canonicalization works correctly and duplicates cannot be created.

Goals Hydration & Trading Toggle Fix (Phase 27.F.1) ensures Goals Engine always displays fresh data and trading mode switches work reliably. Frontend components (`GoalsEngineTab`, `PerformanceTrackingMetrics`) now query `/api/goals` with `refetchOnMount: 'always'` and aggressive cache invalidation after mutations. Trading mode switching uses `/api/trading/set-mode` (not `/api/settings`) to trigger atomic database updates via `TradingStateSync` service and broadcast `trading_state_changed` WebSocket events. TopBar component listens for these WebSocket events and invalidates queries for real-time UI synchronization, with 5-second polling fallback via `useTrading` hook. Both LIVE and PAPER mode buttons are clickable (not mutually exclusive) for seamless switching. Optimistic UI updates provide immediate feedback, with WebSocket confirmation for eventual consistency.

Trading Toggle Synchronization & Stop Logic Final Fix (Phase 27.F.2) provides complete UI/backend synchronization for trading engine start/stop operations. The `TradingStateSync` service now includes a `broadcastUserUpdate` method that broadcasts full trading state (mode, active, timestamp) via WebSocket after every toggle operation. Updated `/api/trading/start` and `/api/trading/stop` endpoints use `tradingStateSync.setEngineActive()` to update `system_context.is_engine_active` and immediately broadcast state changes with deterministic response payloads. Frontend TopBar component derives `isActive` state directly from TanStack Query results (`paperSimStatus?.isRunning` or `tradingStatus?.engineActive`), with WebSocket listeners invalidating all relevant queries for real-time synchronization. A Reconciliation Guard runs every 15 seconds to detect DB/cache mismatches and re-broadcast state for eventual consistency. Owner and admin roles now automatically receive all permissions via the `can()` helper in `useUserRole`, ensuring LIVE and PAPER mode buttons are always clickable for administrators. Console logs `[TradingStart]`, `[TradingStop]`, and `[TradingSync]` provide comprehensive audit trails for all state changes.

Unified Trading State Authority (Phase 27.F.3) establishes a single source of truth for all trading state across frontend and backend. Backend enhancements include: `broadcastUserUpdate()` expanded with complete state snapshot (mode, isEngineActive, tradingModeLabel, lastModeChange, changedBy, changeReason), `/api/trading/status` endpoint returns unified state object with all metadata (mode, active, engineStatus, lastUpdate, lastUserAction) always fresh from database. Frontend consolidation: `useTrading` hook now subscribes to `trading_state_changed` WebSocket events for immediate invalidation, implements 3-second forced reconciliation timer to detect state mismatches, logs all sync events with `[SYNC]` prefix for debugging. TopBar toggle derives `isActive` directly from TanStack Query cache (never local state), disabled only during pending mutations. ModeBanner enhanced to display both mode (Live/Paper) and status (ACTIVE/STOPPED) derived from unified trading store, with play/pause icons. All components poll `/api/trading/status` every 5 seconds as fallback, ensuring eventual consistency even without WebSocket. Console logging provides full audit trail: `[Phase-27.F.3]`, `[SYNC]`, `[TradingSync]`.

Trading Engine Invocation Fix with Audit Trail (Phase 27.F.6) ensures trading toggles actually start/stop trading engines (not just update UI state) and provides comprehensive audit logging for all trading operations. Database infrastructure includes `trading_audit_log` table with columns (id, user_id, action, mode, triggered_by, metadata, created_at) for tracking all start/stop actions. Frontend modals provide safety guardrails: `ConfirmLiveTradingModal` warns users about real money risk before live trading activation, `ConfirmStopLiveTradingModal` confirms stopping live trading operations. TopBar toggle buttons now invoke actual engine endpoints (`/api/trading/start`, `/api/trading/stop`, `/api/paper-sim/start`, `/api/paper-sim/stop`) instead of just updating state. All four endpoints emit standardized `[TradingStart]` and `[TradingStop]` console logs for operational visibility and call `storage.createTradingAuditLog()` wrapped in try-catch to prevent audit failures from breaking core flows. The implementation maintains existing WebSocket state synchronization and 5-second polling fallback for real-time UI updates.

PaperSim Lifecycle Initialization Fix (Phase 27.F.8) eliminates ghost manager issues by implementing lazy initialization and explicit reset on startup. The `resetPaperSimService()` function in `server/services/paper-sim-service.ts` clears all in-memory state (`global.globalPaperPortfolioManager` and `global.globalPaperSimOperationLock`) on server boot, preventing orphaned managers from persisting across workflow restarts. This reset runs immediately after route registration in `server/index.ts` (before any services initialize), ensuring clean state with logs confirming `hasManager: false, hasDbSession: false`. The fix addresses pre-existing state desync where managers existed in memory without corresponding database sessions, providing a deterministic startup sequence: routes register → reset clears globals → heartbeat checks → services initialize. Managers are now only created when `/api/paper-sim/start` is explicitly called, never during passive status checks or heartbeat operations.

PaperSim State Reconciliation & Atomic Manager Creation (Phase 27.F.9) fixes state mismatches between the PaperSim service and global manager by implementing synchronized manager API helpers and atomic creation/destruction patterns. The implementation adds three helper functions (`getGlobalPaperSimManager`, `setGlobalPaperSimManager`, `clearGlobalPaperSimManager`) to provide atomic access to the global manager state. The `startPaperSimulation()` function now atomically creates both database session and global manager with comprehensive reconciliation logic: if both exist, returns idempotent success; if session exists but manager is lost, recreates manager; if orphaned manager exists without session, clears it before creating new session. The `stopPaperSimulation()` function atomically clears both global manager reference and ends DB session with cleanup logs. The heartbeat service (`paper_sim_heartbeat.ts`) includes a reconciliation guard that automatically detects and cleans up orphaned global managers (manager exists without DB session). Enhanced logging in routes.ts provides audit trails with `[TradingStart]` and `[TradingStop]` prefixes. The fix ensures hasManager state accurately reflects reality, eliminates "already running (system-wide)" errors after normal stop/start cycles, maintains global and service state synchronization, and ensures PaperSim sessions appear and end correctly in the database with UI toggle status always reflecting real engine state.
