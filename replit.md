# Crypto Day Trading Web App

## Overview
This project is a long-only, spot-trading cryptocurrency day trading web application for Kraken. It automates advanced trading strategies, integrates real-time market scanning, disciplined risk management, and offers both live and paper trading capabilities. The application leverages OpenAI's GPT models for AI analysis, trade tracking, performance analytics, error diagnosis, and an autonomous learning engine. Its primary goal is to provide a comprehensive, resilient, and continuously improving self-optimizing trading platform, delivering a leading-edge solution in automated crypto trading with significant business and market potential.

## System Architecture
The frontend is built with React, TypeScript, Vite, shadcn/ui (Radix UI + Tailwind CSS), and TanStack Query, featuring a mobile-first, responsive design with dynamic mode-aware UI, voice transcription, and a System Truth Panel. The backend uses Node.js with Express, providing a RESTful API and WebSocket support. Data storage is handled by PostgreSQL via Neon serverless driver and Drizzle ORM.

Key services include `KrakenService`, `TradingEngine`, `StrategyEngine`, `MarketScanner`, `RiskManager`, `AIAnalyst`, and `AIOpportunitiesService`. The system supports 8 automated trading strategies, multi-layered risk management, and a Continuous Learning Engine (CLE). Authentication uses username/password with bcrypt, JWT, and WebAuthn.

An AI Orchestrator & Command Center, powered by GPT-4o, provides insights and an AI SysAdmin Co-Pilot named Walter handles system configuration and optimization. Walter operates with a Unified Command & Conversation Layer, Semantic Memory Layer (pgvector and OpenAI embeddings), and an Intelligence Refinement Layer with a Self-optimizing Cognitive Weight Adjuster. A Paper Trading Simulation Engine provides real-time execution.

The system incorporates a multi-module intelligent caching system (Bob Core) and a Hybrid Cortex Intelligent Memory Layer. System Health & Diagnostic Intelligence includes `SystemHealthMonitor` and a `SelfRepairService` for automated recovery. A Natural Language Action Interpreter (NLAI) and Contextual Intent Engine (CIE) enable Walter's understanding and command execution.

The Real-Time Execution Layer includes `MarketDataWebSocket`, `ExecutionTimingService`, `SlippageFeeModelingService`, `RateControlService`, `MarketDataCoordinator`, `RealtimePaperExecutor`, and `ParityGateService`. Unified Portfolio & Strategy State ensures a single source of truth, maintained by a `portfolio_state` database table and `StrategySync` Service. System Truth Synchronization & Context Refresh establishes cross-layer data consistency validation.

Walter features a Hybrid Cognitive-Operational architecture with a Cognitive Layer for intent reflection and an Intent Gateway for validating operational commands with RBAC, risk assessment, and audit logging. Unified Conversational Walter routes all system outputs through natural language interpretation via a Cognitive Interpreter Service and Event Broker.

Data Provenance & Source Governance ensures end-to-end traceability with `data_lineage` and `bob_trace_log` tables. Schema Binding Validation & Learning Alignment provides comprehensive validation of data sources and cognitive learning alignment. A Purpose Layer (`purpose-layer.ts`) loads system purposes, and Corpus Domain Rebinding (`corpus-domain-service.ts`) manages knowledge domains.

Secure-Core Mode Toggle (`SecureCoreService`) restricts Walter's domains when enabled. The Continuous Learning Pipeline extends the Event Broker to capture trade events, generate insights, and transfer knowledge from paper to live trading.

A State Awareness Layer (`StateAwarenessService`) provides a single authoritative snapshot of the entire system state for Walter and UI components, which is injected into Walter's system prompt. An Intent Execution Framework provides safe, audited execution of validated intents from Walter AI with full RBAC, state validation, and provenance tracking, logging operations to `intent_audit_log`. A Pre-Execution Validator (`pre-execution-validator.ts`) ensures every trade intent undergoes comprehensive validation for risk compliance, goal alignment, and execution readiness before placement.

Context Bridge (Phase 8.7.4) enables real-time, bidirectional synchronization between Walter's panel, chat widget, and backend systems via WebSocket broadcasting. `ContextBridge` service (`context-bridge.ts`) maintains active WebSocket client connections with tenant isolation (userId-based filtering), broadcasts state updates to connected clients with 3-retry logic and exponential backoff (1s→2s→4s), manages unified session context with intent history tracking, and logs all broadcasts to `context_bridge_log` table with deliveryStats {successCount, failureCount, totalTargets} for audit trail. Auto-broadcast integration: State Awareness Layer broadcasts after snapshot generation, Intent Execution Service broadcasts after successful execution, config changes trigger config_update broadcasts. Event types: `state_update` (trading status, balances, strategies), `chat_update` (Walter messages), `config_update` (settings changes), `trade_update` (execution results). WebSocket clients connect via `/ws` endpoint with `userId` query parameter extracted from localStorage. Frontend `useWebSocket` hook (`use-websocket.tsx`) implements exponential backoff reconnection (1s→2s→4s up to 30s max), heartbeat ping/pong every 25s (closes after 3 missed pongs), and auto-connects when WalterPage or ChatPanel components mount. Session context includes sessionId, userId, intentHistory (last 50 intents), validationContext, and lastUpdated timestamp. Stale session cleanup runs hourly (24-hour inactivity threshold). API endpoint: `GET /api/context/bridge/stats` returns connectedClients count, activeSessions count, and session details. React Query cache invalidation: config_update invalidates /api/settings and /api/goals/summary, state_update invalidates /api/trading/status and /api/portfolio/overview, trade_update invalidates /api/trades, chat_update invalidates /api/walter/chats. Verified working: E2E tests confirm WebSocket client registration, broadcast delivery (totalTargets=1, successCount=1, failureCount=0), and UI auto-refresh within 2 seconds of backend state changes.

Reasoning Orchestrator (Phase 8.8.1) enables Walter's multi-step transparent reasoning via Domain Bobs (DevOps, FullStack, UX) for contextual analysis before LLM response generation. `ReasoningOrchestrator` service (`reasoning-orchestrator.ts`) builds execution plans from user intents, queues domain-specific tasks in `reasoning_queue` PostgreSQL table, executes tasks via specialized Domain Bobs, and logs complete reasoning traces to `reasoning_trace` table with provenance tracking. Domain Bobs include: `DevOpsBob` (system health, deployment metrics, error logs), `FullStackBob` (schema analysis, API performance, codebase insights), and `UXBob` (UI layout validation, usability feedback, component analysis). Integration flow: walter-response.ts calls reasoningOrchestrator.createPlan() after state snapshot → builds multi-step plan with domain context → injects reasoning chain into system prompt → LLM generates response → logResult() stores outcome. Reasoning traces include traceId (nanoid), userId, intentAction, systemState snapshot, mode (live/paper), status (pending/in_progress/completed/failed), steps array, domainContext array, outcome, error, and processingTimeMs. Queue tasks include id (serial), traceId, stepId, bobDomain (devops/fullstack/ux), action, params (JSONB), status, result (JSONB), error, retryCount (max 3 with exponential backoff), createdAt, startedAt, completedAt. Debug API endpoint `GET /api/reasoning/debug/:traceId` returns complete trace with all queued tasks for transparency and audit. Walter's system prompt includes reasoning chain section with trace ID, domains, and step-by-step breakdown, enabling transparent multi-step analysis visible to users.

Memory Lifecycle Manager (Phase 8.8.2) ensures semantic memory integrity through automated checksum validation, auto-repair, and nightly learning feedback aggregation. `MemoryLifecycle` service (`memory-lifecycle.ts`) initializes on server startup, computes SHA-256 checksums for all semantic_memory entries, detects inconsistencies via checksum comparison, and auto-repairs corrupted entries by rehydrating from file_persistence backup with audit logging to `memory_audit_log` table. Learning Feedback Job (`jobs/learning-feedback.ts`) runs nightly at 2 AM, aggregates last 24h trade insights from `trades` table (outcome, realizedPL, reasonSnapshot, notes), generates embeddings via OpenAI, synthesizes narrative learnings via GPT-4o mini, and populates `learning_fragments` table with traceId provenance. Memory audit log includes id (serial), memoryId (FK to semantic_memory), checksum (varchar), status (enum: valid/corrupted/rehydrated), traceId, error, createdAt, validatedAt. Rehydration API endpoint `POST /api/memory/rehydrate` manually triggers memory restoration from backup. Status API endpoint `GET /api/memory/status` returns {totalEntries, validCount, corruptedCount, lastValidation}. Audit API endpoint `GET /api/memory/audit` returns recent audit logs with pagination. Integration: server/index.ts imports memoryLifecycle.initialize() on startup for auto-validation, registerLearningFeedbackJob() registers nightly scheduler task. Memory integrity workflow: startup → compute checksums → compare with stored values → detect corruption → auto-repair from file_persistence → log audit trail → nightly learning synthesis → embed and store fragments.
