## 2. FINDING F-1 — the overall feed status locks itself at `critical` (rule 24 outcome 1, real defect)
**Symptom, measured:** Friday, **234 of 236** feed checks logged `Creating critical alert` while every liveness line was healthy; the saved report at 07:50Z reads `overallGrade F`, `uptimePercent 0.42`, `stalenessSec 0`, `reconnectCount 0`, `latencyMs 1001`. No `FEED_*` override in staging's `.env` (0 lines), so the code defaults apply.
**Mechanism (re-derived by a claim-only fresh reader, its correction folded):** `recordSnapshot` reads `uptimePercent = calculateTimeBasedUptime()` (`feed-integrity-monitor.ts:475`) — `healthyMinutes / minutes since uptimeStartTime` — and grades `isHealthy` from it (`:478-479`, `categorizeHealthBySpec`: healthy needs uptime ≥ 95, critical below 80) **before** crediting the current interval to `healthyMinutes` (`:482-487`), which it does only when `isHealthy`. The first snapshot after construction is credited a few seconds (the `< 1 min → 100` branch, `:437-438`); the second, ~5 min later, reads uptime ≈ 0 → critical → its interval is not credited → **locked**. A restart or `reset()` (`routes.ts:15336`, the cleanup route) restarts the same dynamics. **The clear (`feed-integrity-auto-check.ts:127`) reads `metrics.status` from `getHealthMetrics`, which uses the same `calculateTimeBasedUptime` (`:240`)** — so it is critical whenever uptime < 80 and the "non-healthy → healthy" transition the clear waits for cannot happen.
**Provenance:** `calculateTimeBasedUptime` was introduced by `b4ca15d63` (2025-10-21, Replit, *"Enhance data feed monitoring…"*). P19-B6.9 (`#398`) already replaced the PARITY GATE's uptime with `getRollingWindowReadiness()` (`:278`) — a windowed, self-healing ratio over the 12-snapshot ring of per-interval reconnects — *"the self-healing property the cumulative metric lacked"* (its own docstring); the status path was never moved. Ledger searched (`RUNNING_ISSUES`, completion reports) for `calculateTimeBasedUptime` / `healthyMinutes` / `uptimePercent`: only the `#398` parity-gate work; this lock is not recorded.
**Proposed fix (one uptime, not two):** the status path takes its uptime from `getRollingWindowReadiness()` — connection-based (reconnects per interval), not derived from the status's own verdict — and while it is warming up (`ready: false`) the uptime term does not vote (the other terms still do). `calculateTimeBasedUptime`, `healthyMinutes`, `totalMinutes`, `uptimeStartTime` are then dead → deleted (rule 18). **Test:** a monitor run through N healthy snapshots reports `healthy` (it reports `critical` today — mutation-proving); a reconnect-heavy window still drives `critical`. **Effect on staging:** the status follows the connection; the first recovery fires the clear and the 1,098 backlog is acknowledged (objective 2's own criterion, then measurable).
