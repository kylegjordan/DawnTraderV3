## 2. STEP 2 — Outage-tagging (folded into Step 3 — NOT a separate batch)

### Design note

The `macro_feed_archive` table already has `fallback_active BOOLEAN` per row, captured at `captured_at` timestamp every poll cycle. So we DON'T need to tag the `regime_factor_alternates` rows themselves — we can do the exclusion at backtest read-time by joining on `evaluated_at`/`captured_at` proximity.

Backtest query joins logic:

```sql
-- For b67_1_* macro-modifier sub-rows only, exclude when feed was in fallback at signal time
LEFT JOIN LATERAL (
  SELECT fallback_active
  FROM macro_feed_archive
  WHERE captured_at <= rfa.evaluated_at
  ORDER BY captured_at DESC
  LIMIT 1
) feed ON true
WHERE
  rfa.factor_name NOT IN ('b67_1_btc_dominance', 'b67_1_mcap_momentum')  -- non-macro: include all
  OR (feed.fallback_active = false)  -- macro: exclude fallback-active windows
```

`b67_1_funding_rates` does NOT need the feed-exclusion filter because Binance is the source for that sub-component and Binance stayed clean.

### Why this is design-only, not a separate batch

- No schema change required (`macro_feed_archive.fallback_active` exists since B70 Step 3.3)
- No emitter-code change required (the alternates rows already capture the modifier value at signal time; we infer fallback retroactively by timestamp join)
- The filtering lives entirely in the backtest tool's read query

### Specific question for you

Q2a — Acceptable to do the filtering at query-time via timestamp join, OR do you want a tagged-at-emission-time approach (new column `feed_state TEXT` on `regime_factor_alternates`, populated by emitter)? Query-time is cheaper and retroactively-applicable; tag-at-emission is more durable but requires schema migration + emitter change for future-proofing.

Q2b — The proximity-join window: `captured_at <= evaluated_at ORDER BY captured_at DESC LIMIT 1` finds the most-recent macro snapshot at-or-before signal time. Max staleness — should I add an `AND captured_at >= evaluated_at - INTERVAL '5 minutes'` clamp so we don't accidentally use a stale snapshot from a feed gap (e.g., if PM2 was down)? Default is 60s poll cadence, so 5min would mean "missed up to 5 polls."

## 3. STEP 3 — B-NEW-33: One-shot factor calibration backtest tool

### Scope

**Goal:** produce per-lever lift verdicts on the existing 30-day data without waiting for the broken nightly replay cron to recover.

**Output:** structured markdown report at `Claude Comms and Packages/Backtest Reports/B-NEW-33_FACTOR_CALIBRATION_BACKTEST_<date>.md` PLUS a JSON dump alongside. Optional: surface results in a new section of the Drift Dashboard UI tab (deferred to follow-on if time-boxed).

**New file:** `server/scripts/factor-calibration-backtest.ts` (companion to existing `replay-ablation.ts`, not a replacement). Idempotent, side-effect-free (reads only, no DB writes).

### Algorithm

1. **Load alternates:** `SELECT factor_name, evaluated_at, real_decision, alternate_decision, source_type, source_id, symbol, strategy, metadata FROM regime_factor_alternates WHERE evaluated_at >= NOW() - INTERVAL '<N>' days AND asset_class = 'crypto_spot'`
   - Default N=30; CLI flag `--days N` to adjust
   - For b67_1_* and b67_2_*: filter to `metadata.calibrationFrameworkVersion='b76_chain_final'` (per existing aggregator semantics)
   - For b67_1_btc_dominance and b67_1_mcap_momentum specifically: also join `macro_feed_archive` per Step 2 logic and exclude `fallback_active=true` windows
   - For b67_1_funding_rates: no feed exclusion (Binance source clean)

2. **Match to VTS trade outcomes:** for each alternate row, find the corresponding `vts_open_trades` (or closed-trade) record by:
   - Primary: exact match on `signal_id` (if alternate has source_id pointing at a paper_sim_trades row) — currently disabled in `replay-ablation.ts` per the `unreplayable_active_no_signal_id_join` outcome note (line 251-256). NEW work: actually JOIN on `signal_id` if it exists; the existing `paper_sim_trades` schema may need a check on whether signal_id is captured.
   - Fallback: bucket-match on `(symbol, strategy, evaluated_at ± window)` against closed VTS trades in `vts_open_trades` (closed = `closed_at IS NOT NULL`). Window: 5 minutes default (configurable).
   - Tertiary: skip with `outcome='unreplayable_no_match'` and don't count it toward sample sizes.

3. **Compute outcomes:** read `pnl_usd`, `won_lost`, `closed_at` from matched VTS trade. Outcome categories: `admitted_won`, `admitted_lost`, `still_open`, `unreplayable_no_match`. Only `admitted_won` and `admitted_lost` count toward win-rate calculations.

4. **Bucket + statistics:** identical algorithm to existing `computeFactorCalibration` (split into tertiles by realConfidence and altConfidence, compute win-rate spread per tertile, derive predictive-lift = real_spread − alt_spread).

5. **Decision-grade gates:**
   - `n_per_bucket ≥ 150` (existing constant `MIN_N_PER_BUCKET`)
   - `tertile_spread ≥ 7pp` (within real-confidence binning — measures discrimination)
   - `predictive_lift ≥ 7pp` (real vs alt — measures value-add)
   - `p-value < 0.05` via two-tailed binomial test on tertile win-rate difference (high vs low bucket)

6. **Per-lever verdict:**
   - **KEEP**: passes all gates with positive lift
   - **RETUNE**: borderline (n≥150 but one of the spread/lift/p gates marginal) — needs threshold/weight adjustment
   - **DROP**: passes n-gate AND has clear negative lift (e.g., b68_5 candidate)
   - **ACCUMULATING**: n<150 in any bucket — wait for more data

7. **Report sections:**
   - Per-lever summary table (10 factors)
   - Detailed per-factor tertile breakdowns
   - Excluded-row counts with reasons (fallback-active, version-filter, no-match)
   - Recommended B67.5 consumer-gate threshold candidates (derived from the data, not hardcoded)
   - Comparison vs API-output baseline (sanity check: should match `computeFactorCalibration` on the subset of replayed rows)

### Reuse vs new code

**Strongly reuse:**
- `bucketWinRate()` and `splitTertiles()` from `drift-dashboard-aggregator.ts` (lines 1000-1032) — extract to a shared util file
- Existing factor-name filter logic (b76_chain_final version-filter) — extract similarly

**New code:**
- The VTS-trade-outcome matcher (since `replay-ablation.ts`'s matcher is what's broken)
- The macro-feed-archive proximity-join logic (per Step 2)
- The binomial p-value computation (currently absent in aggregator; only spreads + lifts)
- The verdict-classification rules
- The report generator

### Verification plan

1. Local run on staging: `npm run script:factor-calibration-backtest -- --days 30`
2. Compare output against `/api/analytics/factor-calibration?window=rolling_30d` for the rows BOTH cover (replayed + post-b76 + clean-feed) — numbers should match within rounding
3. Visual verification: if we add a UI section, view it via Claude-in-Chrome at `/diagnostics?tab=drift-dashboard`. If markdown-only, the report file IS the verification artifact.

### Specific questions for you

Q3a — Symbol/strategy bucket-match fallback window: I proposed 5 minutes ± evaluated_at. The trade-open event is downstream of the signal-emit by some small delay (signal → orchestrator → VTS-open). Is 5min appropriate or should I make it tighter (e.g., 2min) to reduce false positives from rapid retriggered signals on the same symbol/strategy?

1. Backtests don't need live alerting to function — we're solving the present data-recovery problem first
2. The CoinGecko fix + the backtest tool collectively eliminate the immediate visibility gap (we'll have clean data flowing again post-step-1, and we'll have the audit report from step-3)
3. The alert-dispatcher is a real architectural component deserving its own scope + pre-audit + design review — not a rushed bolt-on
4. xStock Phase 0 (corp-actions audit) is the higher-priority next-batch after B67.5 finalization; squeezing the alerter in delays Phase 0
