## Increment 1b — OBJ-1b: a CHECKED-OUT connection ended by the server no longer crashes the app
**Found at Step 2, measured on staging 2026-11-04 (pg 8.13.1, own test pool, `application_name cc-a-pool-guard-test`):** pg-pool removes its error listener from a client when it hands it out (`index.js` `_acquireClient`, `client.removeListener('error', idleListener)`); pg emits `error` on a connection failure even mid-query (`client.js` `_handleErrorEvent`); `pool.query()` covers itself with `once('error')`, but a drizzle transaction holds the client from `pool.connect()` (`session.js:138`) with no listener. Test: transaction held, server ends it (`25P04 terminating connection due to transaction timeout`), release delayed 800 ms — **without the guard the process exits 1 (`Unhandled 'error' event`); with it, exit 0, one checked-out log line, and the next query on the pool succeeds on a fresh connection.** Released immediately instead, the error lands after release and the pool listener (OBJ-1) catches it.
**Changed:** `server/db.ts`: `pool.on('connect')` gives each new client a permanent error listener that logs `[B-DB-POOL-GUARD][POOL_CHECKED_OUT_CLIENT_ERROR]` only while the client is checked out (flag set on `acquire`, cleared on `release`); idle errors stay with OBJ-1's pool listener. pg-pool discards the dead client on release (`!client._queryable`).
**Tests (+2, 5 in all):** control (a bare client emitter throws); a checked-out client logs `code=25P04` and counts without throwing, and once released stays silent. Mutation: the connect listener renamed away, 2 of 5 fail.
**Why it matters beyond this batch:** this crash path exists today for any server-side end of a connection while a transaction holds it (an operator terminate, a server restart, a dropped network). OBJ-3 and OBJ-3b end such connections on purpose, so 1b must deploy before them.
