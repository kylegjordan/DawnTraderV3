## 1. Objectives
1. **Arm it — prefetch AND the clear, ONE commit.** Add `feed_health` to `PREFETCH_MODULES`; in the SAME commit flip the guard test: `PREFETCH_EXCEPTIONS` becomes empty, `:248` asserts `[]`, and `feed_health` joins the prefetched-module assertion beside `vts_xstock_touch`/`strategy.orb`. ⛔ **Objective 2 lands in the same commit — a prefetch without the clear arms a source that cannot clear.**
   *Verify:* after deploy, the boot line `[B72][warmup] prefetched module_constants module='feed_health' rows=5` and no `feed_health config not warmed` line since the restart; the guard test passes with the empty exception list; a unit test that `computeLiveness` grades (not skips) with the module warm.
2. **Clear what it raises — both mint paths, by acknowledging.** On a transition to `healthy` from a stored non-healthy status, the job calls `AlertsService.acknowledgeFeedHealthAlerts(admin.id)` for every admin user, logs the count per mode, then records `healthy` via `updateAlertState`, so the next healthy cycle does not repeat it. **No alert-id bookkeeping:** the dead `activeAlertId` branch (`:91-94`) and the field are REMOVED (rule 18). Because both paths mint `alertType: 'feed_health'`, one acknowledge clears grade-path and catch-path rows alike. **The catch-block path is throttled through the same `shouldSendAlert` / `updateAlertState` state** (status `critical`, grade `CHECK_FAILED`), so a persistent throw mints once per cooldown instead of every 5 minutes, and a later healthy check clears it.
   ⚠️ **The verb is ACKNOWLEDGE, not resolve.** `system_alerts` has a boolean `acknowledged` and no resolve state. The crew's "resolve, never ack" rule (§10.5, `#982`) governs `system-alerts.jsonl`, a different store, and does not carry over.
   ⚠️ **Stated effects:** the helper matches `alert_type LIKE '%feed%'`. Today the only such type is `feed_health` — measured in the table (5,708 rows, one type) and in code (the four `createAlert` calls above are the only `feed`-typed literal in `server/` and `shared/`; a dynamically built type would not show in that grep, which is why the table read is the second check). It is per user across BOTH modes, so the first recovery after deploy also acknowledges the 1,088 stale `live` rows (§0.2). That is intended: they are a backlog from a path that could never clear.
   *Verify:* unit tests — (i) non-healthy → rows minted → healthy → the helper is called once per admin and state records `healthy`; (ii) a second healthy cycle does NOT call it again; (iii) a thrown check mints once, a second throw inside the cooldown mints nothing, a later healthy check acknowledges; (iv) fence: no `getActiveAlertId` remains. On staging after deploy: the unacknowledged `feed_health` count read before and after the first post-deploy healthy cycle (expected: 1,088 → 0 if no non-healthy grade intervenes).
3. **Measure before trusting it — a DISTRIBUTION, pre-registered.** r1's criterion ("zero warning/critical while the feed is flowing") was true by construction, because the grade IS the freshest age. Replaced with:
   - **What is recorded:** every auto-check cycle (5 min), per class, the freshest age and the grade — from a new per-cycle log line `[FeedIntegrity][liveness] class=… freshestAgeMs=… grade=… segment=…` (the existing summary line carries only the worst age across classes).
   - **Population:** one full weekday after deploy, every cycle, split by session segment — **regular** (13:30-20:00 UTC), **after-hours** (20:00-24:00), **overnight** (00:00-08:00), **pre-market** (08:00-13:30), and, if the window crosses one, **weekend-closed**. Crypto is graded in every segment. ⚠️ xStock in the **weekend-closed** segment is GATED (suppressed by `isXstockMarketOpenUTC`), not measured — reported as "suppressed, n cycles", never as a pass. 
   - **PASS:** per class, in every graded segment, the **maximum observed freshest age** stays below `warning_age_ms` with a stated margin (crypto 5,000 ms, xStock 60,000 ms, read 2026-10-06) — the report states the margin per segment (e.g. "overnight xStock max 4.2 s vs 60 s"). **FAIL:** any graded segment whose maximum reaches `warning_age_ms` without a matching real outage in the logs ⇒ the thresholds go back before 3a1 relies on them.
   - **Positive control:** the forced bad grade from objective 2's staging check (a test-only hook, never in production) must show `warning`/`critical` on the SAME per-cycle line, so the line is shown able to report a non-healthy grade before its healthy readings count.
   - **Instrument limits, stated:** `configWarnLogged` is one-shot per process (its silence proves nothing); `/var/log/dawntrader/out.log` rotates 6-8 times a day, so the window is read across the rotated files from the `pm_uptime` boundary of the deploy restart, and a restart inside the window is reported, not stitched over.
4. **Expose the per-class liveness for 3a1:** a read-only accessor (class → freshest age, grade). ⚠️ **This is FEED-LEVEL liveness** — it answers "is the class's feed flowing at all", the whole-feed failure 3a1 must still page on. It is NOT the per-symbol discriminator: telling a quiet symbol from a lost subscription needs the COHORT comparison designed in `PHASE_19_PLAN` 3b.f-d (*"feed-level silence cannot make that split"*), which 3a1 builds.
5. **GBP/USD:** census the recorder's subscription set against the engine's priced set; disposition any gap.
