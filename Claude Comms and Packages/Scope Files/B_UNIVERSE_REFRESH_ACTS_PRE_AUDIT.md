## 2.2 J6 — the completeness gate (OBJ-3)
- **Run 182 (2026-10-30T03:00:01.982Z):** 0 pairs, `noTicker=712`; would have dropped all 428. Run 183 rebuilt 481 from the empty cache.
- **Drop share** (dropped ÷ prior size, n = 203): median **0.1190**, p90 **0.1761**, max **0.2345** (110 / 469). Sizes ranged 301-527.
- **Symmetric-difference share** (|added| + |dropped|, ÷ prior size, same n = 203) — the A2(c) comparator's own population: median **0.2430**, p90 **0.3027**, p99 **0.3497**, max **0.3973**.
- **Why arm (a) as first written was a false instrument (§0 row 8):** one silently-empty batch removes ≈ 59 of ~469 symbols ≈ **0.126** drop share, indistinguishable from a median day by arm (b) and invisible to a "did it throw" arm (a). That partial silent outage is the event the gate exists for.
- **Gate arm (a) — "every fetch returned usable rows" (r3, Langston A1):** the loader returns one record per **fetch** `{ok, httpStatus, krakenError, rowsRequested, rowsReturned}` in `batches` — **the AssetPairs fetch first (`universe-loader.ts:195-197`), then each Ticker batch.** A fetch is OK only if `resp.ok` **and** Kraken's `error` array is empty **and** its `result` is non-empty (`rowsReturned > 0`) — the shape the loader already applies at `:369-371` and `:457-465` (`#546`); a throw inside a fetch is caught and recorded as a not-OK record, never propagated past the gate. **Zero Ticker batches is itself incomplete** (an AssetPairs that leaves no candidates cannot pass vacuously). Any record not OK ⇒ REFUSE (`refusal_reason = incomplete_fetch`). ⇒ an HTTP-200 AssetPairs error envelope — the AssetPairs form of run 182 — refuses at arm (a) before any candidate list exists.
- **Gate arm (b):** drop share against the **running** set > `crypto_spot.universe_refresh_max_drop_share` ⇒ REFUSE (`refusal_reason = drop_share`). Seed **0.30** = 1.28 × the worst observed one-day share and nothing more; DB-governed via `getCachedNumberRequired`, **no fallback** (absent ⇒ refuse).
- **The ratchet, and its exit (Langston C1; rewritten r3 per Langston A2).** A refusal leaves membership untouched, so the running set ages and the next measurement is a multi-day diff — more likely to breach. r2's exit ("the next complete run within 0.30 of the stored list is applied") let two degraded answers through: an empty list agrees with an empty stored list, and a confirmed apply was never re-bounded (469 → 324 → 227 = 0.52 of the running set in one apply, at `info`). **r3 rule, four parts:**
  - **(b) Non-degeneracy — what may be stored or confirm anything.** A computed list is **confirmable** only if it is non-empty **and** passes `assertClassifiedPlausible(running_count, computed_count)` (`universe-loader.ts:398`, already exported and called at `:536` — one home for the half-ratio, no new constant). A list that fails is REFUSED with `refusal_reason = degenerate` and recorded `confirmable = false`; it is never a confirmation baseline. ★ The harm guarded is drops: when the running set is itself near-empty there is nothing to drop, so the ratio admits a small list there by construction.
  - **(c) The comparator — named, with its own knob.** Confirmation compares the new confirmable list C_new against the **last confirmable stored list** C_stored by the **symmetric-difference share** `|C_new Δ C_stored| / |C_stored|` (denominator > 0, guaranteed by (b)). Threshold: `crypto_spot.universe_refresh_confirm_max_diff_share`, `getCachedNumberRequired`, no fallback (absent ⇒ refuse). **Seed 0.50 = 1.26 × the worst observed one-day symmetric difference (0.3973, §2.2 population)** — the same principle as 0.30 = 1.28 × for arm (b). Within the threshold ⇒ confirmed. **The confirmed drop set is only the symbols absent from BOTH complete answers**; a symbol missed by one answer only is kept.
  - **Bounded apply.** Each confirmed apply drops at most `max_drop_share × |running set|` symbols — the same arm-(b) knob, re-applied to the confirmed set — taking the **lowest 24 h USD volume first, symbols with no ticker first of all** (the loader gains a `volumeUsdBySymbol` field; no caller changes). Pins (§2.6) are never dropped. Adds are applied in full (adds are ungated). The remainder of the confirmed drop set waits: **each next complete run that again confirms against the prior confirmable list applies another bounded step**, so a genuine large drop steps down over several days and never moves more than 0.30 of the running set in one apply. Walk (non-degenerate, no adds, both lists inside the running set): 469 running; day 1 C_stored = 324 (refused by arm (b), 145 / 469 = 0.309); day 2 C_new = 300 ⊂ C_stored, Δ share 24 / 324 = 0.074 ≤ 0.50 ⇒ confirmed. Drop set = running minus (C_stored ∪ C_new) = 145 (the 24 missed only by day 2 are kept). Apply drops 140 (⌊0.30 × 469⌋), lowest volume first ⇒ 329 running; the remaining 5 wait for the next agreeing run (bound ⌊0.30 × 329⌋ = 98).
  - **Langston's A2 case, 469 → 324 → 227, under r3:** 324 passes (b) (≥ ⌈469 / 2⌉ = 235) and is refused by arm (b) (drop share ≥ 145 / 469 = 0.31), stored confirmable. **227 fails (b) against the running 469 (227 < 235) ⇒ `degenerate`, not stored, confirms nothing.** The 0.52 one-step apply is unreachable twice over: (b) blocks the list and the bounded apply caps any confirmed step at 0.30.
  - **A genuine one-day loss of more than half the universe is held for a human — the loader's own contract.** `assertClassifiedPlausible`'s docstring (`:383-397`) already rules that a halving is venue news the operator confirms, and its perp caller threads a deliberate override (`acceptImplosion`, `:528-537`, from `--confirm-delisting`). **Proposed operator path, for Langston to rule (the attack point of r3):** membership lives inside the app process, so a standalone CLI cannot apply a list itself. Instead `npm run crypto-universe-refresh-confirm -- --occurrence <id> --by <actor>` (actor from `ALERT_ACTORS`) writes `operator_confirmed_by` / `operator_confirmed_at` onto that one refused `degenerate` run row. The next in-app run may use **that row only** as its baseline, and a new list that is complete under arm (a) and agrees with it under (c) is confirmable **for that one occurrence** although it too fails (b) — non-degeneracy is waived for that pair, nothing else is, and the apply is **still bounded by 0.30**, so a confirmed halving steps down over several runs (a later step needs a fresh confirmation while the list stays below half the running set). One occurrence per confirmation; the row records who confirmed. **Alternative, if Langston prefers no new surface:** no operator path in this batch; a > 50 % loss stays held under the rung-3 page and the residual is named in the completion report with a placed home. Restarting the app is neither path and is not recovery. **RULED (Langston, `1574123287120846969`): the alternative. No operator path in this batch** — see the Step-2 PROCEED line at the top for the three carries.
  - **(d) The counter holds across a confirmation.** `consecutive_refusals` increments on `refused` **and** on `applied_confirmed`; it resets only on `applied` (within arm (b) against the running set) or `noop`. ⇒ a refuse / confirm cycle climbs to critical by its third run instead of resetting at `info`, and a genuine large drop stepping down over several days pages critical while it does. That page is intended: a real universe change that big is an event the crew should see.
  - **Walk of Langston's A2(i) case under r3:** the AssetPairs empty envelope refuses at arm (a) (row 11). A truncated-but-HTTP-OK AssetPairs that passes arm (a) yields a computed list far below half the running set ⇒ `degenerate`, never stored as confirmable ⇒ rung 1, rung 2, rung 3 on consecutive days, and it never applies. A missed occurrence (J9, §2.8 — past 4 h it never runs) widens both baselines the same way and exits the same way.
- **Escalation — the rung is in the dedupe key (r3, Langston A3).** r2's single key could not escalate: `addAlert` returns an existing non-resolved row with the same key unchanged (`system-alerts.ts:577-594`). **Rule:** at `consecutive_refusals` 1, 2 and ≥ 3 the refresh mints `crypto-universe-refresh-rung-1` (`info`), `-rung-2` (`warning`), `-rung-3` (`critical`) — each a fresh key, so each mints; the body carries `consecutive_refusals`, `running_set_age_hours`, the refusal reason and the occurrence id. Rung 3 stays open while refusals continue (its dedupe holds it to one row); its body points at `crypto_universe_refresh_runs` for the live count rather than claiming one. **On `applied` or `noop`** the open rungs are resolved by `resolveAlertsByDedupePrefix('crypto-universe-refresh-rung-')` (`system-alerts.ts:924`) with evidence = that occurrence id; resolved rows leave the dedupe check, so the next episode re-mints rung 1. In-repo precedent for the rung-in-key shape: `deploy-drift-rung-<N>` (`dt-deploy-drift.sh:894`, prefix swept at `:645`, `:654`). The prefix is added to the alert owner table (owner CC-A) at P7. Two consecutive arm-(b) refusals still mean two complete answers that disagree with each other, not a one-off.
- **Recovery is not "restart the app":** a restart reconnects every shard — the watchdog's own alarm instrument (scope F3) — and rebuilds from an ungated boot load. The confirmation rule above is the recovery; no operator step is needed.
- **The first refresh after a long uptime is not measurable in advance:** the running set dates from the last process start. ⇒ **the Step-6 deploy is timed just before a 03:00Z run**, so the first diff is one day's. **Order against the other open windows (Langston 2026-11-22, Discord 1574115300243279906 point 2):** B-ENTRY-GATE runs to 11-23T21:00Z; NEW Claude's post-window deploy (B-PRICE-FEED-COVERAGE OBJ-5 + B-AI-BRIEF-OFF) then needs 25 h of uptime, to ≈ 11-24T22:00Z. ⇒ **this batch's Step-6 deploy goes after that read, at the first 02:30-02:55Z slot after it (earliest 11-25), or folds into NEW Claude's sha if Steps 3-5 finish first — agreed with NEW Claude in `#general` before deploying.** Every other open DEPLOY_WINDOWS row is closed or named `--in-window` in the deploy turn.

## 2.3 J5 — warm handling for added symbols: MANDATORY
- **Add share against the running set:** median 0.1211 (against the new size), p90 0.1614, max 0.2639; **against the prior running set the worst case is 123 / 365 = 0.337.**
- If every add lands in one shard and none has ticked, that shard's live share is at worst (300 − adds) × 0.93 / 300; with 183 adds into one 300-slot shard that is **0.567 < floor 0.60** ⇒ a false page is reachable. (0.93 = the lowest live share Langston measured over `#1232`'s first 48 h.)
- **Rule:** an added symbol is excluded from its shard's denominator until its first update **or** one `recorder_live_window_ms` after its subscribe confirmation, whichever is first. Uses the existing window constant; **no new constant.** The process-level warm clock is unchanged. (0.567 rests on Langston's carried 0.93 figure — PLAUSIBLE, not confirmed; J5 is mandatory on the 123 / 365 = 0.337 ratio alone.)
- **Small denominators (Langston C3 i).** The grace rule shrinks the gradable list, and it can get small: a brand-new shard starts with every symbol in grace, so "2 gradable, 1 quiet" would grade critical. n cannot be proven large, so: **a shard whose graced symbols outnumber its gradable symbols is not graded that tick** (this includes n = 0). The suppression is bounded: a graced symbol leaves grace at its first update or one window after confirmation, then counts with its real age (`null` if it never ticked). ⇒ a dead shard is still graded critical at most one `recorder_live_window_ms` later. A ratio of the shard's own counts, not a tunable.

## 2.4 J3 — how membership changes on the wire: incremental subscribe / unsubscribe
- **Never `forceReconnect`** — it is the watchdog's alarm instrument (scope J3, F3).
- **Order:** mutate `shard.symbols` and `symbolShard` FIRST, then send. If the socket is not OPEN, skip the send — the next `onOpen` replays the mutated `shard.symbols`.
- **Unsubscribe replies** get their own branch and counters, so they count neither against `expectedSubscribeReplies` nor as a `subscribeRejected`.
- **Shard stability (a stated departure from hash-mod):** existing symbols stay in their shard; an add goes to the least-full shard under the shard size; a new shard opens only when all are full; a shard emptied by drops is stopped. ⇒ no add ever re-homes an existing symbol. Langston C3: the add side self-levels; a third shard needs > 600 symbols against an observed max of 527.
- **Incremental subscribe accounting (Langston C2).** Today `subscribeOk` / `subscribeRejected` reset at open (`recorder-connection.ts:218-219`) and are read by the open-time reply timer (`:414-416`) and the `forceReconnect` log line (`:289`); that timer is armed only in `ws.on('open')` (`:222`) and captures `expectedSubscribeReplies()` once (`:407`). An incremental add arriving after it has fired would write into counters nobody reads again — the `#1232` failure re-opened on a new path. The feed alarm cannot cover it: after grace a dead add costs ≤ 1/300 = **0.0033** of a shard against a 0.40 margin. **Rule:** each incremental subscribe carries its own `req_id` (distinct from the open-time subscribe) and is tracked in a per-connection `pendingAdds` map (symbol → sentAtMs). Replies are routed by `req_id`, so they never touch the open-time accounting. On success the symbol leaves `pendingAdds` and its grace clock starts. **On rejection, or no reply within the existing `subscribeReplyTimeoutMs`, the symbol is removed from `shard.symbols`, `symbolShard` and the age maps** (never a permanent null) and recorded as `rejected_adds` / `unconfirmed_adds` in the run record with one log line. **No `forceReconnect`.** The next refresh re-adds it if it still qualifies. Whether Kraken v2 echoes `req_id` on subscribe and unsubscribe replies is owed to the P12 wire check; if it does not, routing falls back to `result.symbol` and a symbol-less reply while `pendingAdds` is non-empty is recorded as unattributable.

## 2.5 J4 — pruning a dropped symbol
Prune `shard.symbols`, `symbolShard` **and** `lastTickerUpdateAt` (keyed by symbol only — a re-added symbol would otherwise carry a stale age). Guard the ticker write with `symbolShard.has(symbol)` so a late message for a dropped symbol does not re-create its age.

## 2.9 Shard identity (Langston C3 ii)

## PLAIN-LANGUAGE SUMMARY

Every day the system works out which coins are worth recording, and today nothing uses that answer. This plan makes the running recorder add and drop coins live, one at a time, without the full reconnect the feed watchdog treats as an alarm. It never drops a coin we hold. It refuses to apply a list that came back incomplete or shrank by more than 30 %. "Incomplete" now means any part of the price lookup that came back empty or with an error, not only one that crashed, because on October 30 the lookup failed quietly and nothing crashed. If a big drop is real, the next day's answer will agree with it, and the drop is then applied in steps of no more than 30 % a day, quietest coins first. An answer that loses more than half the coins at once is never applied on its own: it pages the crew and is held. Langston ruled that this batch adds no way for a person to wave it through: it has never happened in 206 days of logs, the held state is loud and safe, and a confirmation button is proposed to Kyle as its own item for the day it first happens. The alert climbs from information to warning to critical on consecutive refusals, and it does not quietly reset while a large drop is still working through. A coin the exchange refuses to send is simply dropped and retried the next day, without a reconnect. And it gives each newly added coin a short grace period before the feed alarm counts it, because on the worst day in the log enough coins were added at once to trip a false alarm. The job moves into the app's own scheduler, the old standalone script is retired, and every run leaves a record of what changed.
