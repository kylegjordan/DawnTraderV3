## 5. JUDGEMENT CALLS FOR ATTACK
1. **Descriptions in a separate file keyed by batch id rather than a §4 column.** A column breaks the checker's strict parse on every edit. The keyed file is a second document, but it holds words, not state, and a missing key shows on the page.
2. **The plan's status cell, and a new `waiting on` column, as the status.** Both are typed by the owning session, which is the GitHub board's weakness. The difference: the plan is already graded at batch close by `gov-planline`, there is one copy of each fact, and the page shows the last recorded step beside it, so a stale cell is visible rather than silent. `waiting on` is new upkeep for the sessions, kept to the pre-sprint items, where Kyle reads NOW and NEXT.
3. **The checker as the writer.** No new timer, and it already reads the plan at the graded ref. The writer runs last in the tick and is wrapped so a failure cannot stop the gate's rules. It deploys by the checker's own auto-redeploy, outside `dt-deploy` and any app deploy hold; the page deploys with the app.
4. **Hosting inside the app rather than a static page.** The app already has a login; a static file served by Caddy would need its own.
5. **Replacing the §0a prose table with a strict table in one batch.** It is the only way the board, the census and the plan-state check read one list. The risk is a lossy migration; the both-directions census in OBJ-1 is the guard.
