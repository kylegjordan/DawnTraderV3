## 3. Plain-language summary

The audit found more held in memory than the scope assumed. The hourly job also rebuilds the tracking page's figures. To do that it loads a second copy of the list of dead tokens and a 321 MB name lookup, only to find names for 100 tokens. The file times from the September kill put the crash about 10 seconds into that step. That is a strong lead, but not yet the answer. The scratch measurement is still the test.

It also found that for the job's last three days in September it was not observing tokens at all. It was skipping every check, because the month's paid allowance had run out, even though these checks cost nothing. So the September crash had nothing to do with response sizes.

Two larger problems come with switching the job back on. Token launches now run at about twice the planned rate, so each hourly run takes 45 minutes or more. That is longer than the 30 minutes after which another job may take its lock, so the lock fix is needed for normal running, not just catch-up. And the page's figures have two writers that would overlap every hour.

Finally, the September and October spending logs have not been fully counted yet, so they cannot be moved off the box until that is done.

The plan:
1. Measure the September crash and the switched-on job separately, in a sealed copy with no network access.
2. Fix whatever that measurement names.
3. Give the lock a heartbeat.
4. Record a check that fails instead of dropping it.
5. Give the page one writer and show "not instrumented" rather than false survivors.
6. Count the unread backlog before moving past it.
7. Finish counting the old spending logs, then archive them.
8. List every archive version in the off-site store.
9. Switch the job back on and watch it for a week, including whether it keeps up.
