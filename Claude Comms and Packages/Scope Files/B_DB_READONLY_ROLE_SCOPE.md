## 0. What this batch is for, in one paragraph

Today every hand read of the staging database (`dt-sql`, and through it the reviewers' staging-parity check) logs in as the app's own `postgres` login, which can write. "Read-only" is a session setting dt-sql asks for, plus a refusal of SQL that names that setting — an accident guard, stated as such in dt-sql's own docstring (`comms-infra/staging/dt-sql:44-49`): *"A read-only database role is the boundary (proposed to Kyle, not built here)."* This batch builds that boundary: a separate login that the database itself refuses to let write, held in its own server-side file, which dt-sql uses instead of the app's login. The close condition, verbatim from its one home, `B_DB_READ_TOOL_COMPLETION_REPORT.md:18` (the parent's open-at-close row): **"a write through dt-sql is refused by the role, not by a session setting."** The plan row (`SPRINT_TO_LIVE_PLAN.md` row 5a1) states the same substance in its own words: *"refused by the database itself rather than by a setting"*. *(r1 attributed the first sentence to the plan row — wrong; corrected r2, C1.)*

## 2. Architectural read (1.a)

**System Impact Map, "Crew database reads" row (`SYSTEM_IMPACT_MAP.md:1392`), re-read 2026-11-22:** upstream = the app's `.env` `DATABASE_URL` (read at run time, decoded, never copied), `/usr/bin/psql`, `/var/lib/dt-sql`, the alert CLI; the Supabase direct endpoint and its ban. Downstream = every session's and reviewer's hand reads, and through the wrapper every `psql` helper on the box (~48). Blast radius of a stuck LOCKED: no hand reads, trading unaffected. **NEW blast radius after this batch (C3-iii):** a missing, unreadable or stale reader credential removes **all** hand database reads, with no fallback — including the instrument the crew would use to diagnose the database itself. Trading is still unaffected. Recovery needs root on staging (reviewers and the `deploy` class cannot do it); **recovery owner: Infra Claude**, by the OBJ-7 runbook, which any root-reaching session can follow. The branch is exercised live (OBJ-4). **This batch changes the upstream credential source** (a new file instead of `.env`) and adds a new upstream object (the role). The "never copied — so a rotation reaches this at once" property (dt-sql:125) is deliberately given up for the reader credential: it is its own credential with its own rotation (OBJ-7).

**System Manual, "Crew Database Reads — `B-DB-READ-TOOL`" (`SYSTEM_MANUAL.md:8616`), re-read 2026-11-22:** describes read-only as an accident guard and the credential as the app's login. Both statements become false at Step 6 and are rewritten in OBJ-8.

**Measured 2026-11-22 through dt-sql (one call, stdin), object = the staging Supabase database, PostgreSQL 17.6:**
- the app login `postgres`: `rolsuper f · rolcreaterole t · rolbypassrls t · rolinherit t`;
- `postgres` is a member of `pg_read_all_data`, `pg_monitor`, `pg_signal_backend`, `pg_create_subscription`, `anon`, `authenticated`, `authenticator`, `service_role` — each **with admin option** — and of `supabase_privileged_role` without;
- row-level security is enabled on **0 of 641** tables in `public`;
- the endpoint dt-sql uses is the **direct** endpoint (`db.<project>.supabase.co:5432`), not the pooler — so a new role logs in under its plain name, with no pooler username suffix.
- ⇒ **Hypothesis for Step 2, NOT RE-READ:** `postgres` can `CREATE ROLE` and grant `pg_read_all_data` to it. RLS bypass is moot today (no table uses RLS) but the role is created without it anyway.

## 4. Open questions for Step 2 (the audit answers these before any plan)

1. **Can `postgres` on Supabase create the role and grant `pg_read_all_data`?** Measure (a harmless check of privileges, not a trial create).
2. **What does the role need beyond `pg_read_all_data`?** Census the crew's real reads (dt-sql log, the reviewer probe, `pg_stat_activity` reads) — e.g. whether `pg_read_all_stats` is needed to see other sessions' query text.
3. **What can PUBLIC still do?** `TEMP` on the database, `CREATE` on `public`, `EXECUTE` on functions (any that write, including `SECURITY DEFINER` ones), sequences. Each becomes either a refusal or a stated residual in OBJ-2.
4. **How the password is set without plaintext in a log** — `password_encryption`, `log_statement` on Supabase; SCRAM verifier vs plaintext.
5. **Where the credential file lives and who reads it** — the dt-api shape (locked account, 0600, narrow sudo) proposed in OBJ-3 vs `root:deploy 0640` argued against that precedent; directory mode; how reviewers (who reach staging as `deploy`) call dt-sql under it.
9. **The OBJ-9 instrument's form** — a dt-sql one-shot mode kept off the production path, or INTENT written by the setup script.
6. **Who runs the one-time setup and with what login** — the app's login, once, as a reviewed script (recommended), vs a migration (rejected unless Step 2 finds a reason: the app's migrations run on every deploy and must not carry crew credentials).
7. **The no-fallback design** — dt-sql refuses when the file is absent; what the lock does in that case (no login was attempted, so no lock).
8. **A live proof without a production bypass** for OBJ-5.
