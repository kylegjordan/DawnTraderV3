## Objective
Add a **per-signal maker-vs-taker entry decision** so the system can enter the cheaper way (post-only ~0.40% maker, capturing the spread) instead of always crossing (~0.80% taker), **and have that choice actually open crypto** — which today is mathematically un-openable because at the ~1.6–1.8% taker round-trip fee wall the Net-Expectancy gate honestly refuses every crypto signal (rung-1 per-class target-floor confirmed this; the maker build is the real opener). Shared by the active path AND VTS. The hard part is **doing it safely with ZERO live passive-fill history** — so the conservatism lives in one calibratable parameter, not in crippling the pipeline.

## The architecture (Kyle's reframe — the load-bearing decision)
**Compute a BEST-OF-BOTH maker/taker EV comparison EARLY — at/just-after signal generation, BEFORE the SQE — snapshot it onto the signal (the same way `diAtQueue`/`dbsScoreAtQueue` are snapshotted at RTB-insert), and let the BEST option (max of taker-EV and haircut-adjusted maker-EV) flow through ALL the downstream EV consumers.** This is the ONLY placement that opens crypto: every gate that can reject crypto sits UPSTREAM of the entry, so a decision placed at execution (v1) can never change what those gates reject — a taker-unprofitable / maker-profitable signal (the crypto opener) is killed before the maker economics are ever seen. **The ACCURATE pipeline (re-verified vs code + the 3-way Active-Trading-Path-Audit — corrects an earlier mis-statement):** scan → signal-gen (with an inline `[HF9]` Net-EV filter, `signal-orchestrator.ts:2144`, REAL DI) → SQE (its own regime-aware ROI floor, taker fee) → RTB insert (snapshots the at-queue EV inputs) → **TCL = a MECHANICAL slot-promoter** (`paper-execution-engine.checkRtbPromotion:1719` — count open slots, sort the RTB by rank, promote the top; NOT a quality gate, NOT a decider) → **OPEN PATH (Stage F)** where the **`[11.8B]` Net-Expectancy gate runs on the AT-QUEUE SNAPSHOT** (`executeSimulatedTrade:2035-2077`, defaulted/queue-time inputs) — F1 guardrail → F2 EV gate (THE crypto blocker) → F3 sizing → F4 classify → F5 depth → F6 fill → F8 insert. **There is NO separate EV calc between TCL-promote and open, and NOTHING in the open path re-evaluates current prices** (the EV gate is part of the open sequence, on the snapshot). So the best-of-both EV consumers are: the inline `[HF9]` gen-filter + the SQE ROI floor + the `[11.8B]` open-gate + the B7.1 RTB ranker — all read the SAME snapshotted best-of-both value. **Single-source it (reuse-over-recompute, B7.1 principle):** computed ONCE at gen, never recomputed per consumer.

## Objectives
**OBJ-1 — per-signal best-of-both EV, computed early, single-sourced.** At/just-after signal generation compute taker-EV AND maker-EV; attach both + the chosen best (max) to the signal; the chosen best is the single value all downstream consumers read. **Use-what-exists:** maker economics reuse the existing maker-aware scaffolding — `slippage-fee-model.calculateFees(isMaker, …)`, `getFrictionForAssetClass().feeRateMaker` (DB-carried, comment `cost-model.ts:38-40` placed it for exactly this flip), `pre-execution-validator`'s fee-mode resolve. Maker-EV = the kernel's EV machinery run with: the maker fee, spread-CAPTURE (a credit, not a debit), ~0 slippage, MINUS the OBJ-2 adverse-selection haircut, MINUS the OBJ-2 non-fill term. Net Expectancy / R-multiple semantics preserved (B7.1).

**OBJ-2 — the signal-conditioned adverse-selection haircut (the one conservatism knob) + the hard floor.** A pessimistic haircut on maker-EV with: **A** (adverse selection) **monotonically increasing in signal strength** — a predictive signal adversely-selects its own passive fills (we fill only when the market hasn't moved our way), so stronger signal → bigger haircut; and **C** (non-fill / alpha-decay cost) **increasing as the signal's half-life shortens**. This makes urgency ENDOGENOUS (strong+fast → big haircut → taker wins; patient/reversal → small → maker wins — the survey's prescription). On TOP, a dumb **hard guardrail FLOOR** (strength ≥ X AND half-life ≤ Y → taker, full stop) as an independent, auditable backstop against a miscalibrated prior (defense-in-depth, one decision path + one floor — NOT "EV-unless-override"). **★ Default is ASYMMETRICALLY pessimistic — biased so errors fall toward UNDER-firing maker** (under-fire = miss some opens = opportunity cost; over-fire = float phantom maker-only opportunities to the top of the ranker = pollute B7.1's selection/IC learning, which paper mode does NOT protect against). DB-governed (`module_constants`), fail-hard, **PER-ASSET-CLASS — NOT a wildcard constant** (maker/taker fill + spread dynamics differ enough crypto vs xStock that one global haircut is a placeholder, not a solution — Langston Step-1, §8 #11), **start deliberately TIGHT** (it's an uncalibrated guess until Phase-21). **★ This is Kyle's one open dial: how conservative the haircut starts.**

**OBJ-3 — the snapshotted best-of-both flows through EVERY EV consumer + the SINGLE-CONSISTENT-NUMBER invariant (with a NAMED TEST).** The four EV consumers all read the SAME snapshotted best-of-both value: the inline `[HF9]` gen-filter (`signal-orchestrator.ts:2144`), the SQE ROI floor, the `[11.8B]` open-gate (`executeSimulatedTrade:2035-2077`, which reads it from the at-queue snapshot like `diAtQueue`), and B7.1's RTB R-multiple ranker — so maker-openers survive all the gates AND the ranking reflects the real opportunity. **INVARIANT:** the SAME haircut-adjusted maker-EV (never a raw, un-haircut maker-EV) reaches all four — that single-consistent-number is what makes ONE haircut protect selection AND ranking simultaneously (Langston's note: assert the IDENTITY of the value as it flows, not three independent recomputations that happen to agree). **A named test that FAILS when a raw (un-haircut) maker-EV reaches the ranker is a deliverable** (Langston Step-1 gate), not just an asserted invariant. **★ Two EV evaluations now live on DIFFERENT data bases and must NOT be conflated (Langston):** the snapshotted haircut-adjusted maker-EV here (the single-number invariant, computed once at gen) vs OBJ-4's convert-safety "current taker-EV" (a deliberately SEPARATE, deliberately-CURRENT recompute in the RTB refresh). They are ALLOWED to differ — that difference IS the point of convert-safety — so the invariant test asserts the snapshot's identity-as-it-flows WITHOUT accidentally binding the refresh's current-data recompute to it.

**OBJ-4 — the make-then-take ladder + CONVERT-SAFETY, HOSTED IN THE RTB REFRESH (Kyle's direction — reuse-what-exists).** **★ Placement (corrected from an earlier wrong draft): the maker/taker DECISION is at signal-generation (OBJ-1); the maker-pending WAIT and the CONVERT-SAFETY re-check live in the RTB REFRESH, NOT a new fill-step routine, and NOT the TCL.** Rationale: the RTB refresh (`refreshSingleSignal`, `ready_to_buy_service.ts:742`, a 30s Central-Clock loop) ALREADY re-evaluates each QUEUED signal on CURRENT market data — it pulls current spread/vol (`getCachedSpread`/`getVolatility`), recomputes the cost-adjusted net edge (`computeNetGeometry`), re-validates SQE, and can EXPIRE or RECONFIRM. That is exactly the "re-check on current data → keep/convert/drop" operation convert-safety needs, so we REUSE it rather than add a new current-price evaluation at the fill step (the open path has no current-price re-eval to reuse — the `[11.8B]` gate runs on the at-queue snapshot). It is also async/non-blocking by construction (the refresh is its own loop, separate from the promotion cycle). **Model:** a posted-but-unfilled maker order is a signal that stays RTB-QUEUE-RESIDENT in a `maker_pending` state; each 30s refresh tick (a) applies the HONEST fill check — did the price actually TRADE THROUGH the limit since posting? if yes → it fills (promote/open as maker) — never optimistically marked; and (b) on time-budget expiry runs CONVERT-SAFETY → if the current taker-EV > 0, flip the signal to taker-mode, else EXPIRE it. One rule: taker-profitable signals convert; maker-only signals expire rather than open a guaranteed loser.
**★★ MUST-FIX — convert-safety's "taker-EV" MUST be the netEV KERNEL value, NOT the refresh's native `computeNetGeometry` (CC-A landmine — a silent field-name collision):** the refresh natively computes `computeNetGeometry` whose output field `netRewardToRisk` (`cost-model.ts:224`) is a GROSS reward:risk net-of-cost with NO pWin — a DIFFERENT quantity from the **netEV kernel's** `netRewardToRisk` (`net-expectancy-kernel.ts:117`, the pWin-WEIGHTED expected R-multiple) that the `[11.8B]` gate AND the B7.1 ranker use. The names are identical, so grabbing the refresh's value-sitting-right-there would run the convert decision on gross-edge while selection/gate run on pWin-weighted netEV — they can DISAGREE (positive gross, negative pWin-weighted) and convert into a trade the ranker would never pick. **HARD REQUIREMENT: single-source the EV — convert-safety calls the netEV KERNEL on FRESH current inputs (spread/mid/friction recomputed at convert time, not a cached plan-time snapshot); best-of-both (OBJ-1) + the ranker + convert-safety are ALL defined in KERNEL-netEV terms; a test asserts convert-EV == the gate's kernel-netEV for the same inputs (NOT == `computeNetGeometry`).** The honest-fill trade-through check is genuinely **NET-NEW logic in the refresh** (not a reuse of `computeNetGeometry`) — flagged so Step-4 scopes it correctly.
**★ MUST-FIX — CONVERT→OPEN-GATE SNAPSHOT RE-STAMP (Langston Step-1, a real split-brain):** a maker-opener is BY CONSTRUCTION a signal whose AT-QUEUE taker-EV was NEGATIVE (that's the only reason maker was needed to open it). When convert-safety flips it to taker and it later promotes to Stage F2, the `[11.8B]` open-gate reads the AT-QUEUE SNAPSHOT taker-EV — the STALE NEGATIVE value — and KILLS the exact signal convert-safety just approved (the crypto-blocker rebuilt one stage downstream; the convert branch is mathematically un-openable without this). **So the convert path MUST RE-STAMP the signal's snapshot EV inputs with the CURRENT values it used** (the refresh already holds them), so F2 honors the convert decision instead of overruling it on stale data. Named in the verification criteria.
**★ SLOT/CAPITAL semantics (Langston + CC-A Step-1 — settled for paper):** `maker_pending` stays POOL-RESIDENT + **SLOT-FREE while WAITING**, but **SLOT-CHECKED AT FILL** — a fill must ACQUIRE a free slot or DEFER (cannot exceed `maxTrades` if several `maker_pending` fill the same tick). **MUTUAL EXCLUSION (explicit in the state model):** a `maker_pending` signal is NOT promotable-to-open while pending — it cannot simultaneously hold a pending post AND compete for a slot through the ranker (double-count). In LIVE (Phase-21) a real resting limit order TIES UP capital/buying-power, so it must count against exposure/capacity (a resting-order budget), NOT be free — the Phase-21 delta. The DECISION logic stays in this same place either way; only the slot/capital accounting + order-placement mechanics differ. **REAL Kraken post-only resting-order lifecycle (place/reprice/timeout/cancel on the exchange) = Phase-21**, a named §13 home.

**OBJ-5 — #330 reconcile: consolidate the two fee-source paths to ONE resolver.** Today the EV gate (`getCachedCostMetrics`) and the fill (`getFrictionForAssetClass`) are two code paths to one DB `fee_model` fact (both taker). Consolidate to one resolver so the maker/taker decision has a single fee source — a CONSOLIDATION, not a redesign (layering a maker/taker tier on an unreconciled fee path is a split-brain). Resolves RUNNING_ISSUES #330.

**OBJ-6 — telemetry + the DATA FENCE (the Phase-25 calibration substrate).** Capture the maker/taker decision (chosen mode, taker-EV, haircut-adjusted maker-EV, the haircut components A/C, the floor-fired flag) + the realized fill outcome in the shadow/telemetry layer (extend B7.1's `selection-ic` / reorg-B4 shadow). **★ TAG paper maker-fill rows as NON-CALIBRATION** — synthetic model-vs-model fills CANNOT train the A haircut (circular); A calibrates ONLY on Phase-21 live passive fills. The Phase-21→Phase-25 calibration dependency is explicit.
