## 0. WHY (measured; `#1259` holds the full record)
- **Supabase bans an address after two wrong passwords in a row** (Supabase troubleshooting, *"Connection refused when trying to connect"*; ~30 min, ours lasted ~60).
- **The trigger was ours:** Langston's session `3113524e` ran `psql` ON STAGING twice (results 04:20:12Z and 04:20:29Z) with the password cut out of `.env` by `sed`. The stored URL's password is **percent-encoded** (one `%40` escape; 18 bytes encoded, 16 decoded — Langston's re-derivation), so `sed` sent the encoded form. **Each call printed the failure twice.** ⚠️ **A doubled CLIENT line is not a server-side count** (A-3): the attempt count per call is measured separately, against a local listener that counts TCP connections — `sslmode=prefer` 2, `sslmode=require` 1 (pre-audit A1) — so "two attempts per call" is a libpq behaviour measured locally, and "four wrong passwords" is two calls times that, never measured against Supabase's own counter. The app's first refused connection came 11 s after the second call; ~60 min of no database for the whole app (no paper entries, exit checks not running, up to 132,466 archive rows dropped).
- **There is no governed way to read the database from staging.** `workflow-07-verify-cc` says *"psql to Supabase"* and nothing more; sessions improvise. Of the 18 helper scripts in `/home/deploy`, two reach the database (`w166b-pgq.py`, `pgq_pooler.py`), both through `psql` with a correct `unquote` — the 11-16 failure came from a hand-built login outside any helper. `dt-api` (B-CREDENTIALS-PRIVATE-REPO OBJ-1, `#1023`) is the existing pattern for the web API; there is none for the database.
- **Why each `psql` call tries twice:** the host resolves to exactly ONE address (IPv6 only, no A record), so the multi-address candidate is excluded; the URL carries no `sslmode`, so libpq's default `prefer` is in force, and it retries WITHOUT SSL after a failed SSL attempt (measured: pre-audit A1).

## 1. PROVENANCE AND DISPOSITIONS
- **Tier 2 — `dt-api`** (`comms-infra/staging/dt-api`, B-CREDENTIALS-PRIVATE-REPO OBJ-1): read only, as the PATTERN (one command, a held credential, exit codes, a stated accident-guard-not-boundary). **Disposition (1): relevant and correct, unchanged.**
- **Tier 2 — the app's `.env` `DATABASE_URL`** (`/home/deploy/dawntrader/.env`, `deploy` 0600): read at run time, never copied. Unchanged.
- **Tier 2 — the helpers in `/home/deploy`** (Langston's census, top-level `*.py|*.sh|*.mjs|*.js|*.ts`: **88 files, 51 call `psql`**; 2 set `PGPASSWORD` from a decoded URL — `w166b-pgq.py` (mine), `pgq_pooler.py`; **48 pass the whole `$DATABASE_URL`**, most of them Langston's `lang_*.sh`). All 51 use libpq's default `sslmode=prefer` ⇒ **each is a two-attempts-per-call client on a failure**; they send the right password today, but **a password rotation makes any one of them, or any cron, a ban in a single call.** Disposition: OBJ-7. My own `w166b-pgq.py` is **deleted on the spot at Step 3** (rule 18), logged in `DELETED_COMPONENTS_LOG`.

| **OBJ-3** | **Fail-closed lockout, written BEFORE the attempt (A-1).** Inside the serialising lock it first writes an INTENT record (time, caller); it clears it ONLY on a clean success. A call killed between connect and record (timeout, signal, OOM, a dropped session) leaves the intent behind, and **the next call treats a left-over intent as LOCKED.** Outcomes: clean success → intent cleared; `password authentication failed` / `no pg_hba.conf entry` (28P01/28000) → LOCKED + critical page, exit 4; `Connection refused` (the ban's symptom) → exit 3 *"the address may be banned — do not retry"*, intent cleared (no password was judged); **timeout, signal death, or any non-zero exit not parsed above → LOCKED** (exit 4, ambiguous = failed). Every later call refuses until `dt-sql --unlock --by <actor>`. | Tests with a fake `psql` for every outcome, including a SIGKILL mid-call leaving the intent; the second of two queued callers refuses. **No live wrong-password test against Supabase — the one-attempt guarantee rests on libpq semantics plus the local listener; live silence is never evidence for it (#661 leg 3).** |
| **OBJ-4** | **Read-only by default:** `PGOPTIONS` sets `default_transaction_read_only=on` and a `statement_timeout`; SQL that tries to switch read-only off is refused. **Stated as an accident guard, not a boundary** (the password is the superuser's; `deploy` can read `.env`). A read-only database role is the boundary — named as a follow-on proposal for Kyle, not built here. | A write (`CREATE TEMP TABLE` / `INSERT`) refuses live with SQLSTATE 25006; a `SET default_transaction_read_only = off` is refused before connecting. |
