## 0. What is there
- **The verifier** (`server/services/cron-fire-evidence-verifier.ts`, B-NEW-49 / B-NEW-51), started once from `server/index.ts:1534-1535`, runs `runVerification()` every 15 min on its own `setInterval` (`:271-285`). `queryLastFires` (`:72-107`) pre-fills every registered job with `null`, runs an unfiltered `SELECT task_name, MAX(fired_at) … GROUP BY task_name`, and **on any error logs `[CRON-FIRE-VERIFIER][QUERY_FAIL]` and returns the nulls** (`:99-106`) under the comment *"verifier silently skips this run rather than alerting spuriously on a DB hiccup."* `runVerification` cannot tell a failed read from an empty one (`:137`) and pages every job whose last occurrence is past the 10-min latency grace as `no_fires_ever` (`:181`, `:192-203`); 5-minute jobs are always inside the grace.
- **Measured (`#1211`):** the same four hourly-to-daily jobs paged together seven times (2026-08-07 → 10-17); the 10-17 14:28:21Z and 10-10 00:41:30Z sets each sit at a logged `QUERY_FAIL` second. Langston re-derived the mechanism at the ref and that each job had in fact fired (fire rows 12-14 ms after each occurrence).
- **Why it was never caught:** the existing test *"does not throw if DB query fails (failure-safe)"* (`server/tests/unit/cron-fire-evidence-verifier.test.ts:173-181`) asserts only that the run resolves — it never looks at the alerts that run raises.

## 2. Objectives
1. **A failed read is reported, not read as empty.** `queryLastFires` returns `null` (not a map of nulls) when the query throws; `runVerification` then judges no job, logs one line `[CRON-FIRE-VERIFIER][SKIPPED_QUERY_FAIL] consecutive=<n> since=<first-skip ISO>`, and returns `{ ok: true, stale: [], skipped: 'query_fail' }` — a test-only surface (Langston record: the one production call site, `:279`, discards the result), so all Step-7 evidence comes from the log line and the queue.
2. **The skip is a distinguishable state, and a run of them escalates (Langston C-1).** A module-level count of consecutive skipped runs, reset by the next successful read. At **N = 4 consecutive skips** (one hour blind at the 15-min cadence) it mints one alert — `dedupe_key: cron_verifier_blind:<first-skip ISO>`, severity `warning`, *"the cron verifier could not read job history for N consecutive checks since T; every schedule is unchecked until it can"* — one per blind episode, never per run. **Its body states a floor, not a live count (Langston C-5):** *"at least 4 consecutive checks since T; the live count is in the `SKIPPED_QUERY_FAIL` line"* — a row minted at skip 4 must not read "4" forever through a six-hour blindness. The log line also carries `total=<m>` (skips since process start), because the consecutive count cannot see a sustained fail/succeed alternation. **Why 4 — derived from the cadence, not from a failure-isolation claim (Langston C-4):** the staleness predicate is **level-triggered on `prevOccurrence`**, so one skipped run costs no detection — it delays it by 15 minutes; four consecutive skips is exactly where an hourly occurrence (`awareness_state_update_cron`, the shortest cadence that pages) passes unexamined. The alert queue cannot show whether failures cluster (one `prevOccurrence` key covers the four runs in an hour, so one failure and four mint the same page-set); the log can: **2 `QUERY_FAIL` lines** in the retained stderr (`error__2026-10-05` → `error.log`; control: 200 `CRON-FIRE-VERIFIER` lines), 2026-10-10 00:41:30Z and 2026-10-17 14:28:21Z, each a single run — **measured on 2 of the 7 episodes, inferred on 5** (stderr retention ~14 days does not reach August/September). N is a constant with this reasoning beside it, not a DB setting (it is the verifier's own liveness, not a trading knob).
3. **Tests — each negative assertion ships with its minting twin (Langston C-2):** a throwing query mints **no** `cron_stale` alert and returns `skipped`; **the same fixture without the throw** (a registered job with no fire row, past grace) **does** mint `no_fires_ever` — so the first test cannot pass on an empty registry or a job inside grace. Four consecutive throws mint exactly one `cron_verifier_blind` alert; a fifth mints none (same episode); a successful read resets the count. The existing *"does not throw"* test gains the assertion it was missing (no alert). **Mechanics (Langston C-7):** the four-consecutive case uses a persistent `mockImplementation` with an explicit restore for the reset leg (`mockImplementationOnce` throws once); the module-level counter is cleaned between tests by the existing `vi.resetModules()` — no new reset hook; the minting twin reuses the existing fixture at `:101-109` verbatim.
4. **Verify (Step 7):** the verifier's regular cycle on staging is unchanged after the deploy (its `healthy` / `prev_occurrence_within_grace` lines every 15 min, no new error lines). **The live failure path is NOT a gate (Langston C-6):** waiting for a real DB timeout to show that no `cron_stale` row was minted would be waiting to observe an absence, which proves nothing (`#661` leg 3). The batch closes on the tests plus the unchanged regular cycle; **the first real `SKIPPED_QUERY_FAIL` line is carried as a named forward read on `#1211`.**

**The shared-file interlock (Langston C-3), stated:** `B-CRON-MISSED-CATCHUP` leg (a) (row 3, CC-C) will later write resolve-on-recovery into this same file. After this batch a failed read mints no `cron_stale` row at all, so there is nothing QUERY_FAIL-era for it to clear; the `cron_verifier_blind` row this batch adds is **not** self-resolving — it is resolved by hand with the evidence of the read coming back, because a monitor that clears its own "I was blind" alert erases the only record that it was. Whoever writes leg (a) must keep both true: resolve-on-recovery keys only on real fire evidence for a `cron_stale` row, and never touches `cron_verifier_blind`.
