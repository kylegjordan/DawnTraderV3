## 0. What is there
- **The verifier** (`server/services/cron-fire-evidence-verifier.ts`, B-NEW-49 / B-NEW-51), started once from `server/index.ts:1534-1535`, runs `runVerification()` every 15 min on its own `setInterval` (`:271-285`). `queryLastFires` (`:72-107`) pre-fills every registered job with `null`, runs an unfiltered `SELECT task_name, MAX(fired_at) … GROUP BY task_name`, and **on any error logs `[CRON-FIRE-VERIFIER][QUERY_FAIL]` and returns the nulls** (`:99-106`) under the comment *"verifier silently skips this run rather than alerting spuriously on a DB hiccup."* `runVerification` cannot tell a failed read from an empty one (`:137`) and pages every job whose last occurrence is past the 10-min latency grace as `no_fires_ever` (`:181`, `:192-203`); 5-minute jobs are always inside the grace.
- **Measured (`#1211`):** the same four hourly-to-daily jobs paged together seven times (2026-08-07 → 10-17); the 10-17 14:28:21Z and 10-10 00:41:30Z sets each sit at a logged `QUERY_FAIL` second. Langston re-derived the mechanism at the ref and that each job had in fact fired (fire rows 12-14 ms after each occurrence).
- **Why it was never caught:** the existing test *"does not throw if DB query fails (failure-safe)"* (`server/tests/unit/cron-fire-evidence-verifier.test.ts:173-181`) asserts only that the run resolves — it never looks at the alerts that run raises.

## 2. Objectives
1. **A failed read is reported, not read as empty.** `queryLastFires` returns `null` (not a map of nulls) when the query throws; `runVerification` then judges no job, logs one line `[CRON-FIRE-VERIFIER][SKIPPED_QUERY_FAIL] consecutive=<n> since=<first-skip ISO>`, and returns `{ ok: true, stale: [], skipped: 'query_fail' }`.
2. **The skip is a distinguishable state, and a run of them escalates (Langston C-1).** A module-level count of consecutive skipped runs, reset by the next successful read. At **N = 4 consecutive skips** (one hour blind at the 15-min cadence) it mints one alert — `dedupe_key: cron_verifier_blind:<first-skip ISO>`, severity `warning`, *"the cron verifier could not read job history for N consecutive checks since T; every schedule is unchecked until it can"* — one per blind episode, never per run. **Why 4:** every measured failure was a single isolated run (each set of pages sits on one `QUERY_FAIL` second), so one failure is noise; but the hourly jobs (`awareness_state_update_cron`) would be unchecked across a whole cycle beyond an hour, which is the shortest real cadence that pages. N is a constant with this reasoning beside it, not a DB setting (it is the verifier's own liveness, not a trading knob).
3. **Tests — each negative assertion ships with its minting twin (Langston C-2):** a throwing query mints **no** `cron_stale` alert and returns `skipped`; **the same fixture without the throw** (a registered job with no fire row, past grace) **does** mint `no_fires_ever` — so the first test cannot pass on an empty registry or a job inside grace. Four consecutive throws mint exactly one `cron_verifier_blind` alert; a fifth mints none (same episode); a successful read resets the count. The existing *"does not throw"* test gains the assertion it was missing (no alert).
4. **Verify (Step 7):** staging logs show the verifier's regular cycle unchanged (`healthy` / `prev_occurrence_within_grace` lines); a forced failure is not safe to stage, so the failure path is evidenced by the tests and, live, by the next real `QUERY_FAIL` (it now logs `SKIPPED_QUERY_FAIL` and mints no `cron_stale` row) — recorded as the observation it is, not claimed in advance.

**The shared-file interlock (Langston C-3), stated:** `B-CRON-MISSED-CATCHUP` leg (a) (row 3, CC-C) will later write resolve-on-recovery into this same file. After this batch a failed read mints no `cron_stale` row at all, so there is nothing QUERY_FAIL-era for it to clear; the `cron_verifier_blind` row this batch adds is **not** self-resolving — it is resolved by hand with the evidence of the read coming back, because a monitor that clears its own "I was blind" alert erases the only record that it was. Whoever writes leg (a) must keep both true: resolve-on-recovery keys only on real fire evidence for a `cron_stale` row, and never touches `cron_verifier_blind`.
**Also in this file, not changed here:** the alert body still says *"this clears automatically on the next successful fire"* — false today (zero resolve sites); that sentence belongs to leg (a), already homed on `#691` (row 3).
