## 1. The problem, measured

**The pool (`server/db.ts:68-78` at `562d48a8c`):** `max: 10`, `query_timeout: 30_000` (client side), `idleTimeoutMillis: 30_000`, `keepAlive`, `application_name: 'dawntrader_main'`. **No** `connectionTimeoutMillis` (a caller waits for a slot forever, `pg-pool/index.js:187` takes the no-timeout branch), **no** session `statement_timeout`, **no** `idle_in_transaction_session_timeout`, and **no `pool.on('error')` listener** (repo-wide grep of `server/` for `pool.on(` returns nothing; `server/` has no `uncaughtException` handler either).

**The database (Supabase, direct connection `:5432`, read 2026-11-04 ~21:05Z as the app's own role `postgres`):** `statement_timeout` **120000 ms, source `configuration file`** (server-wide; the `postgres` role sets only `search_path`); `idle_in_transaction_session_timeout` **0 (never), source default**; `max_connections` **90**, 3 reserved. Client backends at that moment: `dawntrader_main` 9 idle, plus 4 Supabase/system connections and my census client. ⇒ there is room for a second small pool.

**What happened on 2026-11-04 (mechanism re-derived by ANALYST Claude and Langston; I re-read the lines cited):**
1. The client gives up at 30 s and does **not** cancel the statement on the server (`pg/lib/client.js:543-564`, pg 8.13.1). The server keeps running it for up to 120 s.
2. Drizzle's `ROLLBACK` is queued behind that statement, times out unsent, and the client is released **still inside a transaction** (`drizzle-orm/node-postgres/session.js:146-150`, 0.39.1). One slot is now spent.
3. A lock held by the first stuck transaction made every later one stick: `pg_stat_activity` 18:14:52Z, **10 of 10** `dawntrader_main` held, 1 `idle in transaction` + 9 `idle in transaction (aborted)` (`#1037` am.4).
4. **901** pool-slot timeouts across every asset class and both writers, 18:03-18:16Z (873) and 19:36-19:54Z (19) (Langston's count). Price bars and signal-evaluation rows were dropped. Paper trading stalled about 13 minutes.
5. **Ending it crashed the app.** ANALYST terminated the 10 backends at 18:16:23Z; staging `error.log` at that second holds `error: terminating connection due to administrator command … code: '57P01'` and PM2 restarted the process at 18:16:28Z. **Mechanism, read at the line:** an idle pooled client that errors calls `pool.emit('error', err, client)` (`pg-pool/index.js:51-62`, `makeIdleListener`); with no listener, Node throws. ⇒ **today, ANY server-side end of an idle pooled connection — an operator's terminate, a server restart, a network drop that keepalive catches, or a database-side idle timeout — takes the whole app down.**

**The five unbounded transaction sites** (repo grep `\.transaction(` in `server/`, tests excluded, at `562d48a8c` — seven sites in all): `xstock-bar-availability.ts:45` (bounded at 20 s by R5a) · `drift-dashboard-aggregator.ts:952` (bounded at 4 s) · and five with no bound: `availability-aggregator.ts:179` and `:568` (xStock bar availability windows), `task-queue.ts:90` (fetch-and-lock with `FOR UPDATE SKIP LOCKED`), `portfolio-anchor-service.ts:148` (anchor write), **`storage.ts:859` (`upsertGuardrailsV2WithAudit`, the settings save and its audit row, added `05715c150` 2026-09-29)**. The handover named four; `storage.ts:859` is the fifth and is in scope for the same reason.

## 2. Objectives (each with how it is verified)

| # | objective | verified by |
|---|---|---|
| **OBJ-1** | **An ended connection never crashes the app.** `db.ts` registers a pool `error` listener: it logs one line naming the error code and the pool's counts, counts the event, and does nothing else (the pool has already removed the client). This is the precondition for OBJ-3, which makes the database end connections on purpose. | Unit: an idle client emitting `error` does not throw and the counter rises. Staging (Step 7): terminate ONE idle `dawntrader_main` backend (`pg_terminate_backend` on a backend with `state='idle'`), and the app stays up: same PM2 restart count before and after, one log line. |
| **OBJ-2** | **Every statement on the pool is bounded by the database, below the client's 30 s.** The pool sets a session `statement_timeout` as a connection startup parameter (pg supports it, `client.js:434-436`; the crew board's pool already uses it, `crew-coordination.ts:97`). It covers `BEGIN`, the five unbounded transaction sites, and every plain query. Existing `SET LOCAL` values stay (4 s, 20 s) and still win inside their transactions. Starting value **25 s**; Step 2 sets it from the measured distribution of the pool's own statements. | `SHOW statement_timeout` on a fresh `dawntrader_main` backend returns the value. Unit test pins it below `query_timeout`. Staging: a deliberate `pg_sleep` past the bound through the app's pool (diagnostic route or one-shot script using the same pool config) ends with `canceling statement due to statement timeout`, not `Query read timeout`, and the backend is back to `idle`, not `idle in transaction`. |
| **OBJ-3** | **A connection handed back mid-transaction is ended by the database, not kept.** The pool sets `idle_in_transaction_session_timeout` (startup parameter, `client.js:440-442`). Starting value **60 s**; Step 2 checks every transaction body for a non-database `await` that could legitimately sit idle that long. With OBJ-1 in place the pool drops the ended client and opens a fresh one. | Staging: a test client with the pool's config opens a transaction and goes quiet; the database ends it at the bound (`57P05`), the app logs it through OBJ-1 and does not restart. `pg_stat_activity` shows no `dawntrader_main` backend `idle in transaction` older than the bound across a 24 h read. |
| **OBJ-4** | **Waiting for a slot has a time limit.** The pool sets `connectionTimeoutMillis`, so a caller that cannot get a connection fails with a named error instead of queueing without end. Value set at Step 2 **from a census of every caller's handling of that error** (the writers drop on error by design, `#705`; a scanner tick already has a 25 s ceiling). | Unit: an exhausted test pool rejects the 11th acquire at the bound with the named message. ## 5. Risks, stated
- **OBJ-2 turns a 25-30 s statement from a pass into a failure.** Today anything over 30 s already fails client-side, so only the 25-30 s band changes. Step 2 reads the pool's statement distribution above the mean (the same gap ANALYST named for R5a) before fixing the number.
- **OBJ-3 ends a transaction that legitimately waits.** Step 2 reads every transaction body for a non-database `await` (an HTTP call, a timer) inside the transaction.
- **OBJ-4 turns a long wait into an error.** For a writer that drops on error, a bounded wait can drop rows that an unbounded wait would have written late. Step 2's census decides the value per this trade, and may set it long (e.g. well above a normal burst) so it only bites in a jam.
- **OBJ-1 is the order constraint:** OBJ-3 must not deploy before OBJ-1, or each idle-in-transaction kill restarts the app. One commit, or OBJ-1 first.
- **A second pool adds up to 2 connections** against 90 allowed and about 14 in use at the census.
