## 1. The problem, measured

**The pool (`server/db.ts:68-78` at `562d48a8c`):** `max: 10`, `query_timeout: 30_000` (client side), `idleTimeoutMillis: 30_000`, `keepAlive`, `application_name: 'dawntrader_main'`. **No** `connectionTimeoutMillis` (a caller waits for a slot forever, `pg-pool/index.js:187` takes the no-timeout branch), **no** session `statement_timeout`, **no** `idle_in_transaction_session_timeout`, and (before `d6ce6b042`) **no `pool.on('error')` listener**. ⚠️ **Correction to r1:** `server/` has exactly one `pool.on(`, `crew-coordination.ts:101`, `pool.on('error', () => {})`, under the comment *"A pool-level error with no listener crashes the process."* The same ten lines set `connectionTimeoutMillis`, `query_timeout` and `statement_timeout` on that pool (`:95-97`). The invariant was written down in `server/` and the main pool did not follow it. That file is removed by `B-CREW-BOARD-REMOVAL`, so it is a precedent, not the reference implementation. **The crew pool needs no per-client listener (Langston, Step 4, disposition 5 — no work):** it has no `.connect(` and no transaction, only `.query(` (6 sites), and `pool.query()`'s own `once('error')` covers a checked-out client, so the in-use crash path is not reachable there. If that pool ever gets a transaction, it is.

**The database (Supabase PostgreSQL **17.6**, direct `:5432`, read 2026-11-04 between 20:55 and 21:45Z as the app's own role `postgres`):** `statement_timeout` **120000 ms, source `configuration file`** (the role sets only `search_path`); `idle_in_transaction_session_timeout` **0, default**; **`transaction_timeout` exists, 0, default**; `max_connections` **90**, 3 reserved; `dawntrader_main` 9 idle at the first read. ⚠️ `RULED ON REPORTED FACT` for Langston (no database access from his side); in-repo corroboration of the 120 s: `scanner.ts:604`, `partition-exporter.ts:159`. Step 2 re-reads all of these and records the exact query beside each value.

**What happened on 2026-11-04 (mechanism re-derived by ANALYST Claude and Langston; I re-read the lines cited):**
1. The client gives up at 30 s and does not cancel the statement on the server (`pg/lib/client.js:543-564`, pg 8.13.1); the server runs it for up to 120 s.
2. Drizzle's `ROLLBACK` is queued behind it, times out unsent, and the client is released still inside a transaction (`drizzle-orm/node-postgres/session.js:146-150`, 0.39.1). One slot spent.
3. A lock held by the first stuck transaction made every later one stick: 10 of 10 `dawntrader_main` held at 18:14:52Z, 1 `idle in transaction` + 9 `idle in transaction (aborted)` (`#1037` am.4).
4. 901 pool-slot timeouts across every asset class and both writers (Langston's count); bars and signal-evaluation rows dropped; paper trading stalled about 13 minutes.
5. **Ending it crashed the app:** `57P01` at 18:16:23Z in `error.log`, PM2 restart at 18:16:28Z. pg-pool's `makeIdleListener` calls `pool.emit('error')` (`index.js:51-62`) and Node throws with no listener. **Fixed by OBJ-1 (`d6ce6b042`).**
6. **Tonight's 20:56:48Z cancel (alert `09684639`, xStock OHLC writer, 243 rows) fits step 1, it does not contradict it:** the xStock writer's projection runs in `boundedTransaction` (`xstock-bar-availability.ts:559`, `:588`), whose first statement is `SET LOCAL statement_timeout = 20000` (`:44-48`), so the server's 20 s cancels before the client's 30 s. R5d (deployed `8ff2a691e`, 21:20:15Z) retries that case; the alert is CC-C's.

**The seven transaction sites** (`\.transaction(` in `server/`, tests excluded, re-derived by Langston at `955d0931f6`): two bounded (`xstock-bar-availability.ts:45`, 20 s; `drift-dashboard-aggregator.ts:952`, 4 s) and **five unbounded**: `availability-aggregator.ts:179`, `:568`; `task-queue.ts:90`; `portfolio-anchor-service.ts:148`; `storage.ts:859`.
