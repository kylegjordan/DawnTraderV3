## Objectives and verification

1. **Serialize fallback with the existing ledger rewrite.** Drive the real watchdog with its CLI forced to fail, and the real canonical writer at the read-to-replace boundary, against isolated ledgers. Force fallback-first and rewrite-first orderings. Pass: the exact critical watchdog UUID and an unrelated control row survive both orderings, and a live holder past the stale threshold retains ownership and excludes the fallback. Fail: lost or duplicated UUID, lock takeover while a live holder owns it, corrupted ledger, or unexpected control-row change. Test timeout and a genuinely dead holder as distinct states. Removal of the protection must restore failure in the hostile ordering.
2. **Carry a pending emission through timeout and restart.** The watchdog must durably retain a failed emission and retry it independently of the CLI and of whether the check still fails on the next tick. Exercise process restart after a timeout and after the row is written but before pending state is cleared. Pass: the held-lock run leaves the existing ledger intact, a subsequent eligible retry writes the same UUID once, and another retry adds no copy. Exercise ordinary CLI success, unresolved-key dedupe, clearing and a fresh post-recovery occurrence, plus the no-key heartbeat and `OnFailure` paths. Fail: lost pending row, false success, missed recovery or accidental suppression of a later occurrence. Step 2 must specify the evidence for competing same-key CLI success and for a pending row that has already resolved.
3. **Prove first delivery through the ordinary route.** In each forced ordering, give the retained critical UUID to the real dispatcher using an isolated delivery receipt sink. Pass: one successful first receipt for that UUID and persisted normal delivery state. Prove a failed delivery yields no success receipt and the ordinary retry can deliver it. Fail: a fallback-only store record with no receipt, a duplicate successful first receipt in the exercised ordering, or a change to an unrelated receipt. Before any staging verification, register the permitted proof window, installed-writer compatibility and any cleanup; a protected window or missing authority leaves the staging proof pending.

**Step 1 baseline, not acceptance evidence.** A local scratch check started the tracked watchdog with `--self-fail` and a nonexistent CLI working directory. In each of two tests the executable logged the CLI failure, appended one generated critical UUID, and included the fallback origin marker. A fixture modeled the canonical writer's read/temporary-file/rename boundary and held a lock marker using the live parent PID. The watchdog UUID survived **0/1** with the append before the fixture rename and **1/1** with append after rename. The existing control row survived **1/1** in each run. The fixture simulated the rewrite boundary; Step 2/3 proof must exercise the canonical writer and real dispatcher.
