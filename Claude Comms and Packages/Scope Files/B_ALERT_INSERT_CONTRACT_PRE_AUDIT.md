### A.9 The re-raise rule (C-1: the reset needed its own finding)
A refresh means "the same condition is still true". A dismissal by a person must survive it. What should bring a row back is **a new episode**: the condition went away, and then it returned. Only the feed-health monitor knows when an episode ends: on a healthy cycle (`feed-integrity-auto-check.ts:135-145`) and on a trading stop (`clearFeedHealthAlertsOnStop`). Both run `acknowledgeFeedHealthAlerts`.
⇒ **That function marks the episode closed:** it sets `acknowledged = true` and stamps `metadata.episodeClosedAt`. **The refresh re-raises a row only if it carries that stamp,** and the new metadata drops the stamp. A row a person dismissed mid-episode has no stamp, so it stays dismissed until the episode ends. The next recurrence after the episode ends re-raises it. Writers without an episode notion (formula audit, unknown-strategy, rate limiter, Expert Insights) never re-raise a dismissed row; a different text is a different row anyway. No schema change: the stamp lives in the existing `metadata` jsonb.
**The flap case (C-8), stated:** the clear runs on every healthy cycle, not only on a transition, so one healthy 5-minute check closes an episode. A feed that flaps (degraded, then healthy for one check, then degraded) brings a dismissed alert back within about 10 minutes. **Accepted as a genuine clear-and-return:** the monitor graded the feed healthy for a full check, so the next degradation is a new event that Kyle should see. It is not bounded by an N-healthy-cycles rule, which would hide a real recurrence. If flapping turns out to be noisy in practice, that is a tuning question for the monitor, not for the insert contract.
*Cost, stated:* on its first healthy cycle after deploy the clear stamps every historical `feed_health` row once (5,888 rows on 2026-11-14, nearly all already dismissed). After that it touches only rows not yet stamped.
