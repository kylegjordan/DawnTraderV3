**Disposition framework (to apply per site in the design doc):** each reader is one of — (a) **request-scoped** (a user is viewing paper OR live in the UI → keep scalar, it's the viewer's selected mode, harmless); (b) **producer-scoped** (the code is acting AS a producer → must read THAT producer's mode explicitly, not the global); (c) **genuinely-global** (system-state display → keep, but it must mean "any active" not "the one mode"). ### A1.★ — KYLE DISCOVERY METHOD (2026-06-09) — the authoritative way to find EVERY mode-sensitive point; supersedes grep-as-primary
**Principle (the architecture):** the mode is a **property the pair CARRIES**, not an ambient global. It is **stamped at the point the pair enters a producer pipeline** — i.e., at the fan-out where the shared (producer-agnostic) scan/MCE/pattern/strategy output is **copied** into the VTS, paper, or live path (Kyle: "the data comes in, it's immediately copied and then sent into the pipelines"). From that entry stamp, the tag **rides the payload through every stage** — selection → SQE → RTB → TCL → position → outcome → storage. Every stage that needs the mode reads it **off the pair**, never off `getCurrentMode()`. This structurally **eliminates the split-brain ambiguity** (there is no "which mode?" question at a reader if the answer travels with the data).

**Discovery method:** to enumerate every mode-sensitive point, **trace a single pair end-to-end through each pipeline** (one trace for VTS, one for paper, one for live) and mark every stage where the mode is load-bearing. This finds the COMPLETE set — including stages that *should* be mode-aware but currently are not (the gaps a keyword sweep can't surface). The ~107-site grep is the *lower bound* (where mode is read today); the pair-trace is the *true set* (where mode matters). The disposition framework (a/b/c above) is applied to each point the trace surfaces.

**★ Proven precedent — this is exactly the `asset_class` threading we already did (B79.0n).** `asset_class` was made a REQUIRED, explicitly-threaded dimension carried through the detect signatures + selection + storage key (no ambient lookup, compiler-enforced at every call site). **Mode becomes the SECOND first-class threaded dimension, same pattern** — which de-risks it: the threading approach is already proven in this codebase, and the `_SE_KEY(strategy, assetClass)` / per-class resolver pattern is the template for a `(mode, …)`-carried payload. The stored **source-label (D1) is then simply the entry-stamped mode the pair has carried** — not a separate write-time lookup.

**→ Phase-A action (★ Kyle refinement 2026-06-09: BOTH methods, union):** the formal blast-radius pass = **three end-to-end pair-traces (VTS / paper / live)** cross-referenced against SIM + System Manual, **UNIONED with the A1 keyword sweep**. Complementary coverage: the **trace** finds the complete in-pipeline set *including stages that should be mode-aware but currently aren't* (gaps the sweep can't see); the **sweep** finds mode dependencies **outside the pipeline path entirely** (UI/routes display readers, guardrail/admin surfaces, background jobs, telemetry endpoints — things no pair ever flows through). Neither alone is complete. The authoritative mode-touch map = trace ∪ sweep, every entry dispositioned (a) request-scoped / (b) producer-scoped→carried-tag / (c) genuinely-global→any-active.

## A2-RESOLVED — Langston deep-read findings (DR1/DR2/DR3, code-verified 2026-06-09)
- **DR1 (live thin-scaffold — A2.1) = a ONE-LINE seam, no rebuild.** Order routing is NOT entangled with signal generation: `TradingEngine.start()` → SignalOrchestrator → `processSignal()` (all compute+telemetry) → `executeTrade()` at `trading-engine.ts:290`; ALL Kraken order calls live below `:290`. **A `scaffoldNoOp` flag on the `TradingEngine` class, short-circuited in `processSignal` right before `:290` (emit a `LIVE_SCAFFOLD_NOOP` trace + return null), makes the live switch run the full compute+telemetry path with ZERO orders and zero stale commit/bracket/portfolio flow.** Nuance: the pre-seam slippage calc reads the Kraken orderbook (a READ, not an order) — fine for a scaffold; flag only if the bar is "zero Kraken contact" vs "zero orders." → O3 for live is cheap.
- **DR2 (dead constructs — A2.2):** **(c) `paper-48hr-simulation.ts` + `paper-trading-start.ts` = fully orphaned (zero importers, self-disabled) → quarantine NOW.** **(a) `globalPaperEngine`:** the `paper-sim-service.ts:280-281` branch reading `(global as any).globalPaperEngine` is DEAD (never assigned) → quarantine that branch now; the OBJECT has live importers (CommandRouter ctor + status + closeTrade endpoint) → defer object removal to Phase 16. **(b) ★ `global.tradingEngines` Map is NOT a stub — it's a REAL second, parallel per-user live-engine registry** wired to the live-activation endpoints (`routes.ts:5402/5421/...`) + 6 consumer services, coexisting with the Phase-27 `globalLiveEngine` singleton. **→ TWO live-engine instantiation models exist** — a genuine entanglement; cannot quarantine now → **Phase 16/21.** (This is why live's real build is correctly deferred — it's not just a stale engine, it's two competing engine models.)
- **DR3 (guardrails/kill-switch — A2.4) = genuinely per-mode for paper↔live.** `tripKillSwitch(mode)` writes only that mode's `guardrails_v2` row, sets that mode's `isEngineActive=false`, clears that mode's pool, stops only that mode's engine; daily-loss caps per-mode (paper 30% / live 10%); no shared in-memory tripped boolean. **Log (benign):** cross-mode RULE_ID-keyed telemetry counters + shared read-only rules YAML. **★ SAFETY DECISION for the design:** VTS is NOT in the `TradingMode` enum at all → it's structurally immune to paper's kill switch, BUT **VTS has no kill-switch of its own in this subsystem** — does the standalone VTS need its own safety control? Explicit decision, not an assumption.
