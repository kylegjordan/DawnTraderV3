## 1. The defect — and the governance-ledger reconciliation (§9.5 b-ii)
Kyle spotted it in the RTB table (#560, 2026-07-22): xStock DBS + DI are computed but **never reach the at-queue carry** — crypto carries them 83/83, xStock **0/28**. **This is the SAME defect as #377** (reorg-B3 FIND 2, 2026-06-24, CC-B + Langston), which already root-caused it from the open-gate side: "xStock strong-trend signals reach the open-gate with NULL `dbs_score_at_queue` → 0.40-floor pWin … the fix = source xStock's per-class DBS into the at-queue carrier (a non-FX5 path for the xStock builder), landed before xStock active-paper turn-on." **#377 is the authoritative pre-existing home; #560 is Kyle re-finding it live. This scope closes both.** (Filing #560 as fresh without #377 would be the exact §9.5 b-ii failure — a Langston-reviewed decision reported as a new discovery.)

**Root cause (verified at `origin/migration/aws-supabase`, line-drift-corrected from the 5-day-old #560 trace):**
- The carry reads from the **crypto-only** FX5 pool: `signal-orchestrator.ts:746` `fx5Data = activeFilterPool.getFX5DataForSymbol(symbol, mode)` → writes `diAtQueue: fx5Data?.di ?? null` / `dbsScoreAtQueue: fx5Data?.dbsScore ?? null` at **`:1066-1067`** (the #560 trace's `:1060-1061` drifted ~6 lines). The same `fx5Data` also feeds the maker/taker decision at **`:786-788`**.
- The FX5 pool has three write surfaces, **all crypto** (`xstock_spot/friction-sample-store.ts:13-16`; writers `fx5-scanner.ts:1417/1421`). No xStock file writes it → `getFX5DataForSymbol` returns null for an xStock symbol → both columns persist NULL.
- **But xStock's real DBS is already computed and in scope:** the xStock scanner computes it via `computeDirectionalBias` (`xstock_spot/scanner.ts:849`) → `propagatedDbs` → the MCE passes it through unchanged into `mceContext.directionalBias.score` (`market-context-engine.ts:1286`), and the orchestrator **already reads that class-keyed context in the same function** (`getCachedContext(symbol, assetClass)` at `:671` and `:1207`; `symbolCtx.directionalBias.score` at `:1418`) for the regime label — proven working for xStock. The DBS the carry needs is one already-in-scope read away; it's just reading the wrong (crypto-only) source.

## 2. The two settle-first questions (#560 required these BEFORE any wiring) — ANSWERED
**(a) Same scale/basis? — YES for DBS, proven from code.** Both classes call the identical `computeDirectionalBias` (`directional-bias.ts:56`), `.score` clamped to **[-1.0, +1.0]** (`:103`), identical weights + thresholds. xStock spreads `DEFAULT_DBS_CONFIG` overriding ONLY lookback/EMA/ATR periods (`scanner.ts:811-815`), and those are **wall-clock-equivalent** re-expressions for 15-min vs 60-min bars (`scanner.ts:788-790` — 192/48/104/56 on 15m = crypto's 48/12/26/14 on 60m = same 48h windows). The MCE passes the score through unchanged for both classes (`:1276` crypto / `:1286` non-crypto). ⇒ **For DBS this is a "wire the class-aware source" fix, NOT a scale reconciliation** — so the #555/#377 same-name-different-quantity risk does NOT apply to the DBS carry.
**(b) Right seam? — a class-aware source, exactly as #377 prescribed.** For xStock, source DBS from the class-keyed MCE context already in scope (`getCachedContext(symbol, assetClass).directionalBias.score`); crypto continues to read `fx5Data`. Feed it to BOTH consumers of the source (the at-queue carry `:1066-1067` AND the maker/taker decision `:786-788`) so xStock's maker/taker EV also uses the real DBS.

## 3. Objectives
- **OBJ-1 (the fix):** at `buildSizedSignalForStrategy`, resolve `dbsScoreAtQueue` **class-aware** — xStock reads `mceContext.directionalBias.score` (the already-in-scope class-keyed context); crypto path unchanged (`fx5Data.dbsScore`). - **OBJ-2 (DI — deliberate NON-carry, documented):** leave `diAtQueue` NULL for xStock (kernel default `DI=50`). Rationale: (i) DI is **EV-inert** — default DI=50 already caps the standard branch at the 0.60 ceiling, so real-DI threading gives ZERO EV lift (#377 H1); (ii) xStock DI is a **different formula/basis** from crypto DI (signed `(net/abs)×50+50` vs crypto trend-straightness), unreconciled and homed to **Phase-25 #502** — carrying it under the crypto-named `di_at_queue` column is precisely the same-name-different-quantity silent harm. So DI carry is deferred to #502; the fail-safe null (EV-neutral) holds until then. **(Recommend Langston/Kyle ratify this non-carry; the alternative — carry lane-native DI with a basis flag — is more work for zero EV benefit and reintroduces the basis risk.)**
