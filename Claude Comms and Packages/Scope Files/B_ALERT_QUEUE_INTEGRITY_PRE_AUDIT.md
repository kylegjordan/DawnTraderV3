### A2 · Competing writes, ownership and compatibility

- `server/scripts/staging-liveness-watchdog.mjs:183–215` first waits up to 60 seconds for the normal CLI, then scans the file and directly appends after failure. The unlocked append can occur after a canonical reader has taken its snapshot and before it replaces the file. That loses the new row even though the append returned successfully. The failing CLI can also have committed before returning an error, so falling into the catch is insufficient to infer absence. The current fallback success line logs the key and leaves UUID, terminal state and delivery to be derived from the actual store.
- `server/services/system-alerts.ts:401–453` uses exclusive creation and records PID/time but permits contenders to unlink a lock older than 30 seconds based on mtime alone. The acquire retry budget is 50 × 100 ms. Sharing that existing algorithm leaves a live-but-old holder exposed, and compare-then-unlink without serialized reapers leaves an old-owner-to-new-owner race. The temporary dispatcher artifact has the same lock-file name and age-based takeover; check the source and installed hash again before any rollout. A mixed old/new writer is unsafe on this ledger.
- Installed Linux provides `/usr/bin/flock` (util-linux 2.39.3) and the ledger is on a local ext-family filesystem as reported by stat. Linux permits process birth identity checks with boot ID and process start ticks. Design fail-closed on inaccessible identity, including ambiguous or malformed locks. A bounded wait can safely defer the watchdog emission if the ledger is busy; retention and a guaranteed later retry need to exist independently of that ledger.

### A3 · Delivery and failed sends

At the audit ref, `scripts/system-alerts.ts:216–255` calls `fireDue`, which persists scheduled → active and `fired_at` under lock before the send. Both normal and #1191 r2 dispatchers use the same warning/critical delivery route. An HTTP rejection gives no success receipt, and a later ordinary due scan does not re-promote the active row. For an unresolved active critical alert, its first ordinary re-surface is due at `fired_at + 2h` (`server/services/system-alerts.ts:760–800`). For acknowledged critical the base is 4h. Once re-surface is due, failed delivery leaves the back-off unchanged and the existing timer can retry on the next tick. Only a successful re-surface advances delivery bookkeeping. The #1191 hold predicate is for its retained active warning IDs and VTS keys, so it cannot select the critical watchdog row. Initial `fired_at` is promotion evidence and the matched HTTP success is receipt evidence.

## Implementation and proof plan

1. **P1 · Shared ownership and commit boundary (A1, A2).** Use one plain-Node lock implementation in the watchdog and canonical library. Keep the existing ledger lock path and bounded asynchronous wait. Publish a fully written owner token atomically via an exclusive same-directory hard link. Carry process identity (boot ID, PID, start ticks), and fail closed if identity or the token cannot be verified. Common acquisition stays filesystem-only. After the existing age floor, serialize dead-owner reclamation through a bounded `flock` on a separate permanent reaper file, re-read the token inside the guard and remove only a proven dead owner. All active writer versions must follow this protocol. A live holder never enters the reclaim arm. Normal acquisition can succeed only after the canonical name is absent. The reaper file stays stable and must never be unlinked during operation. Compare lock-wait and normal acquire cost offline and use the existing Linux CI/Docker host for real filesystem controls. Reject unverified legacy locks; the cutover below keeps legacy and new holders out of the same writer population.
2. **P2 · Durable pending write and retry (A1, A2, A4).** Keep the CLI as primary. On failure publish the existing fallback shape and an attempt start marker to a durable per-occurrence pending file outside the checkout, adjacent to the ledger. Use an atomically published, fully written file, one pending attempt per dedupe key, so a concurrent watchdog cannot overwrite the first UUID. Flush the file and pending directory before reporting that it is retained. On each watchdog invocation, retry pending work within the existing lock budget before resolving or deduping the matching occurrence. An ambiguous lock or persistence error must be visible and must leave a published pending record for the next run. Do not require the application build or alter watchdog timers. Under the canonical lock, re-read the ledger. If that UUID already exists, including resolved, retire the pending attempt without replay. If another unresolved row holds the key, use that row. If a racing CLI committed then resolved after the attempt began, settle the same in-flight occurrence by that persisted ID. A resolved row from before the attempt does not suppress a fresh occurrence. Apply the comparison to last-row-wins state and retain enough correlation evidence to test the boundary; equal or ambiguous times retain pending until safely settled. Otherwise commit the fallback row and only then retire pending. Use atomic replacement of the original bytes plus one complete line in the fallback path so unrelated rows stay byte-preserved, including malformed history outside this item's repair scope. No success before a committed ledger row or a matched existing row. A crash after commit and before pending cleanup must converge by UUID on the next invocation.
3. **P3 · Offline controls against real code (A1–A4; scope OBJ-1/2/3).** Run the real watchdog with actual failed CLI, actual library writer and actual ordinary dispatcher against isolated ledgers. Gate a real writer at the read-before-rename seam and force both orderings. Retain the exact UUID and unrelated row in each. Hold a live lock past 30s, ramp to contention timeout, then verify that the same UUID is committed once after release and process restart. Kill a distinct real child holding the lock, race two reapers with a contender, and prove the successor can acquire with no overlap. Exercise crash after pending publication and after ledger commit, CLI success, CLI commit then error and a later same-key recovery/new occurrence, already-resolved pending UUID, weekly UTC dedupe and `--self-fail`. The hostile ordering must fail under the old unlocked append as a negative control. Reject stale takeover of a live holder, lost pending, changed control rows, extra UUIDs and accidental re-arming suppression.
4. **P4 · Receipt proof (A3).** For each forced ordering, run the real normal dispatcher against a local HTTP receipt sink with one tracked watchdog UUID. Match the Alert ID in the webhook body and dispatcher success line to the persisted UUID. Require one successful initial receipt, no second initial receipt on the next tick, and retention of the unrelated control. Repeat the relevant receipt paths with the exact #1191 dispatcher fixture. For a forced initial 5xx, require promotion but zero successful receipts, no premature duplicate during the active-critical TTL, one eligible re-surface receipt, and persisted re-surface count and time. A failed eligible re-surface retry must leave those fields unchanged before a later successful tick. Keep normal retry policy and the #1191 hold predicate intact.
5. **P5 · Activation and proof boundary (A1, A2, A4).** Review exact CLI/checkout, PM2, normal/temporary dispatcher, watchdog unit and maintenance callers by path and artifact hash in Step 4/6. Agree a short coordinated writer drain for cutover and rollback. Close admission to new old-version CLI/manual/maintenance activity, wait for in-flight app/CLI/dispatcher/watchdog writers to leave, verify no old holder or binary can still write, then enable only mutually compatible versions. Do not delete an unverified lock. Keep pending files intact across cutover/rollback and explicitly replay them when compatible writers return. Do not change the live #1191 temporary artifact or interrupt its joint recovery read. Activation waits until the normal dispatcher is restored or a separately approved compatible placement exists. Plan Step 7 as an isolated fault proof (no live alert injection) and immediate deployed writer/console/receipt-path readback in a registered, permitted slot. No elapsed trading or soak population is planned here. File the exact proof/cleanup window before staging verification and preserve higher-priority windows. If the staged proof cannot exercise the relevant seam, carry it as pending, not as verification. Keep #994 Step 3 parked until the safeguard is verified.

In plain language, the watchdog can currently write an alert just before another writer replaces the alert list, and the new row can disappear. The plan keeps a durable copy of that alert, gives its retry the same protection as the ordinary alert writers, and proves the exact alert reaches the normal notification route after contention and restart.
