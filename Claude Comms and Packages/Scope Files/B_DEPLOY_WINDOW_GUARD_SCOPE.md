## 4. Judgement calls I want attacked

- **J1. Where the register is read.** The settled recommendation says *"at the sha being deployed"*. The later channel carry (2026-11-06) says *"at the fetched origin HEAD"*. **I propose origin HEAD.** A window filed after the deploying sha was cut would be invisible at that sha, which is the defect itself. And a broken register is then fixed by a commit to the branch, with no deploy needed, so fail-closed can never lock staging out of its own repair. Attack: does reading HEAD let an unreviewed register row block a deploy? Every row on the branch has come through review, so I think not.
- **J2. `--in-window` names every open window, not one.** Naming one would let a deploy authorised by one owner silently land in a second owner's window, the exact `#1249` shape. Cost: a deploy during two windows needs both names typed. Attack: is that friction a reason sessions will route around the tool?
- **J3. Does a STALE window block?** I propose it does not block, but it is printed, and the alert in OBJ-3 still mints for it. A stale window is a filing that forgot to close, and refusing on it would let one forgotten row stop every deploy. The cost is that a window that genuinely overran its end loses protection without warning its owner, except through the alert. Attack this one hardest.
- **J4. The register's location.** It must sit in a file the drift line's runtime predicate does not count (`SYSTEM_IMPACT_MAP.md` drift entry, four sinks). Otherwise filing a window would itself raise drift alerts and demand a deploy. I propose a governance path under `1-system-manual/`, checked at Step 2 against the predicate's file list.
- **J5. Scheduling the comparator here rather than in `P19-B12`.** This batch changes `dt-deploy` and installs it by hand, which is exactly the event the comparator exists to check. Leaving it unscheduled would ship a new refusal whose installed copy nothing verifies. It is mine either way (row 164 owner = Infra Claude), so this is an item moved within agreed work (§9.4 disposition 2), not a new slot. Attack: does it bloat this batch?
- **J6. The wake route.** Staging has no `cc-send` (§0), and an alert-webhook post reaches sessions only through Langston's relay, which wakes one name. The candidates are (a) a Helsinki watcher on the deploy record that posts through `cc-send` with every owner in the opening list (the `dt-push-notice` shape); (b) `dt-deploy` prints the exact post and the deploying session must send it (unenforced); (c) alert-only plus the `@CC-WAKE` tag. **I lean to (a)**, since only (a) does not depend on a session remembering. Step 2 settles it with a measured wake.

## 5. Risks named now

- **Fail-closed can block an urgent deploy.** The mitigation is J1: a register fix is a branch commit, never a deploy, and `--in-window` with every name is always available. A true emergency still runs through the hotfix path with Langston, and the deploy then names the windows it lands in, which is the point.
- **The register goes stale.** A window left open blocks deploys (unless J3's stale rule applies), and a closed batch left in the "not yet live" list misleads the joint-deploy pass. The weekly plan census is the existing reader for this; Step 2 names where staleness is surfaced.
- **The installed copy and the reviewed copy diverge again** (`#1004`). OBJ-5 is the mitigation and is required, not optional.
- **This batch's own install happens during NEW Claude's windows.** Installing `/usr/local/bin/dt-deploy` restarts nothing, but it changes what the next deploy does. The install is announced to every open window's owner under the interim rule, and it happens outside 14:30-21:00Z on any day NEW Claude has a US-session window registered.
