### 1.3 Findings — the shared-state census (who writes, reads, mutates, deletes, schedules)

- **A1 — the circuit breaker is per worker.** `breaker = {"bot_turns": 0}` is created inside `task_worker` (`:762`) and mutated in `process_task` (`:458-473`). Two workers would each count half the turns, so `BOT_TURN_LIMIT` would trip at twice the intended count. **(1) folded:** one shared breaker under a lock.
- **A2 — the runaway cap is a module global with no lock.** `_cap = lq.CapTracker()` (`:61`) is reset by every real inbound (`:455`) and read/advanced by `_self_advance` (`:373`, `:382`). Two threads interleave unprotected. **(1) folded:** the same lock as A1.
- **A3 — the review-queue file is read-modify-written WITHOUT the lock, at six sites.** `save_queue` takes `queue_lock` for the write itself, but the bridge's `load_queue → mutate → save_queue` sequences are not one transaction: enqueue (`:513-521`), inbound marker (`:534-537`), the post-reply marker and auto-settle (`:677-720`), `_self_advance` (`:365`, `:379`), and `_resurface_stale_blocked` (`:733-753`). The atomic primitive already exists — **`lq.locked_update` (`langston_queue.py:415`, `#495`) — and the bridge never calls it.** With one worker the only concurrent writer is rare; with two, worker 2 saving a list it loaded before worker 1's marker landed **erases that marker** (a lost update). **(1) folded:** every site moves to `locked_update`.
- **A4 — self-advance could re-invoke one item twice. Self-advance is ON live (`LANGSTON_SELF_ADVANCE=1`).** After each reply `_self_advance` picks the next `ready` item and enqueues a re-invoke (`:349-384`). Two workers finishing close together each pick the SAME next item. **(1) folded:** the pick and the "advancing" mark happen in one `locked_update`, so the second worker sees the item already taken.
- **A5 — `_resurface_stale_blocked` would post twice.** It runs from each worker's idle heartbeat (`:771-772`) and posts a reminder per stale item. Two workers both run it. **(1) folded:** it runs only inside `locked_update` and only when its last-run stamp is older than the heartbeat.
- **A6 — `state` and `save_state`.** Writers: the startup save (`:1295`) and the rotation backstop (`:307-311`), which `:604-605` says is "now effectively never triggered" (every call uses a fresh UUID, `:606`). `save_state` is atomic (temp file + `os.replace`). **Disposition: (5) delete the backstop — but only AFTER P6** (r2, Langston D-2). The journal back to 2026-09-10 has **0** `session UUID locked, rotating` lines (positive control: the same grep finds the 3,188 `handling msg` lines), but that zero is single-worker history and the trigger matches a concurrency-flavoured string (`already in use`); this batch is the first to run two invokes on the account at once. So P6's smoke test captures both invokes' stderr, and the deletion lands after it, in this batch, with the smoke test as its positive control (rule 18 satisfied). (Langston cannot read this journal from his account, so the zero stands as reported.)
- **A7 — the inbox mirror and the log.** `mirror_event` and `log` each open the file in append mode and make one `write` per line (`discord_common.py:151-152`, `:211-212`). The inbox log already has three writer processes (this bridge, the CC bridge, Coltrane), so concurrent appends are not new. **(1) no change**, and a Step-3 test drives both from two threads and checks every line parses.
- **A8 — the alert spool** is one file per message id (`spool_write`/`spool_remove`), written by the lane worker and `process_task`. Distinct ids never share a file. **(1) no change.**
- **A9 — memory and ledger writes (Langston C-2).** `--ledger-append` is an anchored insert, so a bounded retry is safe. A whole-file `--part` write under compare-and-swap is not: a retry would resubmit a stale body. **Measured load:** his own memory writes run at about 24 per 190 invocations (pack §3.4, ~13 %). **(1) folded (P4), and the mechanism is RECOVERY, not a lease** (r2, Langston D-1): the tool already serialises writers (`open_lock()`, exclusive flock on a root-owned lock, the target re-hashed under it), so two part writes cannot corrupt the file and the loser gets exit 4 with the current sha. What two workers add is that refusal happening routinely, so the gap is the loser's recovery. A lease would hold the mutex across his compose step (the hazard the tool's own header names), add a stuck state, and its 15-min TTL equals the 900-s invoke ceiling.
- **A10 — scratch collisions.** Both his `scratch/` (2,547 fixed-name files) and his home root (`a.md`, `b.md`, `ri.md`) collide by name. **(1) folded:** P3.
- **A11 — the people-class lane share is 31 % (§0).** Escalations dominate it (75 % have no batch id). **Consequence:** the shared serial lane will mostly carry escalations and un-keyed Kyle/session posts. That is still never worse than today, since today every task is in one serial lane. **(2), a design note, corrected at r2 (Langston D-3):** an escalation keys by **`alert_lane.alert_key(text)`** — `(template, symbol)`, `alert_lane.py:202` — the precedent store's own key (consumed by `langston_precedent :217` and `effective_owner :276`), falling back to the alert id when it returns `None`. Keying by id would put two escalations of the same template in different lanes, run them at once, and interleave their markers, which `effective_owner` reads as `ok=False` and escalates back to him (measured 2026-11-05: 22 markers on one template, interleaved). One key closes both.
- **A12 — Kyle's post can wait behind a lower-priority task that started after it arrived** (scope OBJ-1 note). That happens only when both workers are busy and his task is in a busy lane; P8's log records post, start and both workers' spans, so it is counted, not argued.
- **A13 — the baseline days, re-based on ARRIVALS (r2, Langston D-4).** Handled tasks per day is a consequence of the treatment (two workers clear more), so selecting days by it biases the comparison. Arrivals are exogenous. **Measured (inbox log, `langston_inbound` = session/Kyle text, `langston_alert_inbound` = alerts):** 10-20 49 / 24 · 10-21 32 / 97 · 10-22 → 11-03 **0 text every day** (alerts 22-77) · 11-04 90 / 68 · 11-05 201 / 83 · 11-06 (part) 49 / 18. ## 4. Plain-language summary
Today Langston reviews one thing at a time and sessions wait about 70 minutes. This batch lets him run two reviews at once. The audit found what two at once would break: his review to-do list is saved without a lock in six places, so two reviews could erase each other's notes; his "move on to the next item" step could pick the same item twice; his working files and his memory saves could overwrite each other. The plan fixes each of those, installs with only one worker running to collect a fair "before" picture on busy days, then turns the second worker on and watches waiting time and review quality, with automatic stop rules.
