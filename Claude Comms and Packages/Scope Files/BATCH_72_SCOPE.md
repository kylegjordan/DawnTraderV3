## Why this batch exists

DawnTrader's go-live design intent (Kyle directive 2026-04-26, codified in roadmap §B72): **every threshold, weight, multiplier, limit, and tunable coefficient in the active codebase MUST be DB-tunable BEFORE live trading turns on.** The operator cannot be required to deploy code + restart PM2 to adjust a parameter once real money is on the line.

The infrastructure for this already exists. B65.1 shipped the `module_constants` table with a 5-dimensional resolution model (`module_name × exchange × asset_class × strategy × regime` → constant_name → value), most-specific-wins, 60s cached, no silent fallback. Migrations through B65/B66/B67/B68/B69/B70 have inline-migrated dozens of constants as those batches added or modified them.

What is missing is the **comprehensive backstop sweep** — the audit that finds every remaining hardcoded lever in the active codebase, classifies it for promotability, and migrates the promotable ones in one coordinated batch. Without this sweep, levers introduced before B65.1 (Phase 12-15a era) and any levers added inline since but not surfaced in module_constants will still require code redeploys.

This is the **final pre-Phase-19 batch** by Kyle directive 2026-05-05. After B72: Phase 16 housekeeping (TS errors + storage.ts), then Phase 19 paper-active turn-on.

**Forward-design note (Trend Mining Engine + ML-light):** with every lever DB-tunable, the post-launch ML pipeline gets a clean configuration surface to learn over. ML-light can propose `module_constants` row changes as its output without touching code.

## Goals

1. **Comprehensive lever inventory.** Every hardcoded threshold, weight, multiplier, limit, ratio, cooldown, percentile, ATR multiplier, percent-band, count-cap, score-cutoff, time-window in the active server-side codebase, catalogued with: file path, line number, current value, type (threshold / weight / multiplier / limit / ratio / window / count / etc.), candidate `module_name`, candidate resolution scope (which of the 4 dimensions are meaningful), candidate constant_name, current default to seed, migration risk rating (LOW / MEDIUM / HIGH), and reason for the rating.
2. **Promotable vs non-promotable classification.** Not every numeric literal is a tunable lever. Sweep distinguishes:
   - **Promote** — operator-tunable parameter that influences gating / scoring / sizing / exit / cadence behavior.
   - **Keep hardcoded** — mathematical constants, schema enum values, structural literals (e.g. `7` days in a week, `100` for percent conversion, array indices, regex group counts, RFC-compliant magic numbers).
   - **Already migrated** — already lives in `module_constants` (skip; record location for inventory completeness).
   - **DB-governed elsewhere** — already lives in `screener_filters` or another canonical config table (record but do not double-migrate).
3. **Migrate the Promote class.** For each promotable lever, replace the source-file literal with a `moduleConstantsService.get(...)` call wired to the right resolution key, seed the DB row(s) at the chosen resolution scope, and verify the read path returns the seeded value. **No silent fallbacks** — if the DB read returns undefined, fail hard with an explicit error referencing the missing row (Kyle directive: no hard-coded fallbacks for DB-governed settings).
4. **`LEVER_INVENTORY.md` deliverable (static catalog).** Single canonical inventory document at `1-system-manual/LEVER_INVENTORY.md` listing every catalogued lever with full classification. Read in pre-audit of every future batch to prevent re-introduction of hardcoded levers.
4a. **`CURRENT_SETTINGS_REGISTRY.md` deliverable (live snapshot, NEW per Kyle directive 2026-05-05).** Auto-generated live snapshot at `1-system-manual/CURRENT_SETTINGS_REGISTRY.md` listing every DB-governed setting and its current value + last-updated-at, pulled from `module_constants` + `screener_filters` + any other canonical config table. Regenerated by `server/scripts/dump-settings-registry.ts` (runnable on demand + invoked post-deploy). Purpose: at any moment, one place to look up "what is X currently set to?" without writing SQL.
5. **Resolution-scope discipline.** For each promoted lever, choose the SMALLEST resolution scope that makes operational sense, not the most specific possible. A single global `(*, *, *, *)` row beats six per-regime rows when the lever is genuinely regime-agnostic. Per-regime calibration is the highest-weight axis only when the lever's operational tuning is regime-driven.
6. **Document the resolution-scope choice.** For every migrated lever, record in inventory the rationale for the chosen scope dimensions so the next maintainer knows why this lever is `(*, *, *, regime)` and that one is `(*, asset_class, strategy, *)`.

## Non-goals

- **8-module architectural extraction.** That is Phase 21.4 post-live. B72 is the config-surface sweep, not the modularization itself.
- **`module_constants` schema changes.** Schema is fixed at B65.1; B72 only adds rows.
- **UI for lever editing.** A future batch may add an admin UI; B72 only ensures the rows are queryable + writable via SQL/Drizzle.
- **Adjusting current values.** B72 migrates levers AT THEIR CURRENT VALUES. Any tuning is a separate decision in a separate batch — B72 is a structural migration only, not a calibration batch.
- **Frontend client-side levers.** Client-side magic numbers (animation durations, layout constants, etc.) are out of scope. Server-side only.
- **TypeScript error cleanup.** That is Phase 16. B72 must not introduce new TS errors but does not address existing ones.
- **Storage.ts modularization.** Phase 16.

## §A. Numbered Objectives

### A.1 Audit pass — full active-codebase sweep (Step 2)

For each of the following directories, walk every `.ts` file and identify candidate levers. Output each finding into `LEVER_INVENTORY.md` (Step 2 deliverable, reviewed by Langston before any code is written):

1. `server/core/` — math kernels (regime, EV, friction, cost-model, geometry, classifier paths).
2. `server/services/` — all pipeline services (signal-orchestrator, vts-runner, paper-execution-engine, MCE, SQE, RTB, TCL, FX5, modulators, archivers, run-mode controller, B62/B67/B68 services).
3. `server/strategies/` — every canonical strategy (17 active).
4. `server/risk/` and `server/execution/` — guardrails, position sizing, exit logic.
5. `server/api/` and `server/routes/` — only behaviors-influencing constants (rate limits, default page sizes if they affect filtering, etc. — usually a small set).
6. `shared/` — shared constant declarations actively imported by server-side runtime.

Sweep technique: ripgrep numeric-literal patterns + manual file-by-file review of any hot-path service. Cross-reference against `module_constants` rows already seeded so already-migrated levers are not re-counted.

### A.2 `LEVER_INVENTORY.md` schema

Each row in the inventory contains:

| Column | Description |
|---|---|
| Lever ID | `B72-<NNN>` sequential. |
| File | Repo-relative path. |
| Line | Line number at audit time (annotate if line shifts post-migration). |
| Symbol / context | Variable name + 1-line context. |
| Current value | Literal as it appears today. |
| Type | threshold / weight / multiplier / limit / ratio / window / count / cooldown / percentile / ATR mult / etc. |
| Classification | PROMOTE / KEEP / ALREADY_MIGRATED / DB_GOVERNED_ELSEWHERE. |
| Candidate `module_name` | If PROMOTE — proposed module bucket. |
| Candidate resolution scope | If PROMOTE — which of `(exchange, asset_class, strategy, regime)` are meaningful for this lever. |
| Candidate `constant_name` | If PROMOTE — proposed name. |
| Migration risk | LOW (pure replacement) / MEDIUM (callsite touches hot path) / HIGH (multi-callsite, tight coupling, regime-frozen code). |
| Risk rationale | One-line reason for the rating. |
| Notes | Cross-references, deferral rationale, etc. |

Inventory closes with a summary: total count by Classification, total count by Migration risk, total count of PROMOTE rows scheduled for B72 implementation.

### A.3 Implementation pass — surgical migration of all PROMOTE rows (Step 3)

For each PROMOTE row in the inventory, in ascending Migration-risk order (LOW first, HIGH last):

1. **DB seed migration.** Single Drizzle SQL migration `drizzle/migrations/2026-05-XX-b72-lever-sweep.sql` that INSERTs every promoted lever's initial row(s) at the chosen resolution scope, with current literal as `value`. One migration file for the whole batch unless individual sub-groups warrant separation for review clarity (Langston call).
2. **Source replacement.** Replace the literal with `await moduleConstantsService.get({ moduleName, exchange, assetClass, strategy, regime, constantName })` (or the `getNumeric` / `getNumericRequired` helper as appropriate). Hot paths that need synchronous reads use the existing 60s cache or pre-load on startup.
3. **No-fallback enforcement.** Reads MUST throw on undefined return (`getNumericRequired` or equivalent). No `?? defaultValue` shorthand for any DB-governed lever. Bootstrapping order: every promoted lever must be readable before the consuming service starts handling traffic.
4. **Per-row commit.** Each PROMOTE row gets a self-contained code change traceable in the change list.
5. **No behavior change.** B72 is a structural migration. Verification confirms current-value reads back equal to old hardcoded value at every callsite. Any behavior delta is a B72 bug.

### A.4 Verification (Step 7)

For every PROMOTE row:

1. **DB row exists** at the seeded resolution scope. `SELECT * FROM module_constants WHERE module_name = ... AND constant_name = ...` returns the expected row(s).
2. **Source no longer contains the literal.** Grep confirms the literal is gone from the original file.
3. **Read path returns the seeded value.** Either via direct DB read or via observable system behavior (admit count, exit decision, regime classification, etc. unchanged from B70-final baseline).
4. **PM2 logs clean.** No new "module_constants row missing" errors. No new TS errors. CI green (Test Suite + Build + Docker Build minimum; legacy TS Check baseline acceptable).
5. **Operational tuning sanity check.** UPDATE one representative promoted lever's value via SQL, confirm the cache TTL respects the 60s window, confirm consuming code picks up the new value within the next cache cycle. Revert.

## §C. Risks + mitigations

1. **Risk:** Inventory undercounts. A lever is missed → ships to live still hardcoded.
   **Mitigation:** Step 2 inventory includes a "reverse pass" — grep all hot-path services for any numeric literal not on the inventory list. Langston second-pass reviews the inventory completeness.

2. **Risk:** Resolution scope chosen too narrow → operator must seed multiple rows for the same lever.
   **Mitigation:** Default scope is GLOBAL (`*, *, *, *`) unless there is documented per-dimension calibration intent. Per-regime / per-strategy / per-asset-class scope only when there is concrete operational reason.

3. **Risk:** Resolution scope chosen too wide → operator cannot tune per-regime when it matters.
   **Mitigation:** Scope choice rationale documented in inventory. Future batches can promote a lever to a more specific scope by adding rows; can never demote silently.

4. **Risk:** Migration introduces silent fallback by accident → DB row missing produces wrong value at runtime.
   **Mitigation:** Mandatory `getNumericRequired` (or equivalent) for every promoted lever. CI test seeds an empty DB and asserts service startup fails hard if any required lever is missing. (Implementation detail: Step 2 specifies exact bootstrap-order requirement.)

5. **Risk:** Cache staleness causes operator confusion. They UPDATE a row, behavior doesn't change for 60s.
   **Mitigation:** ADJUSTMENT_FRAMEWORK.md documents the 60s cache cycle. Optional follow-up: add `moduleConstantsService.invalidate(moduleName)` admin endpoint (not in B72 scope; flag as candidate post-B72 enhancement if Kyle wants it).

6. **Risk:** Hot-path async DB reads add latency.
   **Mitigation:** Service uses 60s in-memory cache. Tight loops pre-load values once at cycle start, not per-iteration. Spot-check PM2 latency post-deploy.

7. **Risk:** Calibration windows in flight (B67.4 / B68.x closing 2026-05-15 → 2026-05-17).
   **Mitigation:** B72 does not change behavior. Same value, different storage location. Calibration data integrity preserved. Verify in Step 7 that B67/B68 ablation rows continue accumulating normally post-deploy.

## §D. Open questions for Langston (Step 1 review)

1. **Scope-choice default.** B72 defaults to GLOBAL `(*, *, *, *)` unless documented otherwise. Confirm this is the right default vs. defaulting to `(*, asset_class, *, *)` since asset-class expansion is the primary post-launch driver.
2. **Inventory granularity.** Some hot-path constants (e.g. cache TTLs, internal poll intervals) are infrastructure-level rather than trading-decision levers. Should those promote to module_constants, or stay hardcoded as engineering-controlled? Recommendation: KEEP for pure infra, PROMOTE for anything that influences trading decisions.
3. **Migration grouping.** Single SQL migration vs. risk-tiered multiple migrations. Recommendation: single migration for atomic rollback simplicity; if Langston prefers per-tier separation for review clarity, swap to that.
4. **Strategy-internal levers.** Each of the 17 canonical strategies has internal thresholds. Should B72 sweep into strategy files, or are strategy levers reviewed separately by strategy-author? Recommendation: include in B72 sweep, classify per-strategy in inventory, defer any HIGH-risk strategy lever to a follow-up if Langston flags individual cases.
5. **`getNumericRequired` ergonomics.** Confirm the existing service helper signature is sufficient for hot-path use (or whether B72 needs to add a synchronous `getCachedNumericRequired(...)` for tight inner loops where awaiting a Promise is awkward). Recommendation: add the sync helper if any HIGH-risk inner-loop migration needs it; defer otherwise.
6. **Inventory structure.** Single flat `LEVER_INVENTORY.md` vs. partitioned by directory (`LEVER_INVENTORY_CORE.md`, `LEVER_INVENTORY_SERVICES.md`, etc.). Recommendation: single flat file with sortable table; prune-on-completion is straightforward.
