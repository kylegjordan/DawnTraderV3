### 2.1 OBJ-1 — THE CREW-LOGIN DESIGN (r4)
1. **Setting it.** A root script generates a value that passes `validatePasswordStrength` (`server/services/auth-service.ts:10-16`) and writes it **only** to `/etc/dawntrader/staging-api.env` (`0600 root:root`). It writes the **bcrypt hash (cost 10)** with **`WHERE username = 'testuser123'`**, asserts `UPDATE 1`, then confirms with one `dt-api` call. ⛔ **The value and the database URL never appear in argv:** the value goes in on stdin or an fd, and the DB credentials come from `PGPASSFILE` or the environment (`ps` is world-readable; the `agent-staging-session:21-23` house rule). Why not by email: the login resolves username and then email (`routes.ts:950-954`), and `testuser`'s email reads `testuser123`. Why not the admin route: it needs an admin session (`:1196`) that no session holds.
2. **`dt-api <METHOD> <path>`** runs as root. It talks only to `http://localhost:5000` and accepts only `GET/POST/PUT/PATCH/DELETE`. The path must start with `/api/`. **It refuses `/api/admin/users*`, `/api/auth/*` and `/api/user/profile` with `REFUSED: dt-api does not call account or credential routes`.** It uses no shell, and it **reads stdin only for POST, PUT and PATCH**.
3. **The token cache** lives in `/var/lib/dt-api/` (root, `0700`), is replaced atomically, and is opened with `O_NOFOLLOW`. **It re-mints only on `authenticateToken`'s own 401s** (`routes.ts:184,190,219,240`) or on a local `exp` check, never on any 401. It retries at most once per call, under a `flock`. That is because the limiter allows 5 logins per 15 min, counts every attempt, and all localhost callers share one bucket (`routes.ts:86-92`, `server/index.ts:175`). Other routes also return 401 without the token being stale (`:961`, `:1011`, `:1039`, …).
4. **`dt-api mint`** is for the agents' browsers. It does a **fresh login and prints the token pair** to stdout, once per agent per day. ⚠️ This **hands `deploy` a bearer token**, and that is stated. Refresh cannot help, because it always fails (`routes.ts:1031` → `:144-146` → `:1038-1040`, a `B-SEC-HARDEN` item).
5. **Access.** The four sessions reach `dt-api` as root. **Langston** reaches it through a sudoers entry for `deploy` covering exactly `/usr/local/bin/dt-api`. **Coltrane** gets a browser only: `agent-staging-session` calls `dt-api mint` over Langston's existing key. **Both** Helsinki password files (`/etc/langston/staging.env`, `/etc/coltrane/staging.env`) and the script's public-host login (`agent-staging-session:46`) are retired (`DELETED_COMPONENTS_LOG`).
6. **OBJ-1(h) is a GATE with a named action, not an observation.** The hash write updates a `users` row, so it can move `testuser123` ahead of `kylegjordan` in physical order: freed slots are reused, so an update can land lower. If it does, **the daily-loss KILL and WARNING banners** (`daily-loss-budget.ts:257-267`, first owner) and the `users[0]` consumers (`cle-orchestrator.ts:481,:765`, `context-loader.ts:298`) **follow the crew account.** ⇒ **Disposition 1 on the §9.4 scale: this batch pins ONE site before the hash write — the daily-loss banner target — to the owner account by explicit identity**, because this batch's own write is the trigger and that banner is the one tied to risk. The remaining picks stay with `#1092`. After the write, the order is re-measured and recorded on `#1092`, whatever the result.
