## Pre-Governance History (Phases 1-11)

> **Reconstruction basis**: `bridge/canonical/` materials in the repo, especially `DawnTrader_Complete_Project_History.md`, `Phase_8_Implementation_History.md`, `Phase_9_Implementation_History.md`, `Phase_10_Implementation_History.md`, and `Phase_11_Implementation_History.md`.
>
> **Important**: These phases predate the current governance/batch-documentation system, so the summaries below are historical reconstructions rather than batch-level records.

### Phases 1-3 — Initial Platform Build + Walter Era
The earliest DawnTrader build established the core V1 trading platform: FX5 scanning, a 9-strategy engine, RTB queuing, paper-trading lifecycle, and a Stage-3 event-store style truth engine. During this same era, Walter was integrated as an OpenAI-backed AI sysadmin/advisory copilot with memory, intent, reasoning, and expert-corpus components.

### Phases 3-4 — Walter Sidelined, LATTi Created
Walter was removed from the real-time path because API latency, throttling, and cost made him unsuitable for live-loop decision support. LATTi/Lottie was then created as a local, embedded, passive-only telemetry/tuning layer, establishing the long-running split between offline strategic AI guidance and local runtime behavior.

### Phases 4-5 — Failed V2 Attempt
A full V2 rewrite was attempted and failed catastrophically. The historical record makes clear that this period damaged continuity rather than improving it, and it directly motivated the later restoration and rebuild discipline.

### Phases 5-7 — Restoration and Early Refactoring
After the failed V2 path, DawnTrader went through restoration and structured cleanup to recover the working V1 system. This was the bridge into the more explicitly documented Phase 8.x era.

### Phase 8 — Foundation Repairs, REB Restoration, End-to-End Pipeline Recovery
Phase 8’s stated mission was to fix and complete the paper-mode trading engine without Lottie active in the loop. The canonical Phase 8 history breaks the work into:

- **8.1** — accounting-model / FX5 output repairs

- **8.4** — breakdown-accuracy fixes
- **8.5** — batch-selection repair
- **8.6** — top-end rotation + UI integration
- **8.7** — reactivation of unused filters

- **REB 1.0-2.12F** — emergency restoration of lost functionality
- **8.8.1** — scanner-output audit
- **8.8.2** — signal-engine audit

By the end of Phase 8.8.3, DawnTrader again had a functioning end-to-end scanner → signal → RTB → paper-trade pipeline.

Phase 9’s mission was to finalize DawnTrader’s mathematical core and establish single sources of truth for quantitative calculations.

**Diagnosis (B-NEW-40 pre-audit, Langston rev1 + rev2 reviews):** two stacked contributors.

**Lessons captured for future debugging context:**

1. **Fire-and-forget patterns must have a timeout escape hatch.** Any `await someAsyncOp()` chained with `.catch().finally()` that relies on the awaited promise eventually settling will silently lock its surrounding coalescer/in-flight tracker if the underlying promise hangs. The fix is `Promise.race([op, timeout])`, never just `op`. This is a general pattern, not specific to TEC.

2. **pg-pool's default `keepAlive: false` is dangerous on long-lived Node processes with cross-region database connections.** SO_KEEPALIVE must be explicitly enabled, and `keepAliveInitialDelayMillis` set short enough (10s is the empirical sweet spot) to actually detect dead sockets within a useful window — Linux default 2-hour `tcp_keepalive_time` is unusable.

3. **"Zero log events for the catch handler" is a smoking gun for a hung promise.** If a `.catch` clause never executes despite thousands of downstream symptoms, the underlying promise is neither resolving nor rejecting. That's not a "rare race"; that's a hung await on a dead I/O channel.

4. **Exact-duplicate-duration log clustering is the fingerprint of "trapped Map entry, every reader re-evaluates the same fixed check."** Distinct from a recurring network blip, which produces a distribution of durations.

**P19-B6.5e shipped 2026-06-18 — the spot where a ready-to-buy crypto signal was silently vanishing instead of opening a trade is now fully visible and accounted for, and that visibility revealed the real reason no crypto trade opens: the system is correctly turning every crypto signal down because its profit-vs-cost math is running on placeholder inputs ✅** (run autonomously with Langston per Kyle's directive · `P19_B6_5e_COMPLETION_REPORT.md` · `PHASE_19_PLAN.md` §1/§5). The previous batch left one blocker: a sized crypto signal would clear the buy queue and then never actually open a position, with no error and no reason — the system's own counter showed signals were "attempted" but neither opened nor blocked, so they were disappearing into a blind spot. The root cause was exactly that — a blind spot: the open step didn't report a result, it just ran and quietly stopped at any of about seven exit points without recording why, and the layer above it guessed "did it work?" by checking whether the trade count went up. So a failed open looked identical to nothing happening. The fix made the open step report a real, typed outcome and added a third counting category — "open failed, and here's the stage it failed at" — so the system's open-path tally now always balances (attempts equals opened plus blocked plus open-failed) and can never hide a vanished signal again. This was proven on the live server with a contained crypto trial run that was switched back off afterward: the counter reconciled and named the exact stage every time. **And naming the stage is what produced the real diagnosis:** the crypto open is NOT broken in execution — it runs all the way to the profit-expectancy gate and is HONESTLY turned down there, because after trading costs the expected value comes out slightly negative on every crypto signal. The gate is working correctly and must not be weakened. The actual reason it never clears is that the profit math is being fed placeholder inputs — the same default win-probability and market-condition numbers on every signal instead of each signal's real values — which is a previously-known gap. Feeding the real inputs (not touching the open path) is the lever that will let genuine signals clear and open.
