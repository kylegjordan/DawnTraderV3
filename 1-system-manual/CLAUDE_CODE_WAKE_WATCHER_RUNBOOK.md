## 1. THE ARM COMMAND (verbatim; §4.5 carries the same — the two must not drift)
Run via **Bash with `run_in_background: true`** (since 2026-09-30, `B-TOKEN-BURN-CUT` `#1127`):
```
S=C:/Users/kyleg/.claude; A=<ALIAS>; L=$(cat /proc/$$/winpid); grep -q LEASE_V1 "$S/cc-wake-filter.py" || { echo "WATCHER-UPGRADE: install the leased filter, then re-arm"; exit 0; }; while :; do P=$(python3 "$S/cc-wake-filter.py" $A --positions --loop $L) || break; ssh -o ServerAliveInterval=60 -o ServerAliveCountMax=2 -o ConnectTimeout=15 root@204.168.141.77 "python3 - $P" < "$S/cc-wake-follow.py" | python3 -u "$S/cc-wake-filter.py" $A --once --loop $L; [ "${PIPESTATUS[1]}" = 0 ] && break; sleep 30; done
```
**The task ends on the first message for you, and its completion notification is the wake.** Read the task's output file (the `WAKE[...]` lines, each tagged `[src=<file>@<offset> id=<message_id>]`), act, then re-arm with the same command. It resumes from `C:/Users/kyleg/.claude/cc-wake-state/<ALIAS>.json`, so nothing written between two arms is lost; a burst is delivered as one wake. `cc-wake-follow.py` is never installed on Helsinki — the laptop pipes it over ssh, so the laptop copy is the only copy.
`<ALIAS>` = CC-A | CC-B | CC-C (your roster-bound name — `(repo)/.claude/cc-session-roster.json`; unbound → ask Kyle + register, NEVER infer from role).

## 2. THE TRAPS (each with its incident — the content this home exists to preserve)
- **⚠️ THE 06-19 TRAP, NOW USED ON PURPOSE:** a background Bash task notifies only when it EXITS, so the 06-19 `while true` watcher, which never exited, never woke anyone. The event-only watcher is built on exactly that property: it EXITS on the first message, so its one exit notification is the wake. **A watcher that does not end on a message is the broken one.**
- **⚠️ THE MONITOR FORM IS RETIRED (2026-09-30):** since CC 2.1.271 every Monitor ends within 30 minutes (`CLAUDE_CODE_FEATURE_WATCH.md`, the 2026-09-15 row), and each ending woke the session with nothing to say — measured in `B_TOKEN_BURN_CUT_PRE_AUDIT.md` §0. Do not arm a Monitor for the wake watcher.
- **⚠️ THE BACKGROUND FORM WAS CUT AT 30 MIN ON SOME BUILDS (NEW Claude, 2026-10-05) — NOT on the current one.** CC 2.1.285 put a 30-min default on `run_in_background` commands in ALL sessions; 2.1.288 restricted it to unattended runs (`-p`, SDK, CI) — `code.claude.com/docs/en/tools-reference` "Time limit for background commands". Measured 2026-10-06: an Infra watcher armed 21:50Z was alive at 22:25Z. If a task ever reports "stopped after reaching its background time limit" in an interactive session again, note the app version and raise `BASH_DEFAULT_TIMEOUT_MS` (env, ms; no settings key) rather than re-arming in a loop.
- **⚠️ MULTI-file tail, never split:** the single `tail -F` over all three files keeps the `==>` headers the filter needs to attribute lines; three single-file tails lose them.
- **⚠️ TaskList CANNOT verify the watcher (06-25 trap):** it shows todo items only. **ONE WATCHER PER SESSION IS ENFORCED, NOT INSTRUCTED (`B-WAKE-ARM-EXCLUSIVE`, `#1140`):** the arm loop passes its own Windows pid (`--loop $L`, read once before its `while`; keep `--loop` AFTER the mode flag) and the filter holds a lease (`~/.claude/cc-wake-state/<ALIAS>.lease`) on that loop. A second arm is refused before it reads anything: stdout empty, exit 5, and one line whose FIRST WORD the session acts on — `WATCHER-STAND-DOWN` (a watcher of yours is live: do NOT re-arm) · `WATCHER-STUCK` (running, not saving: stop it, re-arm) · `WATCHER-ORPHAN` (readers with no live loop, all listed: stop them, re-arm) · `WATCHER-OLD-ARM` (an arm older than the lease: re-arm with the current command) · `WATCHER-CENSUS` (the reader census could not prove it ran: re-arm once, then stop and tell Kyle) · `WATCHER-INTERPRETER` (not python.exe: tell Kyle) · `WATCHER-UPGRADE` (the installed filter predates the lease). A refusal can take up to ~122 s (two 60 s census attempts). `.alive` and `bash ~/.claude/cc-wake-count.sh <ALIAS>` (readers: a number, `unknown: …` when the census fails, `n/a` off Windows) are DIAGNOSTICS, never the guard.
- **THE POSITION CANNOT BE SAVED OR READ (`B-WAKE-STATE-UNSAVED-LOUD`, `#1151`, 2026-10-07):** two more first-word lines, on stderr, which can follow a `WAKE[` line in the same task output — so look for them on ANY line, not only the first. `WATCHER-STATE-UNSAVED: <state dir> errno <n> (<reason>) — …` means the folder `~/.claude/cc-wake-state` cannot be written: the run still ended and the message was delivered, but the position was not saved, so the next arm delivers the same message again (a duplicate, never a loss). When it says *"the watcher was away over 12 h; anything posted since <time> was NOT delivered"*, sweep the Discord inbox from that time by hand. `WATCHER-STATE-UNREADABLE: <state file> …` means the position file exists but cannot be read or parsed (permissions, or an empty, truncated or garbled file): the watcher refuses to resume (an empty start would skip everything posted while away, and lose the saved time that triggers the "you were away" notice) — sweep the inbox from the last time you were woken, then delete or fix the file. ⚠️ The one realistic way to get an EMPTY position file is a host crash during a save (the save is atomic by rename but does not fsync), so after a crash this line means: delete `~/.claude/cc-wake-state/<ALIAS>.json` by hand and re-arm — the refusal is the intended stop, not a bug (Langston, Step 4). **For either: re-arm once; if it repeats, stop and tell Kyle — the folder's permissions need fixing.** ⚠️ While saves fail, `.alive` is not refreshed by the watcher (only a successful keepalive save refreshes it), but a run that delivers and then fails to save exits with `.alive` still fresh from its last keepalive — up to 15 minutes in which the heartbeat cannot see that no watcher is running (measured and pinned by `scripts/analysis/test-wake-state-unsaved.py` OBJ-4).
- **⚠️ The app may end idle background tasks when the laptop is short of memory** (CC 2.1.193). Kyle decided 2026-09-30 to change nothing: the hourly heartbeat's liveness check is how we find out whether it ever happens.
- **⚠️ Compaction USUALLY kills the watcher but NOT always** (2026-06-25 it survived) — the doubled-event check is the reliable dedup, not an assumption either way.

## 3. THE THREE RELIABILITY LAYERS (all outside the conversation, so they survive compaction)
1. **SessionStart hook** (`.claude/settings.local.json`, matcher `startup|resume|compact`): auto-injects a re-arm reminder every start/resume/compaction. Act on it FIRST thing that turn + sweep the Discord inbox for anything missed.
2. **The rule in both loaded files** (`CLAUDE.md` §6.9 + shared MEMORY §4.5-pointer): the reloaded post-compaction context always carries the instruction.
3. **Hourly heartbeat** (scheduled task `wake-watcher-heartbeat`): reads every session's `.alive` file on the laptop and wakes NOBODY when all are alive; a stale one is first COUNTED (`~/.claude/cc-wake-count.sh`): 0 = DEAD, reported with `--notify` to Kyle, because a dead watcher cannot be reached through itself; 1+ = STUCK (running, not saving; since the lease, 2+ means an arm older than the lease), reported without `--notify` because the post reaches it; `unknown: …` = the census failed, reported as CENSUS-FAILED, never as DEAD (`B-WAKE-OUT-OF-BAND`, after live, is the out-of-band fix). Once a day it plants `WATCHER-CONTROL <ALIAS> <date>` in `cc-wake.log`; a live watcher answers with `<ALIAS>.json.control` — no print, no wake.

**Honest residual gap:** a fully-CLOSED desktop session — nothing to wake. Platform limitation, unfixable from here.
