## 3. What is built today (code at the ref and on Helsinki; measured today)

### 3.1 Design as built
- **One worker, one queue:** `task_q = lq.TaskPriorityQueue()` (`discord-langston-bridge.py:1288`), one `task-worker` thread (`:1294`), `task_worker` (`:755-785`) does `get → process_task → task_done` serially. Alert lane has its own queue/worker (`:1297-1301`, `alert_worker :977`) — a second worker only for alert triage.
- **What triggers an invocation (`on_message`, `:1089-1257`):** (i) Kyle: any message naming "langston" anywhere (`ADDRESS_RE :81`, check `:1201-1202`); (ii) a CC post that STARTS with "Langston" (`ADDRESS_START_RE :85`, check `:1204`); (iii) voice from Kyle; (iv) any alert-webhook post (`:1248`) — with the lane on, routed to the lane first. Every accepted post is `task_q.put(...)` (`:1257`) and **every queued task costs one full `claude -p` invocation** (`invoke_claude :268`, called `:603`); there is no content check — nothing in the bridge looks at whether the post asks for anything. The only no-post exits after the invocation are `[SILENT]` (stripped, replaced with an ack if empty: `:611-621`) and bridge-error suppression. **So a post that leads with "Langston" but asks nothing DOES cost a full invocation (~6 min) and gets a reply.** The gate's own comment (`:1143`) says the lead-with-name rule exists *"so CC's ACK / bookkeeping posts never burn a paid Langston turn"* — i.e. the only existing lever is the sender not leading with his name.
- Review requests also feed the self-advance queue only if `lq.is_review_request(prompt)` (`:502-508`) — not a throttle.

  - **The design I would propose (a batch, for Kyle's list through PM — not started):**
    1. Two task workers over the existing priority queue.
    2. **A per-batch lane:** a task whose opening carries a batch id is held while another task for the same batch id is running, so a batch's rounds are reviewed in arrival order. Tasks for different batches, and Kyle's own messages, run in parallel.
    3. `breaker` becomes shared, under a lock.
    4. A per-invocation scratch directory (`TMPDIR`) so two invokes never share a scratch file name. This also covers the `/tmp` exposure class that `B-AGENT-PRIVATE-TMP` (row 13) is about.
    5. `SYSTEM_IMPACT_MAP.md:2974`'s MUST is amended, with the dead reason replaced by the new invariants: one worker per batch, and memory writes by CAS.

    7. **The pre-registered test:** the median wait for session posts falls under **20 min** over the first full working day, measured with the same message-id-to-handling-time method as §3.2.
  - **Weekly usage and Kyle's 85 % stop line (PM's consideration, added round 1b):**

Two workers turn that idle time into work, so the sessions spend allowance faster. When the week does not reach the line (76 % with about 2 h to the reset today), more work gets done and usage moves up toward 85 %. When the week would reach it anyway, the same allowance is spent earlier in the week and the stop comes sooner. **It does not raise the total that can be spent; it moves the stop earlier.** I cannot put a number on the rise from Langston's box; the crew's burn is read where PM reads it.

When it is set, neither worker starts a new invocation, finishes the one in hand, and the queue is kept for later. This gives PM a "stop at a good point" that cannot catch either lane halfway through a review.

      4. The pre-registered test gains a usage leg: the week's usage share at the time of the stop line, compared with the prior week, reported alongside the wait median.

- **Langston, round 1 (msg `1568020720724869231`, ~22:05Z):** **AGREES: (a) two workers + (f) as queued, and the per-batch lane.** Re-derived the box himself (2,608 MB available, load 0.07, ~259 MB per invoke): **two is the right ceiling, not a pool.** Four conditions:
  - **C1 (BINDING): compare-and-swap protects the FILE, not the WRITE.** The installed `/usr/local/bin/langston-memory-write` (2,929 lines) takes `fcntl.flock(LOCK_EX)` at `:613`, blocking, and compares at `:1406` (LEDGER.md), `:2064` (whole file) and `:2190` (part). A mismatch is `Refused(4)`, nothing is written, and there is **no retry anywhere in the tool** (`retry|backoff|LOCK_NB`: 0 lines). The loser of a race has its content dropped, and the party who must notice is a stateless invoke at the end of its turn. Two workers make that race routine (upper-bound base rate: 24 snapshots today against 190 invokes, about 13 % of invokes write), and what is lost is a ledger retraction. ⇒ **retry-on-4 inside the tool (re-read the sha, re-apply, bounded attempts), OR memory and ledger writes routed through one serialising lane.**
